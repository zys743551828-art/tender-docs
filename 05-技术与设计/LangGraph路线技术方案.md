# LangGraph路线技术方案

本文给出以LangGraph为AI执行核心的候选架构，用于路线选择，不表示已经切换正式系统。业务规则以[工作台PRD](../02-业务与产品/AI投标工作台PRD.md)为准，评分算法以[评分预测方案](评分预测训练与验收方案.md)为准。原件、证据、业务事务、模型适配和发布资格沿用[全新系统技术方案](AI投标工作台全新系统技术方案.md)中的职责契约；本文独立维护替代执行层的设计，不继承其Temporal部署要求。

## 1. 组成与运行方式

采用React／TypeScript前端、FastAPI领域API、LangGraph Worker、PostgreSQL及pgvector、私有对象存储。LangGraph使用持久checkpointer候选PostgresSaver／AsyncPostgresSaver，准确的发行版本、连接管理及恢复行为须完成适配验证后锁定。

一期以少量固定业务图执行评审、改稿建议和知识候选处理；图内仅在证据不足等明确条件下做有上限的模型与工具循环。上传核验、文件解析、索引、导出和训练可以作为普通后台任务运行，不要求所有程序都转换成Agent节点。

生产运行区分三个变体：开源LangGraph配合Celery等成熟队列；LangGraph配合官方Agent Server；开源库配自写PostgreSQL调度。前两者优先作为完整生产路线比较，自写队列仅作受控实验或小规模备选。Agent Server已提供队列、恢复和线程并发策略，自托管涉及Enterprise授权、PostgreSQL、Redis和正式部署要求，具体来源见[执行路线复核](../01-背景与市场研究/AI执行与工作流选型复核.md)。

以下第2—6节详细展开嵌入式Worker与PG任务表变体，用于暴露必须补齐的运行契约，不代表推荐生产上完全自写调度。采用成熟队列时以其领取与确认协议替代任务表领取；采用Agent Server时以其运行记录、队列与checkpoint替代自建图调度，业务事实与发布仍经领域服务。各路线都不依赖HTTP请求存活或FastAPI进程内BackgroundTasks。

## 2. 总体结构与状态归属

~~~mermaid
flowchart TB
  U[项目对话、卡片、历史与知识] --> A[FastAPI：查询、命令、认证]
  A --> P[(PostgreSQL：正式业务、任务与事件)]
  A --> O[(私有文件与证据产物)]
  P --> W[Worker：领取与恢复任务]
  W --> G[LangGraph：评审与建议图]
  G --> C[(独立schema：图checkpoint)]
  G --> D[领域服务：幂等写入与资格检查]
  D --> P
  G --> M[模型适配端口]
  G --> R[按用途检索与完整章节包]
  R --> P
  R --> O
  P --> E[持久事件SSE]
  E --> U
~~~

| 信息 | 主记录 | 边界 |
| --- | --- | --- |
| 项目、稿件、正式决定、提交、成绩、知识发布、模型资格 | 业务表 | 不从图状态或聊天文字推断正式事实 |
| 待执行任务、领取、执行代次、取消与重试安排 | 任务表 | 负责谁能运行和何时运行，不另存一份可写的逐节点流程真值 |
| 图输入、节点进度、中断与中间结果引用 | checkpoint | 用于图恢复；不能授权提交、成绩核验或模型发布 |
| 文件、解析产物、判断和报告的字节 | 对象存储，身份在业务表 | checkpoint保存引用与摘要，避免重复存大文件和完整正文 |

业务表和checkpoint可共享PostgreSQL实例，使用不同schema和最小必要凭据；两种写入并不因此成为同一事务。备份须覆盖业务关系、checkpoint和对象字节，不能只备业务表。

## 3. 图的划分

| 图或任务 | 过程与产物 |
| --- | --- |
| ProjectAssistantGraph | 识别意图→读取当前项目→调用允许的查询或任务工具→返回文本／领域卡片引用；工具循环有上限 |
| ReviewGraph | 冻结本轮资料→准备规则与事实→否决／强制核对和评分子任务→证据与覆盖校验→汇总本轮报告 |
| ScoreJudgmentGraph | 构造干净评分输入→组装逐项完整章节包→每项三次有效判断→特征→适用模型预测→资格校验 |
| RevisionAdviceGraph | 读取本轮有效问题→检索适用参考→产生修改草稿→校验引文与工程前提→等待采纳决定 |
| KnowledgeCandidateGraph | 读取允许来源→形成候选条目与适用条件→校验证据→人工核验后通过领域命令发布 |
| Import／Train／Export任务 | 资料核验、固定划分训练、统计评测和导出按确定流程执行；AI不动态修改测试集或发布协议 |

主会话可以触发多次独立任务，每次任务建立operation_id，并绑定graph_run_id、thread_id、graph_version、输入版本、方法和用途。业务标识与LangGraph的thread_id建立显式映射；thread_id只是checkpoint命名空间，不提供项目授权或互斥。

普通对话可以读取项目记忆；正式评分使用新的干净图执行，从ScoreInputBuilder获取白名单资料。图内输入边界同样适用于子图、工具返回、检索、摘要与缓存，不能把主对话的消息列表直接传给评分子图。

## 4. 评分图如何执行

~~~mermaid
flowchart LR
  A[冻结生效招标与目标稿] --> B[评分结构及页级证据]
  B --> C[逐项完整章节包]
  C --> D[按项有界并发与三次判断]
  D --> E[结构、引文、覆盖与失败校验]
  E --> F[版本化特征]
  F --> G[适用且已验收的统计模型]
  G --> H[预测资格、区间与报告]
~~~

评分方法保持四层路线。LangGraph只组织执行，最终分数仍来自正式成绩监督的统计模型。比较锚定按评分方案作为受控对照；多家模型协作的新增方案暂缓。

每项判断使用稳定的逻辑键，例如review_run＋评分项＋重复序号＋方法摘要。重试仍是同一次判断；三个有效结果分别保留身份，不能用重复投递凑次数。章节包与证据存为不可变产物，图状态保存引用及读取缺口。

对不同评分项和重复判断有界并发，模型调用通过统一端口控制速率、预算和超时。图状态的并行结果按稳定键合并，重复键不得重复累加，全部预期子任务终态明确后才汇总。不得让并发节点共同追加一个无去重规则的列表，再据此计算分数覆盖。

失败时保存已完成的有效产物，只重跑符合复用条件的缺失逻辑步骤。关键图页或评分项无法读取时，保留缺口并限制估分资格；统计模型不适用时仍可显示有出处的判断，不发布合格总分。线上与训练使用相同的输入和特征定义。

## 5. 嵌入式变体的调度、恢复与幂等

1. API在一个业务事务中创建operation、任务、审计和事件，返回任务身份；任务表在此承担持久派发职责，不再要求Temporal启动Outbox。
2. Worker通过短事务领取可执行任务，保存执行者、执行代次、租约和尝试身份，然后在事务外运行指定版本的图。
3. checkpoint按已验证的持久模式保存。任务表仅投影执行状态，逐节点恢复位置以checkpoint为准；“最后一次完成的业务对象”也不能替代图恢复位置。
4. 节点先检查相同逻辑步骤是否已有有效产物，再调用外部服务；领域提交用唯一操作键及输入摘要实现幂等。业务提交与checkpoint之间可能崩溃，恢复节点必须能读取既有结果。
5. 取消先记录请求，Worker协作停止并核验后确认终态。网络故障按明确上限退避，输入或权限错误不盲目重试；模型调用可能重复计费，记录所有尝试。

必须防止两个Worker同时推进同一graph_run。任务租约、thread_id和SKIP LOCKED本身不足以阻止租约过期后旧Worker继续写入。自动接管要求执行代次同时约束领域写入及checkpoint提交，且校验与相应写入具有原子性；不能先查租约再无保护地提交checkpoint。

标准PostgresSaver能否满足上述互斥与提交契约，需要适配验证；不能因为支持PostgreSQL就假定已经支持执行代次隔离。该项未完成前，保守运行方式是不自动接管疑似仍在执行的任务，先停止并确认旧执行者退出，再受控恢复。未通过并发恢复门槛时，限制试点范围，不宣称高可用。

大文件解析与长模型调用在checkpoint之前中断仍可能重做。必要时拆成有独立结果身份的小步骤，不能声称任意故障后都会精确从上一行代码继续。

## 6. 人工中断、会话恢复与版本

需要人工决定时，节点先持久保存候选和action_id，再以interrupt等待，工作进程可以退出。用户通过明确按钮确认，领域事务核验对象版本、身份和用途，保存决定并建立唯一恢复任务；Worker通过Command(resume=...)恢复对应图。

恢复参数只携带决定引用，不能信任前端传来的“已批准”。恢复节点重新读取决定与当前前提；对象变更、成员失效或来源撤回时转为重新确认。interrupt恢复可能从节点开头执行，中断前的逻辑必须幂等，正式业务副作用放在有效决定核验之后。

等待人工确认不持续占用Worker。新稿产生新review_run，不修改旧图输入；旧图完成也不夺取当前轮次指针。关闭聊天窗口不取消任务，浏览器重开后从业务快照和持久事件恢复展示。

graph_version参与运行身份，部署保留对应版本的执行器，或先验证明确的状态迁移。不能用新图代码盲目加载旧checkpoint。图的步数、补查轮数、上下文及token设上限；达到上限返回带缺口的阶段结果，而非无限循环。

## 7. 相比Temporal路线的取舍

| 事项 | LangGraph路线的变化 |
| --- | --- |
| 部署 | 嵌入式变体省去Temporal服务端，增加checkpoint及队列或自有调度；Agent Server另计服务、Redis、授权与运维 |
| AI开发 | 节点、条件边、子图与中断直接表达AI任务；业务工具仍需类型化契约 |
| 运行恢复 | 需要自己完成任务调度、同run互斥、故障接管、重试预算、取消与对账 |
| 业务一致性 | 继续使用领域事务、幂等、输入冻结和审计；checkpoint不替代它们 |
| 评分精度 | 编排框架本身不提高预测精度，仍由真实判断质量、标签和独立评测决定 |
| 适用边界 | 适合当前少量固定AI流程；长等待、定时、跨服务流程扩大后应重新比较运行成本 |

嵌入式路线便于直接开发AI流程，团队承担额外运行保障；官方Agent Server提供更完整执行能力，同时增加部署和商业条件。采用哪种运行方式应比较真实任务、恢复要求与维护总成本，不能仅凭图画得直观或组件数少决定。

## 8. 交付与验收

先交付一条评分纵向链路：冻结资料→完整章节→三次判断→证据回看→特征与基线评测。首批10—20份材料用于核验资料和判断质量，不代表精度达标。最小工作台与实验入口并行，训练、发布和正式提交仍受各自主规格约束。

| 必验场景 | 预期 |
| --- | --- |
| Worker在判断或写入前后退出 | 有效产物可追踪，重试不产生重复业务决定；额外外部调用如实计量 |
| 两个Worker领取或旧执行者失联 | 同run互斥与代次隔离有效；未验证前不自动接管 |
| 多评分项并发、重复结果与部分失败 | 稳定键去重，失败和覆盖准确，汇总不提前通过 |
| 人工等待后重启、重复确认或旧卡确认 | 有效决定仅消费一次，恢复后重新验证业务前提 |
| 新稿先完成、旧稿后完成 | 当前结果仍指向正确输入版本 |
| 聊天已出现成绩后发起评分 | 正式评分输入、子图、缓存和检索不携带目标标签 |
| 图代码升级与数据库／对象恢复 | 旧checkpoint可以由对应执行器恢复，数据引用可核对 |

## 9. 证据与自审边界

已有[LangGraph隔离实验](../04-验证与测试/全新技术方案验证与自审.md#32-langgraphinterrupt恢复的重复执行)验证SQLite checkpoint关闭、重开和重新编译后可以恢复，并复现中断前逻辑重复执行；业务唯一操作键可以控制实验中的重复副作用。

未验证：PostgresSaver／AsyncPostgresSaver、任务领取和自动接管、跨进程并发checkpoint、真实模型、生产部署、升级与恢复。上表是待执行验收要求，不是测试通过记录。既有Temporal或旧应用测试不作为本路线已实现的证据。

自审结论：不能省略独立Worker；不能将thread_id当互斥或权限；不能把interrupt当业务授权；不能把checkpoint和业务库当一个事务；不能忽略并行结果去重；不能让聊天上下文污染评分；不能把框架选型当精度证据。完成这些适配与故障验证后，才具备正式路线替换的依据。
