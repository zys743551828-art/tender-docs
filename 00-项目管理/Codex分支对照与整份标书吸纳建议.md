# Codex分支对照与整份标书吸纳建议

项目定位为公司内部的工程投标标书工作台。招标文件与补遗是评审依据，整份投标文件是管理、编制辅助、核对与提交登记的工作对象；施工组织设计是技术部分中的一种内容。资格、商务、技术、报价及附件按具体项目要求组织，可分册也可合卷，不强制每个项目采用相同目录或相同文件数量。

当前 dev 的可部署评审链路保留。Codex 分支的工作区、身份、参考资料和比较机制值得吸纳；两套实现都仍以单个正文版本作为核心评审对象，整套标书需要补文件包和适用范围机制。整份标书的产品范围已经确定，以下吸纳次序属于实施建议，尚未实施的部分不计为已交付。

## 2. 整份标书范围的关键差距

当前 `FileRole` 可区分招标、补遗、图纸、清单、正文、提交稿、成绩和其他资料，但没有资格／商务／技术／报价分册的明确结构。`current_materials.active_body` 及流水线从多个 body 中选一个，快照、判断与预测绑定一个 `body_version_id`。同时上传资格册与技术册，不会自然变成“整套投标文件均已核对”。提示词也明确以技术标／施工组织设计正文为对象。[D1][D2]

Codex 用工程项目、标段轮次和投标主体细分身份，并有 `SubmissionDocuments` 供选择文件，但其 `bid_profiles.current_body_id`、`review_inputs.body_version_id`、提交闸门和两轮比较也仍围绕单稿。文件选择器不能证明多分册整体评审已经存在。[C2][C3]

因此，两个版本的主体模型都需要扩展。需要按项目招标要求识别资格材料、商务承诺、技术正文、报价文件及附件；识别出多个文件并不等于相应内容已检查，缺件也不能直接等同于正文未响应。

| 能力 | 当前 dev | Codex 分支 | 整份标书需要的吸纳或补齐 |
| --- | --- | --- | --- |
| 投标工作单元 | 项目名称、标段、轮次，提交时冻结这些字段 | 工程项目、标段轮次、投标主体、工作单元分别建模 | 吸纳身份分离；同工程不同标段、联合体／不同主体、重新招标不能串材料，主体规则须以项目资料为准 |
| 分册与附件 | 多资料上传，核心只选择一份正文 | 多文件选择与资料快照，核心仍选择一份正文 | 新增本轮投标文件包；按用途选择多个精确文件版本，同一 PDF 可标逻辑分册范围 |
| 条款适用范围 | 规则有条件和来源，核对主要面向单正文 | 有 applicability_scope、来源及规则上下文 | 吸纳范围表达；补“适用哪类文件、主体、标段、条款、时间”的结构化目标，不能把全部条件都到技术正文中找 |
| 资料完整性 | 解析覆盖、缺页与扫描阻断已有 | 项目／来源／解析资格更细，有受检范围守卫 | 从解析完整性扩为招标所要求材料清单，区分缺件、未提供、未检查、无法识别、已核实及不适用 |
| 跨文件一致性 | 当前正文数字及范围检测 | 身份和来源机制较丰富，不能据此认定整套标书一致性已验收 | 新增主体、项目编号、标段、工期、人员、报价等跨册事实对照；不同主体／时间／单位先消歧，再判断冲突 |
| 提交登记 | 绑定一份正文与对应快照 | 仍绑定单稿，但另有已发生事实补录及事前检查时间守卫 | 提交对象升级为精确文件包，分别记录实交事实和系统已核对范围；单册通过不得推导整包通过 |

上述六项优先级高于进一步美化评分说明，也高于整套搬入富文本编辑器。它们决定“检查整份标书”是否成立。

## 6. 目标结构与接入次序

以下名称为设计建议，不是已经存在的 API 或数据表。

### 6.1 标书文件包

一个投标工作单元关联工程、标段、轮次和主体；每轮文件包选择全部待提交分册及附件的精确版本。逻辑条目记录用途、关联要求、主体、原件、解析身份、核验范围和 Word／PDF 对应关系。单 PDF 合卷可以用逻辑分区关联原页；多 PDF 不预先拼成一个新文件来掩盖各自版本和缺口。

招标／补遗依据包与我方投标文件包分别冻结。新增文件后先显示变化及受影响范围，不能沿用“最近上传的正文就是整份最新投标文件”的推断。评分输入按规则选择相关文件范围，资格核对按所需材料检查，不因其他无关册部分解析失败就虚构某条已失败，也不能借相关性推测把未知范围排除。

### 6.2 条款和检查结果

规则增加适用目标及所需材料类型，保存来源、效力、确认状态和无法确定的条件。确认状态与生效状态保持独立。每条检查分别报告输入范围、缺失材料、解析缺口、判断与证据，整份报告按资格、商务、技术、报价及附件汇总，可追溯到具体文件和页。

技术分、商务分、价格分、综合分分别记录对象和满分；沿用现有技术分预测的资格和校准边界。尚未建设的其他评分模型不得借界面改名取得资格。签章、加密、平台文件及回执按实际可核查证据记录；系统未检查的格式或平台要求保持未检查，文件包齐全不等于平台已接受。

### 6.3 建议实施顺序

| 顺序 | 交付内容 | 完成判断 |
| --- | --- | --- |
| 1 | 产品范围、术语与工作对象统一 | 主记录明确整份标书，区分现有单正文能力与目标范围；本次完成文档层统一 |
| 2 | 投标主体、文件包及要求清单契约 | 支持合卷和分册、每项精确版本、缺件和不适用；旧快照不变，多文件不互相顶替 |
| 3 | 包级核对与整套提交身份 | 资格／商务／技术／报价证据按适用范围读取；跨文件冲突、缺附件、未知解析范围有回归；只通过一册不能放行整套 |
| 4 | 两轮比较与实际提交补录 | 能说明哪些内容改变、规则或方法是否变化、哪些问题真正复检；历史实交不伪称事前检查通过 |
| 5 | 企业资料与历史项目的只读复用 | 主体／有效期／适用条件和引用版本明确，参考不自动变为事实或训练样本 |
| 6 | 项目会话、目录计划与局部修改 | 对话可恢复、建议可预览、保存与版本冲突可见，按选定来源和范围工作 |
| 7 | 受控模板与正文构建 | 分阶段确认文本、表格、图片、目录和实际分页；生成稿必须绑定真实产物再评审 |

AI 状态解释、图注敏感性、真实解析质量与完整浏览器链路继续作为质量专项；应围绕以上标书范围组织样例，不继续只用施组单稿增加通过项。真实最终标书与官方技术分配对仍为独立评分验收的必要资料。

## 7. 需要重估的进度

既有 A1—A5、B1—B7 清单描述的是单正文评审融合进度，12 个模块已有实现或受限版本的结论仍只适用于该清单。不能将它换算为整份标书工作台的完成率。

整份标书目标下，文件包、条款适用范围、缺件、跨册核对与包级提交属于核心增量。章节编制、历史与企业资料需要按使用价值重新排期。两个分支的已有成果可以降低实现成本，但都不能直接计作整包能力已完成。本次对照不执行 Codex 程序，不修改运行系统、数据库或自动化。
