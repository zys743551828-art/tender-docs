# AI执行与工作流选型复核

本文维护Temporal、LangGraph、Dify及成熟任务队列的生产路线比较。业务输入为[工作台PRD](../02-业务与产品/AI投标工作台PRD.md)，评分方法为[四层评分方案](../05-技术与设计/评分预测训练与验收方案.md)。通用组件资料见[成熟方案调研](成熟AI系统与技术组件调研.md)，本文专门比较完整落地路线，避免用开源库与完整平台直接排名。

## 1. 结论与推荐边界

成熟度需要分层判断：Temporal针对通用持久业务执行；LangGraph针对AI图、状态与中断；Dify针对可视AI应用和知识工作流。它们各自有成熟机制，不能据此给出一个通用优劣顺序。

结合本产品的实际提交、成绩核验、来源版本和人工决定要求，**独立领域API、成熟任务运行机制、可单独评测的Python评分模块是确定的结构；具体执行器保持候选状态**。项目长期存在不等于一次后台运行必须长期等待。首版固定任务优先比较成熟队列配合普通Python或有界LangGraph；确有跨步骤持久等待、定时与复杂恢复要求时优先比较Temporal。评分步骤目前清晰，不必为了AI产品形态引入多层Agent运行时。

LangGraph是可行的替代路线。若采用它作为主执行框架，生产优先评估**LangGraph＋官方Agent Server**，而不是直接把“开源库＋自写PostgreSQL队列”认作最成熟的整体方案。Agent Server补齐任务队列、恢复和线程并发策略，但自托管涉及Enterprise授权、PostgreSQL、Redis及正式部署运维；接受这些条件后，它是完整竞争路线。

首批10—20份评分资料核验与算法实验可以独立运行，先建立输入、证据、逻辑调用、产物与断点身份，不等待生产引擎。Dify适合快速验证知识应用和可视流程；正式项目核心仍需要领域服务。公开产品的工程对照与14份官方网页核查见[相似产品技术核查](相似AI产品技术路线核查.md)：直接行业披露支持证据、文档关系、受控调用和人工复核，但未公开足以决定本项目执行器的恢复协议。商业运行时预算、数据出口和运维能力未明确前，不自动采购、部署或切换任何路线。

## 3. 关键核查结果

### 3.1 LangGraph：必须区分开源库与Agent Server

开源库提供图、checkpoint、人工中断、节点重试等机制。官方fault-tolerance文档列出节点超时、重试和错误处理，部分能力有最低版本要求；checkpointer支持保存同一super-step内已经成功的节点写入，不能笼统声称“节点失败就要把整图重跑”。应用仍需定义稳定步骤、幂等和恢复入口。

官方Agent Server已包括持久任务队列、线程与run、取消、流式通知、租约和恢复。文档说明同一thread最多一个run执行；enqueue／reject等并发策略属于部署运行时，并非只安装LangGraph库就具有。官方“exactly once”描述限于其队列／尝试语义，不能推导外部模型计费或业务数据库副作用也恰好一次。

自托管Agent Server的官方说明要求PostgreSQL、Redis、license key；自托管概览要求Enterprise方案。Redis承担临时信号与pub/sub，持久run状态在PostgreSQL，不能将Redis当其持久任务主库。官方当前反复测试的生产路径为维护的Kubernetes Helm部署；Docker／Compose示例面向开发、小规模或测试，其他编排需补齐优雅退出、伸缩和升级。不能称其“只多一个轻量开源库、没有授权或运维负担”。

开源LangGraph库本身是MIT，无需因为Agent Server的授权条件而否定库的使用。托管Cloud、BYOC、自托管的服务边界和价格分别核实，不能把自托管Enterprise条件套到全部产品，也不能凭文档获得具体报价。

### 3.2 Dify：有工作流恢复，完整投标业务仍需适配

已核对到Celery后台执行、暂停状态序列化、恢复入口与人工输入策略，以及暂停／恢复集成测试源码。Dify可以承接人工工作流，不能以“只支持简单对话、不能等待人工或恢复”排除。上述源码也不能证明其任意故障恢复已经通过我们的要求。

Compose包含API、Worker、Web、数据库、Redis、插件及若干隔离／代理服务，并带多种可选数据库和向量后端；并非所有profile必须同时运行，不能用文件中全部服务数夸大部署成本。完整平台减少模型接入、知识维护和可视调试开发，但本产品的实交稿、官方标签、来源链、独立评测和模型验收仍须领域模型与API。

合理的平台路线是业务服务持有正式事实，Dify通过明确工具或API读取冻结资料、返回候选产物；评分训练独立运行。需核验工作流、检索结果、平台日志及缓存的用途边界，不把全量聊天和成绩直接同步为通用知识。

许可为附加条件的Apache体系。多租户与前端标识条件按选定版本核对；仅后端API使用的前端条件与直接复用其Web界面不同。内部单工作区使用具备可评估路线，许可不是默认排除它的理由。

### 3.3 Temporal：业务恢复完整，正式部署并不免费

服务架构文档明确事件历史与重放、Workflow／Activity分离；Activity必须按幂等或不重试等策略处理副作用。任务队列、持久等待、超时和恢复由运行时承担，有明确的服务端和SDK职责。这与投标系统跨文件、评审、人工决定和批量任务的运行需求相符。

官方Helm路线需要运行Temporal服务组件并自行提供default和visibility持久存储；两者都可以采用合适的SQL后端，不必默认引入Elasticsearch或Cassandra。服务角色、schema升级、认证、备份、历史保留和Worker版本均有运维成本，不能拿CLI开发模式当生产简化方案。Temporal Server采用MIT许可，托管服务价格及网络可达性另核实。

该方案的主要收益是减少自研任务运行保障，不是提高LLM质量。评分方法、证据、领域事务和业务发布仍需我们实现。

### 3.4 Celery：成熟队列可以比较，任务确认策略不能省略

Celery是成熟后台任务路线，适合固定批任务；与LangGraph组合比完全自写队列更值得评估。官方文档明确任务应幂等，默认可能在执行前确认；acks_late、Worker子进程退出及task_reject_on_worker_lost有各自语义。启用重试不等于自动取得完整恢复保证。

使用Celery需选择并维护broker、确认策略、超时、取消、重复执行防护和checkpoint恢复入口。长时间人工等待可保存为业务决定，在确认后派发下一任务；不要让Worker一直阻塞等待。跨多步骤恢复和图的同run并发仍须设计，不能把Celery当作无条件等价的Temporal替换。

## 4. 对完整路线的比较

| 路线 | 已有成熟能力 | 本项目主要追加工作 | 适用判断 |
| --- | --- | --- | --- |
| 领域API＋Temporal＋普通Python评分模块 | 持久任务、等待、重试、取消、事件历史和Worker协议 | 业务与AI模块；生产运维、升级和幂等 | 对跨步骤持久运行需求匹配；须验证实际收益与维护能力 |
| 领域API＋LangGraph＋官方Agent Server | AI图、持久执行、队列、并发策略、流式与人工中断 | 业务事实、用途隔离、授权／费用和正式部署适配 | 接受其运行与商业条件时的完整替代路线 |
| 领域API＋普通Python／LangGraph＋Celery | AI模块和成熟队列分别提供能力 | broker、图恢复入口、并发控制与对账；仅在需要时引入图checkpoint | 首版固定任务的优先对照，不能省略故障验收 |
| 领域API＋LangGraph＋自写PG调度 | 图与数据库能力成熟 | 全部任务运行保障、失联接管及checkpoint互斥 | 范围受控的实验／小规模备选；不优先作为成熟生产路线 |
| 领域API＋Dify后台API＋独立评分服务 | 模型接入、RAG、可视工作流、现成管理体验 | 两边版本、产物、用途和业务状态衔接 | 快速知识应用和低代码调整价值高时优先；完整投标系统需适配 |

5名在线成员、2个并行评审、约300个案例是初始负载假设，不足以证明任何方案必然能承载，也不足以自动排除Temporal。真实页数、图表、评分项、模型延迟、批次峰值和恢复要求才决定容量与维护成本。

目前评分步骤是明确的资料准备、完整章节判断、特征与统计预测。它可以由普通Python函数／模块实现并交给执行器调度。出现可证明有收益的自适应检索或复杂分支时再引入LangGraph；采用Temporal主执行时，首批无需再维护一个独立持久的图调度系统。

## 5. 采用与推翻条件

1. 首先完成独立评分纵向链路与真实资料核验，固定输入、方法、逻辑调用、产物及标签隔离；编排框架不进入预测算法定义。
2. 首版先按领域API＋成熟队列＋可替换AI模块对照开发与维护成本；有必要的图使用LangGraph。按统一协议核验重投、失联接管、状态衔接与恢复，未经验证不宣布该路线天然可靠。
3. LangGraph主路线优先取得Agent Server实际授权与部署条件，按同样协议验证；若能降低整体维护成本并满足资料和业务约束，可替代Temporal，不因既有推荐排除。
4. 实际任务需要跨步骤持久等待、统一定时、取消和恢复历史时，比较Temporal最小生产或托管配置的收益；同时验证维护责任、认证、备份、升级、恢复及成本。需要频繁可视调整AI流程时比较Dify后台API路线，不凭框架印象淘汰它。
5. 每条路线只保留一个明确的任务运行主记录，领域事实持续由业务服务管理。模型建议不直接发布知识、登记提交或批准模型。

## 6. 同条件验证与自审

统一使用相同文件规模、2个并行评审和固定模型响应故障注入，测量完成时间、恢复时间、重复外部尝试、重复业务决定、人工恢复步骤及全部运行服务成本。真实模型质量与费用另测，不让供应商响应差异掩盖执行器差异。

| 故障／边界 | 所有候选必须达到的要求 |
| --- | --- |
| 任务刚接收、正在调用、业务已提交但执行未确认时退出 | 任务可定位；恢复不重复决定；额外模型尝试可追踪 |
| 两个执行者、失联后接管和重复投递 | 同一运行受控，旧执行者不能继续提交有效新结果 |
| 人工中断后重启、重复确认、对象版本变化 | 批准不丢、不重复消费；恢复时重新核验 |
| 服务／数据库短暂不可用 | 明确失败或等待，不把不可用写成通过 |
| 新旧稿乱序完成与图／工作流代码升级 | 当前结果指针正确，保留运行可按对应版本恢复 |
| 聊天、知识或缓存出现正式成绩 | 正式预测输入和派生资料保持隔离 |
| 备份、恢复和供应商停用 | 原件、决定及运行状态可对账，模型路由可回退 |

上述跨路线验证尚未执行。当前结论是依据公开机制、源码和本产品约束作出的工程推荐；不是三套生产系统实测排名。预算与运维证据可推翻推荐，评分误差和区间覆盖仍须真实官方成绩独立验证。
