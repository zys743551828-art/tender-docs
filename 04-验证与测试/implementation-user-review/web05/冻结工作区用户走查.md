## 主要问题

### W05-U01：保存禁用时缺少就地缺项说明（P2）

触发：完善候选版本，已选主体、地区、类型、用途、期限、无额外事实前提、真实出处，遗漏“特殊条件与范围说明”。滚到“保存候选新版本”时按钮禁用，附近没有缺项说明；因为按钮禁用，原生必填校验也不能通过该动作触发。实际 DOM 中该范围说明 `required=true`、`valid=false`，但页面未将原因告诉用户。

用户影响：长表单末尾无法知道应回到哪里，可能误以为来源解析或保存服务未就绪。“无额外事实前提”也容易使人忽略另填适用边界的要求。本次得到 Owner 提示后，通过界面补填才保存成功，没有降低守卫要求。

最小改进：沿用现有校验，在保存处显示尚缺的字段与定位入口；范围说明旁解释即使不设事实前提也需要说明边界。Frontend Owner 已回复在 06 主源码补缺项清单与短提示；05 原输入未改，本次没有实际复核 06。

复核任务：在新候选故意只漏该说明，确认能从按钮附近知道缺项并键盘到达；补齐后只做原有一次保存，无新增确认或审批。未来请真实新用户完成同任务，观察是否仍需帮助。

证据：`knowledge-version-probe-current.png`、`30-authoritative-sources-selected.png`、`31-candidate-v2-saved.png`；机器复现说明与字段证据见 `result.json`。

### W05-U02：影响范围的项目计数与引用行混在一起（P2）

触发：仅对同一个目标项目登记两次参考，每次知识版本包含两处原页来源；停用后打开当前版本影响。

实际显示：“在办项目 · 4”，四行都是同一个项目，两两项目名、用途和时间完全相同。实际只涉及 1 个不同项目、2 次人工参考登记；此处按什么对象计数没有说明。

用户影响：容易把来源引用数误读成四个受影响项目，也不易区分重复行应核哪一个。没有据此认定服务器重复写入同一操作或数据损坏。

最小改进：按不同项目归组并正确显示项目数，引用展开项说明引用／来源单位及固定摘录。若确实展示引用条目，标题直接使用引用单位，保留不同来源的辨识信息即可。

复核任务：使用同一项目两次引用、每次两处来源，确认不会显示为四个项目；每条仍能追溯当时摘录和原页。具体发现已交 PM／Frontend Owner，整改尚待新候选实际核对。

证据：`42-current-version-impact-history-discovery.png`、`knowledge-history-discovery-result.json`。

## 观察项与边界

- 刷新后历史引用入口实际存在于“查看当前版本影响”。本次最初在参考表单附近找不到，Owner 指路后完成；这属于可发现性观察，不是“没有历史功能”。未来真实任务可用“停用次日找回上次引用依据”验证是否需要更直白入口。
- 首次知识来源位置在本次实际请求中返回 200，未遇到 SOURCE_NOT_READY；不能借此宣布未部署的 source-readable 解耦修复通过，也没有绕过来源守卫。该未就绪／就地重试反例仍需在受控状态执行。
- 分片实际为 2 片，包含一次失败与一次丢 ACK；没有做大规模并发、跨浏览器批次发现、跨设备会话、长期断网或生产对象存储验收。当前 API 未提供的批次集合发现没有被冒测为通过。
- 初次探针使用错误的对象存储片号匹配方式，未命中中断；另有定位器把出处复选框误写为按钮、原页先有展开再打开两步、过早刷新中断探针等自动化限制。早期截图文件名含“ack-lost”不等于已注入成功；只有 `multipart-resume-result.json` 记录的服务器 202 后 abort 才作为丢 ACK 通过证据。`knowledge-withdraw-real-result.json` 中临时 `citation_url` 实为知识详情地址，不能作为引用深链通过证据；停用后历史通过依据是后续真实版本影响入口的两份 history 记录。
- 没有执行正式评审、评分、模型研究、付费调用、Word 接收、正文构建、报告／提交、RAG 质量评测、生产安全认证、真人测试。没有把本地渲染或本批浏览器闭环写成生产通过。
