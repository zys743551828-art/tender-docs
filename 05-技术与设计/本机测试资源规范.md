# 本机测试资源规范

适用本机 Docker 一次性工程验证。持久开发环境与正式业务数据分别管理，测试不得继承真实模型、对象存储或业务数据库凭据。

## TEST-DOCKER-LIFECYCLE

脚本使用应用仓 `workbench/deploy/disposable_docker.py` 的 `DockerTestRun` 上下文，包括服务创建和启动。每次生成唯一 run ID、资源名与 `tender.test.run` / `tender.test.disposable=true` 标签；创建前记录目标，创建后保存精确 ID。镜像只用已有本地缓存，数据使用本轮新建卷或 tmpfs，避免匿名卷，源码只读挂载。

正常、失败、超时及 Python 取消均执行收尾。逐项 inspect 核对标签和 ID 后按依赖逆序删除本轮资源，不按全局前缀清理。回执只记资源身份和清理状态，不保存环境值或命令输出。所有权变化、daemon不可访问或删除失败时，保留未关闭回执和具体待处理对象；不能把检查失败当作资源不存在。

进程强杀、断电与 Docker 不可用无法保证自动清理；恢复后据回执逐项检查。不得调用 system/volume prune，也不能把原开发环境或历史资源登记为本轮临时资源。代码使用方法见[应用说明](https://github.com/zys743551828-art/tender-app/blob/dev/workbench/docs/docker-test-hygiene.md)。

## TEST-DOCKER-NATIVE

`tests/test_disposable_docker_native.py` 要求显式的已核验本地 Python 镜像及全新证据目录。三个用例分别真实创建容器、隔离网络和合成数据卷，验证成功、失败、取消后资源均不存在。默认未提供镜像时跳过，不能计为通过；测试镜像不得包含或挂载业务凭据。

`fusion_desktop prepare/up` 属于保留的开发环境操作，不作为一次性测试入口。既有 `fusion_checks` 复用指定环境，不负责删除该开发环境。

## 历史资源处理

先盘点精确容器 ID、项目标签、停止状态、镜像与数据挂载。删除历史容器须有当次明确范围；保留所有未知镜像、数据卷、绑定目录和本轮新资源。容器即使停止，未挂载文件仍可能只在可写层；删除前必须说明丢失后果并取得对应授权。运行中的对象须先确认用途，不用 force 停止。

用户对具体容器范围及可写层丢失后果确认后，逐个复核原 ID 并删除容器，禁止 `-v`、prune 或扩大到清单外。已不存在的对象记为先前已清理，结果不确定先检查而不盲目重试。审计记录保留删除/跳过/失败清单，以及卷和镜像身份集合的前后校验。

本机实际验证与历史清理结果见[验证记录](../04-验证与测试/本机环境与Docker收尾验证.md)。
