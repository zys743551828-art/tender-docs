# AI 投标工作台产品化方案

本文是当前方案的整合入口，说明产品、评分、检索和技术建设如何组成一条工作链。详细业务行为统一维护在[AI 投标工作台 PRD](AI投标工作台PRD.md)，算法与验收统一维护在[评分预测训练与验收方案](../05-技术与设计/评分预测训练与验收方案.md)，架构与运行契约统一维护在[全新系统技术方案](../05-技术与设计/AI投标工作台全新系统技术方案.md)。本文不另设字段、状态或精度门槛。

## 1. 产品定位与主要参考

公司内部市政工程投标工作台，以降低否决风险、提高技术标质量和验证评分预测为业务主线，结合上传即评审、风险优先的简洁流程与GovDash式项目工作区、章节编辑和随页助手。用户在同一项目中接收招标资料、核对要求、编制章节、检查否决风险、改善评分项、生成版本、登记实交稿与正式成绩。AI助手在当前工作页面就地协助，默认结果先回答“哪里有风险、下一步做什么”，需要时展开完整报告。

产品采用浅色分组侧栏、项目表格与筛选、项目功能菜单、章节编辑、右侧AI助手／来源面板、版本下载和任务运行记录。当前投标、历史项目、企业知识保留可发现的独立入口，企业知识与资料库共用同一知识记录。已核查的公开页面、图片及对应设计见[交互与视觉设计](../05-技术与设计/交互与视觉设计.md)；未取得的后台细节不声明为像素一致。

| GovDash产品做法 | 本产品落点 |
| --- | --- |
| Proposal列表、资料包、目录和正文 | 投标项目→招标资料→响应矩阵→章节编制→版本与导出 |
| 逐项要求与响应目录关联 | 要求、章节、当前正文证据、否决风险和评分项可联动定位 |
| Dash随页辅助、来源选择及选区操作 | AI助手可侧栏／全屏展开；显示项目、章节、来源和修改差异 |
| Agent模板与运行记录 | 预置检查、补遗影响和章节建议任务；手动、事件或显式定时运行，结果回到原项目 |
| Data Library与模板 | 文档、企业知识、公司事实、目录及版式模板分别管理 |
| Versions及Word/PDF下载 | 冻结工作草稿生成文件，按具体PDF评审，实交稿另行登记 |

美国联邦公告发现、Capture、Contract等入口按市政业务对应关系组织为项目概览、招标准备、提交与结果及历史档案。本产品的正式范围见PRD第2节；本次核心不增加美国数据源、销售CRM、合同履约、套餐计费或岗位权限体系。中国市政规则和企业事实由实际资料核验，不能直接套用美国L／M／C章节或CUI分类。

### 1.1 两套产品逻辑的取舍

以下为同一批任务的设计走查判断，未在GovDash登录产品或真实用户中做计时对照。

| 用户任务 | 原方案的优势／负担 | GovDash做法的优势／负担 | 本产品默认行为 |
| --- | --- | --- | --- |
| 已有招标和正文，只想知道风险 | 上传即评审、结果先给风险，路径短 | 资料包与目录便于管理，但编制设置可能增加首次操作 | 保留上传直达评审，跳过目录和模板设置 |
| 看懂一个问题并核对依据 | 风险优先清楚；报告、原文与对话之间可能来回切换 | 矩阵与章节、来源联动，适合持续核对 | 问题、要求、正文和来源可就地切换 |
| 改一章并沿用可靠参考 | 建议清楚，但复制、外部编辑与上传形成断点 | 章节、计划、参考与正文同页，选区修改可预览 | 采用章节编辑与来源辅助，保留外部Word上传 |
| 收到补遗，确认哪里要改 | 自动重评容易理解，但改动影响不够集中 | 要求与响应关系能支持定向核对 | 先列补遗影响与未知范围，接续实际复检 |
| 编制、生成、反复修改和交付 | PDF检查强；持续编制及版式交付入口较弱 | 目录、正文、模板、版本下载形成完整工作面 | 采用GovDash式编制主线，明确草稿与正式文件区别 |
| 截止前检查和登记提交 | 否决风险及提交闸门更贴合本业务 | 通用提案阶段不能替代中国市政否决条件 | 保留明确的提交检查与实交稿登记 |

产品按任务融合：日常先上传、看风险、处理一件最重要的事；需要持续编制时，在同一项目进入章节、参考和版本工作区，AI随页辅助。用户可以只检查现成标书，也可以在产品内完成改稿，无需选择或配置两种模式。目标体验是“有稿直接查，需改就地改，结果有依据，实际提交可追溯”。

产品验收用同样的真实任务观察用户能否独立完成、在哪些步骤卡住、是否误认版本或通过状态；没有用户试用证据前，不宣称某套已被证明更快或更满意。

下表是产品取舍约束，具体业务语义只在对应PRD章节维护；界面改造和功能交付都须核对这些约束。

| 保留的长处 | 融合到新工作区的方式 | PRD主记录 |
| --- | --- | --- |

| 外部Word及完整报告可交付 | 上传外部改稿与在线编辑都保留；完整报告、Word报告和批注PDF可直接取回 | 第10、15节 |
| 历史、知识与成绩闭环 | 独立入口直接查用，正式结果绑定实交稿，监督训练与当前评分输入隔离 | 第11—14节 |
| 一道登录门槛、少管理负担 | 不引入岗位审批、套餐或使用量经营看板，关键操作保留审计 | 第2、8、16节 |

## 2. 一次完整投标的使用方式

### 2.1 默认路径：先检查现成稿件

上传招标、补遗和正文后，只集中处理影响对象和版本的歧义。资料足够且自动开始开启时直接评审；结果先显示关键风险、评分可用性和下一步，不要求先创建目录、选模板或整理知识。

用户从问题打开原文，复核或请求修改建议；可以在原有Word中改后上传，也可在同一项目进入对应章节就地修改。采纳不关闭问题，实际新稿复检后才更新结论。没有必须处理的问题时直接进入提交检查，非阻断建议无需全部处理。关闭可选检测不消除已发现的关键风险；仍须在统一清单中有效复核或有理由驳回。

### 2.2 需要时展开：在项目内编制和改稿

只有招标、准备起草，或现有稿需要持续修改时，进入章节编制：确认候选目录，查看要求与参考，编辑正文或预览AI修改；生成具体Word/PDF版本后按设置接续评审。补遗到达显示变更、影响章节和未判定范围，原人工内容不被自动覆写。

章节页、矩阵、完整报告与助手共用一个项目和同一套问题、文件、引用及任务。跨工作面回到原位置；参考、采纳决定和问题处理进度不丢失。可以在两条路径之间切换，不复制项目或为同一文件新造独立样本。

### 2.3 共同收尾：实交稿与正式结果

登记实际提交文件与检查结论，正式成绩绑定实交稿。历史档案、可复用知识、合格样本各按自己的准入条件形成，评分模型经独立验收后才发布。技术分、综合分、入围和中标分别保存，不承诺改一段就能获得官方加分。

DOCX转换失败在原文件处保留“原件已收、对应检查未完成”并提供“上传此修改稿的PDF”；接续检查实际所选PDF，不凭同名证明Word与PDF对应，也不强迫进入编辑器。下载按钮区分投标正文、评审报告与批注审阅稿，具体用途命名以PRD第15.2节为准。

工作草稿、生成文件、评审稿与实交稿分别保存，原上传件和既有报告不被编辑器覆盖。实际生成或上传的新PDF才承载对应页级证据。用户离开页面任务继续；恢复依据业务记录，正式评分保持独立输入，不继承带成绩的聊天或任意来源。

## 3. 评分采用四层路线

| 层次 | 负责的工作 | 关键边界 |
| --- | --- | --- |
| 评分结构与章节准备 | 提取评分项、满分、档位、要点及例外；建立正文章节树和原页证据 | 同一生效资料和方法可缓存；补遗、方法或正文版本变化须更新相应产物 |
| 大模型逐项判断 | 读取完整相关章节及必要图表；判断档位、覆盖、针对性、具体性，每项重复3次并带出处 | 超长内容分层处理并记录覆盖；分歧是候选特征，三次一致不证明正确 |
| 统计模型学习分数 | 将逐项判断、结构和事前背景映射为正式技术分，比较正则线性、保序与近邻等方法 | 第一条基线不使用带成绩近邻和锚点；所有监督特征严格限于训练来源 |
| 比较式锚定对照 | 与同评分办法、已知分数的可比历史标书逐项比较 | 按独立评测的收益、偏差和费用决定是否启用，不是首版必需能力 |

大模型负责有证据的内容判断，统计模型负责与官方量尺对齐。约300份案例用于训练和验证低维监督模型，起步不训练长篇深度模型。区间来自经过独立检验的误差与校准过程，不能用三次大模型输出的波动替代。

首要验收是：在未见项目上，绝对误差稳定优于历史均值等基线，同时控制大误差、系统偏高偏低、复跑波动、失败覆盖和区间宽度。有同场配对正文才验证稿件间排序；技术入围概率还需入围规则、实际正负结果和事前可用特征，单独校准。技术分、技术入围与中标是不同目标。

具体数据准入、划分、防泄漏、建议门槛与发布条件见评分主规格，本文不把建议数值当作已经达到或已经认可的指标。

## 4. RAG与模型适配层如何支撑评分

| 能力 | 作用 | 对正式评分的约束 |
| --- | --- | --- |
| 文档与证据 | 解析文字、表格和图页，统一页码、坐标、版本与读取缺口 | 关键内容漏读不能靠校准系数补救 |
| 当前项目检索 | 定位规则对应章节、交叉引用与证据 | 检索定位后组装完整相关章节；固定少量片段不能代替整章 |
| 历史与知识检索 | 为建议提供有来源且适用的参考 | 其他项目的条件和企业事实不能自动成为当前项目事实 |
| 受控近邻与锚点 | 给统计模型或比较实验提供训练来源参考 | 与普通知识检索分开，按实验折、同源组和时间隔离正文、成绩及派生产物 |
| 大模型API适配 | 统一生成、结构化判断、视觉、Embedding与重排的能力配置、调用记录及预算 | 正式评分固定模型与方法；故障不得静默换模型、缩上下文或把错误当0分 |

RAG提升查找与依据质量，不能单独保证评分接近官方成绩。模型适配统一业务端口，不假定各家OpenAI兼容接口在结构化输出、视觉、工具、上下文和流式计费方面完全一致；供应商由真实资料质量与费用对照选出。

正式评分由专门的输入构建器从冻结版本取资料，不继承完整聊天历史。目标成绩、评委意见、事后改稿，以及携带这些信息的知识、摘要和缓存均受隔离。最终测试不用于反复调整提示词或挑选模型。

## 5. 工程形态与职责

推荐React＋TypeScript前端、FastAPI／Python领域服务、PostgreSQL＋pgvector、独立后台执行和私有对象存储。统一模型端口和独立评分实验服务连接业务链路。消息基础设施采用Kafka，固定任务由独立Python Worker按当前消费、幂等事务、租约与恢复协议执行，具体基线以技术主记录为准。框架候选的公开证据与比较边界保留在[执行路线复核](../01-背景与市场研究/AI执行与工作流选型复核.md)及[相似产品核查](../01-背景与市场研究/相似AI产品技术路线核查.md)。

业务数据库保存项目、版本、正式决定和发布资格；对象存储保存不可变原件与产物；工作流管理长任务、重试与等待；模型提出判断和操作建议。正式写入仍经过领域校验、幂等事务和审计，聊天文字不能直接改变业务事实。

起步以模块化领域服务配合独立Worker部署，不把全量知识平台、多Agent或更多中间件作为评分验证前提。模型调用发生在数据库短事务之外，重试可能产生额外计费，需要明确预算与调用记录。

## 6. 建设重点与可验收交付

先交付可用的快速评审、风险处理与评分验证；章节编制逐步接入同一闭环。正式评分实验和现成PDF评审不等待完整编辑器、版式模板或任务平台，A1快速评审先独立验收，A2按需编制逐项开放，阶段退出条件统一见PRD第19节。

| 工作 | 首个完整交付 | 通过条件 |
| --- | --- | --- |
| 快速评审与风险闭环 | 简洁项目入口、上传自动评审、关键风险、主要下一步、原文及完整报告 | 不经目录／模板／任务配置也可检查现成PDF，风险优先、失败如实显示、非阻断建议不增加提交条件 |
| 章节编制闭环 | 目录、编写计划、正文编辑、修改预览、模板选择、Word/PDF生成、基于文件的复检 | 编辑→生成→核对→评审→改稿复检完整运行；断线和并发不丢稿；页码与文件版本可追溯 |
| 评分最小链路 | 首批10—20份资料核验、完整章节包、三次判断、证据与费用失败清单 | 验证资料及模型判断，独立项目上比较统计基线；真实验收前不承诺精度 |
| 任务与资料复用 | 预置模板、运行记录、补遗影响、适用参考、历史导入及成绩核验 | 每次产物能定位来源与项目；重复事件不重复决定；来源与成绩保持用途隔离 |
| 稳定运行 | 模板和图表转换、实际上传、恢复、备份及容量验证 | 真实环境运行与恢复证据齐备；演示页面不冒充软件验收 |

正式评分实验不等待全量页面和知识平台；编辑器和模板能力也不以真实评分精度已达标为前提。正式使用始终满足否决／强制核对和提交闸门。固定任务与交互产品使用当前Kafka＋独立Python Worker基线；历史框架比较不形成另一套待定实施基线。A1可用、评分研究可运行、模型业务验收通过分别交付并附证据，首批组合演示和正式发布门槛以PRD第19节为准。

三轮核对已覆盖业务默认、跨页面状态及完整任务反例。入口与主要动作、批次触发、保存生成、取消、Word/PDF对应、预测显示、导出类型及A1/A2依赖均以PRD为准；核对记录及剩余验证边界见[三轮核对与任务走查](../04-验证与测试/PRD逻辑检查与场景验证.md#21-融合方案三轮核对)。

## 7. 状态与阅读入口
