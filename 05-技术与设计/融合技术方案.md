## 0. 融合架构约束

本方案为融合系统架构主记录，产品行为以[PRD第0节](../02-业务与产品/AI投标工作台PRD.md#0-融合目标与适用规则)为准，具体事务和接口约束见[融合详细设计](融合详细设计.md)。以Codex固定应用`27bc639`的`workbench/`为唯一代码主线，当前dev固定`45a5921`只提供择优移植机制；不并排运行两套正式API、队列、身份系统或数据库模型。

业务中心是权威输入包和本方投标包及各自不可变修订，工程／标段／轮次／主体分别标识。现有`current_body_id`、`review_inputs.body_version_id`和单正文比较／提交接口属于受限实现，F01将其提升为包身份；不建立旧库双写或迁移兼容层。正式评分只使用包中明确适用的技术子范围，完整相关章节扩展和解析覆盖独立核验。单文件上传保留为形成一成员包的便捷路径。

正式技术底座为PG17＋pgvector、Kafka＋独立Python Worker、同源API／上传与私有OSS端口。既有PG16演示和供体Celery等仅是来源证据，不反推目标部署。先核已有Python、Node、Docker、镜像和Word运行时，版本锁以融合实测结果为准，不重复安装。前端统一采用PRD第0.3节的视觉及交互，基础组件候选不决定最终页面风格。

包、文件、解析、规则、事实、方法、用途和效力分别冻结并形成摘要；订正追加新身份，历史清单、证据和报告不改写。不完整历史证据保持明确未知，不能按时间倒推出精确冻结。异步producer提交前核包／草稿修订、来源效力、取消、归档和fence，迟到成功不能覆盖当前结果。预算unknown不归零、不自动重发；管理DSN、LOGIN业务角色和NOLOGIN预算组隔离，未审SQL不可当环境初始化入口。

架构选择不代表实现验收。Codex已有真实评分实验、实际基础设施与hardMock机制证据保留各自边界；新组合按融合任务门重验。当前正常业务Word服务继续保留，融合环境独立命名空间，不启动已关闭的Claude测试容器。供体具体入口与反例见[供体映射](../00-项目管理/融合目标规格与供体映射.md)。

## 1. 设计前提与结论

本方案按从零建设设计，不受既有技术栈、任务实现、数据库结构或部署清单约束。业务输入为[AI 投标工作台 PRD](../02-业务与产品/AI投标工作台PRD.md)。没有旧系统迁移、旧接口兼容、状态映射或双系统切换需求；历史标书与成绩作为新资料入库。

推荐总体结构：React19＋TypeScript工作区；Python／FastAPI模块化领域服务；PostgreSQL17＋pgvector向量数据库与RAG服务；Kafka＋独立Python Worker；私有对象存储；独立评分实验与受控模型发布。AI通过类型化工具读取、解释和提出操作，正式决定由领域事务执行。知识和历史检索、评分预测、成绩复盘使用不同用途的上下文。

消息基础设施按用户要求确定为Kafka；任务由独立Python Worker执行，消费位点、阶段收据、重试、取消及部署协议以[详细技术设计](融合详细设计.md)为实施主记录。Kafka和PostgreSQL之间按Outbox及领域幂等处理，不宣称外部模型与存储端到端恰好一次。Celery、RabbitMQ和Temporal不作为当前部署依赖；相关调研与隔离实验保留候选机制证据身份，不代表已采用。

RAG从首批建设，pgvector承担向量存储与检索，不因没有独立向量服务而省略语义检索。链路包含解析、保留证据位置的分块、Embedding、词法／向量混合召回、重排端口、上下文与引用核验。正式评分只借助RAG定位，再扩展完整相关章节，不用普通聊天片段替代评分范围。

这是目标技术规格，不是已经完成的系统。官方资料、候选比较和许可依据见[成熟方案调研](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/01-背景与市场研究/成熟AI系统与技术组件调研.md)。实际执行的隔离实验、反例和限制见[验证与自审](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/04-验证与测试/全新技术方案验证与自审.md)。涉及未配置模型、OCR权重、云存储或生产环境的部分保持未验证。

### 2.2 决定及复审条件

| 编号 | 决定 | 理由与证据 | 复审条件 |
| --- | --- | --- | --- |
| N-ADR-01 | 模块化单体领域API，Worker独立部署；暂不拆微服务 | 关键操作需一个事务，当前内部团队不需要分布式业务写入 | 团队边界、部署或容量实测证明需要独立扩展 |
| N-ADR-02 | Kafka＋独立Python Worker执行固定任务 | 用户指定Kafka；消费与业务状态分离，副作用以领域幂等保证 | 对位点、再均衡、重试、取消与升级进行真实故障验收，保留基础设施选择 |
| N-ADR-03 | 单个PostgreSQL事务域保存事实、版本、操作决定、引用和检索元数据 | 并发、回滚、旧卡和撤回检查可在数据库内控制 | 独立压测证明索引负载影响事务预算 |

| N-ADR-08 | ReactSPA＋可替换聊天组件＋领域卡片 | 内部产品无需SEO；统一Python领域API；组件可复用基础交互 | 组件适配验证不通过则用同一协议替换界面库 |

业务事实与向量检索可位于同一PG实例，采用不同schema、角色、用途视图与资源预算。Kafka只传对象引用和事件，任务状态、来源和最终结果在业务PG。SSE来自领域持久事件，不直接把Kafka连接暴露给浏览器。

基础依赖为API、Worker、Kafka、PostgreSQL＋pgvector和私有对象存储；当前不要求RabbitMQ、Celery、Temporal、Redis、专用向量服务、Kubernetes或多Agent协作。生产Kafka与真实云／模型适配需要故障和容量验证，开发单节点不能替代生产容灾。

## 4. 事实归属、数据对象与事务

### 4.1 四种状态来源

| 信息 | 唯一主记录 | 其他位置的身份 |
| --- | --- | --- |
| 项目、正式决定、实际提交、成绩、知识、引用、模型发布 | 业务PostgreSQL | UI卡片与搜索是投影，不接受模型直接改写 |
| 文件和不可变产物的字节 | 私有对象存储，摘要与引用在PG | 临时链接和本地缓存不是原件身份 |
| 操作、阶段尝试、到期计划与副作用收据 | 业务PG中的操作和执行记录 | Kafka保存投递日志和消费位点，不作为正式业务结果与无限期任务档案 |
| 工具调用、模型输入输出和实验 | 受控产物及其清单，关联业务对象 | tracing和MLflow便于诊断，不授权业务发布 |

领域事务提交成功可能早于Kafka消费位点提交。此时业务结果已经成立；重放按相同操作与步骤身份读取既有收据，不重复决定。UI分别显示“业务结果”和“任务执行状态”，不能因回执延迟重做决定。

### 4.2 目标领域对象

| 对象族 | 拟建记录 | 关键键与约束 |
| --- | --- | --- |
| 工程与投标 | engineering_projects、bid_rounds、bids | 工程／标段／轮次／主体分别标识；名称不可作唯一键；一条bid是PRD的项目工作单元 |
| 工作会话 | conversations、messages、message_parts | 项目会话固定bid；全局检索会话独立scope，业务操作固定目标bid；主会话部分唯一约束；内容与卡分类型 |
| 操作 | proposed_actions、commands、operations | action绑定对象版本与请求摘要；命令幂等键；operation稳定ID关联阶段与消息事件 |
| 文件 | blobs、documents、document_versions、document_assignments | sha256唯一内容；原件不覆盖；相同字节可有不同归属与用途 |
| 解析与依据 | parse_runs、pages、evidence_blocks、rule_sets、fact_sets | parser／配置版本、物理页与定位；规则与事实版本不可变 |
| 编制与生成 | outlines、sections、section_revisions、writing_plans、template_versions、document_builds | 章节稳定身份、草稿revision、不可变构建输入与模板；每种格式产物分别记录，转换缺口可定位 |
| 任务模板 | task_definitions、trigger_configs、task_runs | 模板版本、用途和来源固定；定时、事件及手动启动归一为operation；不赋予人工决定权限 |
| 评审 | review_runs、review_inputs、verdicts、findings、finding_decisions、predictions | 冻结输入摘要；问题和预测绑定轮次，不从当前聊天推断 |
| 提交与结果 | submissions、outcomes、verification_decisions | 实交稿、标准／补录身份、更正链；技术分／满分／口径；冲突整体阻断有效配对 |
| 知识 | knowledge_items、knowledge_versions、knowledge_sources | head revision串行更新；版本状态、适用性与有效期分开；来源不可丢 |
| 来源和引用 | lineage_edges、source_groups、citations | 来源方向与派生关系；禁止循环依赖；引用固定版本和用途 |
| 评分数据 | samples、admission_decisions、dataset_manifests、split_assignments | 一个提交一份有效标签身份；实验成员与分组冻结；补录不补造事前预测 |
| 模型 | experiments、model_artifacts、model_acceptances、model_routes | 具体产物摘要、独立验收、适用范围和路由修订；不用可变别名授权 |
| 可靠交付 | outbox、stream_heads、stream_events、audit_entries | 事务发件箱；同stream序号；审计追加 |

名称是设计提案，实际DDL与OpenAPI在实现前单独评审，不视为现有接口。基础实现可以合并纯关联表，但不能把上述不同身份混进一个不受约束的JSON字段。

### 4.3 不变式

1. 实际提交版本、评审输入、正式结果原记录、已发布知识版本和模型产物均不就地覆盖。
2. 每项有效结果可追到输入、方法、操作者和来源；内容摘要稳定序列化，算法版本也参与身份。
3. 项目阶段、归档、工作会话和任务状态分别保存；知识状态不等同于任务适用性。
4. 当前指针按输入revision更新，不按完成时间更新；旧轮次只追加。
5. 事务内同时写正式结果、审计、业务事件及需要派发的Outbox；跨存储不能假设一个大事务。
6. 相同命令键与相同内容返回已有结果；相同键不同内容为409冲突；不同对象不能借用确认卡。
7. 新冲突未解决时该提交不存在无争议有效技术标签，不能退回旧非冲突成绩继续统计。
8. 数据用途与来源限制同时作用于正文、知识、摘要、提示、检索结果和缓存。

## 5. 命令、确认与并发协议

### 5.1 操作提案

AI输出类型化意图：action_type、目标bid、对象ID、预期revision、参数及来源。服务端建立proposed_action，计算规范请求摘要，填写实际操作人、有效期和业务前提，生成可渲染卡片。模型不能生成“已执行”卡片作为正式状态。

确认请求携带action_id、If-Match及Idempotency-Key，参数不能在确认时偷偷改变。服务端校验登录、CSRF、操作范围、有效期、对象状态和版本。按稳定顺序锁定相关head行；相同键先占位，使并发请求串行；写业务结果、审计、事件、Outbox和幂等响应后一次提交。

跨模块采用统一锁顺序：幂等占位、按全局键排序的领域head、提案消费、按ID排序的stream head、发件箱。模型和远程调用均在短事务之外；返回写入前重查必要前提和数据库实际时刻。出现死锁或序列化失败时，只对同一幂等命令有限重试，不重放未经记录的外部操作。

按钮表单已明确对象与影响时，提交本身就是确认，不再追加第二次聊天确认。读取、搜索和草稿可以直接执行。自动评审按项目设置和已上传资料触发，不能被解释为授权全库训练或任意外部执行。

### 5.2 恢复后的授权

人工批准持久保存到PG，Outbox经Kafka投递稳定action_id与operation_id。Worker执行前重新读取批准、当前成员状态、对象revision、来源状态及用途规则。过期或对象已变时返回待重新确认，不照抄历史批准。消息只保存引用，不携带登录Cookie或模型密钥。

### 5.3 错误分类

未登录401；CSRF或禁止操作403；对象不存在404；幂等内容冲突／业务前提冲突409；revision不符412；结构或量尺不合法422；容量／调用限额429；暂时服务故障503。普通成员拥有全部项目访问范围，项目检查负责防止串对象和错误写入，不引入隐藏岗位分权。

幂等不能只靠“成员＋请求键”：两个成员用不同键点击同一提案，仍只能有一个有效消费。对action_id及其提案revision建立业务唯一约束，重复确认返回已有结果。需要保存失效卡或失败审计时，以领域返回值提交记录后再生成HTTP错误；不能抛异常回滚后误以为失效状态已保存。

| BatchImport | 新资料清单校验→异常列表→分组入库 | 新入库批次、原件和成绩出处；不做旧库映射 |
| ScoreExperiment | 准入→固定划分→特征→训练→独立测试 | dataset／split／protocol／artifact摘要 |
| ImpactReview | 停用／更正事件→依赖定位→复核提示 | 根来源与影响记录 |

用户项目与聊天不会占据一个无限执行流程。每项后台任务有operation_id；人工确认另起领域命令，固定阶段由普通Python处理，AI子图按实际需要有界调用。

### 6.2 投递、位点与恢复

业务事务同写operation和Outbox，API返回202。投递器以稳定event_id发布Kafka，收到成功回执再标记；重发允许重复，领域收据防重。消费者禁用自动位点提交和自动offset store，在PG结果提交或可靠持久接管重试后，才提交offset+1。

阶段以operation、step和input digest唯一，执行者持fence；提交产物、收据、下一阶段Outbox在同一事务完成。起步每个分区最多一个在途步骤，poll与计算分离；再均衡停止新派发，接管提升fence，未提交位点按收据重放。Kafka消息保留期、DLQ和重试预算不能替代业务事实。

详细topic、partition key、消费者配置、重试与死信协议统一见[详细设计第6节](融合详细设计.md#6-后台执行与恢复)。Kafka事务不覆盖PG、对象存储和模型调用；外部超时可能重复计费，预算与请求记录如实保存。

### 6.3 取消、计划和升级

取消请求与完成竞争同一操作锁，取消先提交后禁止正常完成发布，已完成决定不回滚。Kafka不能靠删除一条已消费记录完成取消。计划事实和触发去重记录保存于PG，独立唤醒器只发布到期Outbox；不在消费者内存长期等待。

handler_version与输入schema固定；升级保留在途旧处理器或明确终止后重启新操作。消息topic/schema、客户端和broker组合独立验证，故障未通过前不声称生产可恢复。

## 7. 会话、卡片与事件流

### 7.1 消息结构

消息由text、artifact_reference、tool_observation、business_card_reference等part组成。文本可流式显示，正式卡片从服务端对象查询生成，不能将模型任意JSON直接映射到可执行组件。Markdown清理与组件白名单共同防止伪造按钮或脚本执行。

键盘路径、焦点回退、状态文字和390px布局作为组件验收条件。证据侧栏在窄屏切为可返回详情，保留输入和滚动；业务动作提供按钮，用户无需靠输入命令完成上传、核验和复评。

会话保存讨论过程；项目记忆从当前有效事实、稿件、问题和决定组装。摘要只提供定位，不授予事实资格。切换bid或用途时清空相应运行上下文，附件和输入草稿按bid保留。正式评分另起干净任务，见第11节。

### 7.2 持久事件

新增GET /conversations/{id}/events，事件以conversation_id和单调seq为游标。同一stream先锁stream_heads行，再在同事务递增seq并写事件，避免“ID先分配、事务后提交”导致游标跳过。全局自增、UUID排序和created_at都不作为跨并发提交可靠续传依据。

持久化message.created、card.updated、operation.updated、message.completed等关键事件。token.delta可短暂缓存，最终文本必须入库；断线后未完成文本从消息快照恢复，不承诺重放每个临时token。Last-Event-ID绑定stream，错误游标拒绝或要求全量同步，不能用于跳过另一个会话。

事件保留期结束后返回明确的reset_required及当前快照版本。客户端按(seq,event_id)去重；SSE重连先校验当前登录及成员状态，长连接定期复核。PG查询／通知只负责唤醒，通知丢失由轮询补齐；不要求Redis保存事件。

## 8. 文档处理与证据契约

### 8.1 文件接收

上传先建立document_version和临时对象授权。完成后服务端核验实际大小、类型和SHA-256，再变为可引用原件；前端摘要不可信。对象键由服务端生成，原件防覆盖，分片失败支持恢复。未通过核验的文件隔离，不进入评审。

对象存储优先使用公司部署地域内的托管私有服务，AWS S3与阿里云OSS作为候选适配，不把OSS全部功能假设成S3等价。SDK、分片、CORS、短期签名、校验和、条件写及版本保护按实际供应商验证后锁定。没有云账号时本地模拟只验证业务协议。

### 8.2 解析器端口

统一输出page_count、物理页、印刷页标识、page dimensions／rotation、元素种类、原文、bbox坐标系、原始字符或元素定位、解析方法、质量状态与gaps。所有证据绑定原件摘要＋解析版本＋元素ID。

首批实现采用Docling结构化、PaddleOCR扫描页和PDFium渲染适配；MinerU保留真实基准对照候选。具体调用、页质量、分块与模型profile见[实施规约](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/RAG与评分实现规约.md)。这是可落地工程基线，真实资料未通过前不宣称解析效果已验收。按页路由OCR，避免对可靠文字层重复识别产生互相矛盾版本。

表格保存行列及合并关系，必要时同时保留图像；图页只保留图片不算内容已理解。旋转、裁剪与坐标变换在适配器统一，坐标无法验证时显示整页，不画猜测高亮。抽取后的相同文本不能替代内容相同的证明，原件身份始终保留。

### 8.3 规则与页级质量

规则保留条件、例外、分值和原页。满分合计不符、图表未读、补遗冲突或漏页先形成质量缺口，不靠监督校准掩盖。渲染／抽取交叉检查和人工标注共同检验页级正确性；解析器变更建立新parse_run和必要的新review_run。

## 9. 检索、知识与来源链

### 9.1 用途策略先于召回

检索请求包含purpose、bid／review_run、来源时间边界、允许内容类型、适用条件、排除分组和策略版本。这些由服务端任务身份构建，不接受模型任意扩大。普通建议、当前正文查证、历史档案、正式评分和实验锚点为独立用途。

允许集合由PG权威记录限定。召回前过滤，召回后复核；向量副本或缓存中的status不是最终依据。精确当前正文证据通道可以读取目标正文；实验参考通道必须排除目标及禁止组，两者不能用同一条含糊的“排除测试数据”规则。

### 9.2 词法、向量与重排

首批用中文分词后的PostgreSQL simple全文索引，技术术语、条款号、工期／单位和企业名保留精确通道；ts_rank／ts_rank_cd如实命名，不称BM25。分词器与词典固定版本。复杂词法需求与标注集证实当前通道不足时再比较OpenSearch。

语义通道首批采用BAAI/bge-m3的1024维dense profile，使用余弦与L2归一化；profile记录具体权重摘要、维度、距离、分词和预处理。不同profile不可混排向量距离。切模型建立新索引与覆盖进度，验证后原子切换；旧实验继续引用旧profile。

小过滤集合优先精确向量排序；使用HNSW时开启经验证的迭代扫描或采用合适局部索引，报告是否因扫描上限返回不足。实测“有合格内容却返回0条”的负对照说明不能把少结果当库内没有资料。召回候选不足时可以扩大允许范围内的扫描，不允许放宽用途隔离。

词法与向量采用RRF融合，起始候选规模和k为配置并由标注集调优；融合的是排名，不是直接相加不同量尺的分数。reranker按固定版本进行，候选文本仍受用途限制。语义检索为首批必需能力；融合与重排参数由真实标注调优，不以组件已部署视为质量已验收。

### 9.3 知识发布与来源闭包

条目head保存当前版本revision，版本保存候选／待确认／发布／停用／失效及适用性。发布新版本不覆盖旧版；候选无权进入正式自动引用。来源为外部企业时，不能作为本公司可用事实。

lineage_edges保存从原件到抽取、摘要、知识、特征及模型的派生关系；写入时校验无环。分组和时间限制沿完整来源闭包传播，不能仅检查条目直接group_id。实验参考源只要有被禁止组祖先就排除，除非协议明确允许的目标正文专用通道。

停用在同一事务更新head并记录影响事件。提交引用包时，按稳定顺序锁定所需head，重新检查状态、revision和数据库当前时刻；运行期间来源失效时结果可保存为受影响记录，不能更新为当前可信结果。停用完成后查询也按有效来源关系判断，不能只等缓存失效。

来源影响包括在办、已提交、归档项目及数据／模型；只创建复核和更正，不自动替换正文。对象存储的引用计数与数据库关系共同阻止误删；知识索引可以重建，来源记录不能被索引重建覆盖。

## 10. 评审、改稿与实际提交

review_run冻结bid、正文、招标补遗、规则、事实、解析、引用策略和方法。读取全部规则形成响应矩阵，判定与证据校验分别保存。检索top-k未找到内容不足以证明全文缺失；缺失型判断应记录检查范围，必要时扩大章节检查，否则为无法判断。

否决、强制、评分和普通建议分别处理。规则核对完整、评分覆盖、解析质量和人工确认分开；任务成功不合并它们。修改建议有草稿身份和工程前提，采纳不改变问题已解决状态。新稿建立新review_run，匹配旧问题并标明已解决、仍存在、新增或未复检。

跨轮比较首先比对规则、量尺和方法摘要。方法不同可以看原始结果，不能把分差直接称作改稿收益；需要时在同一冻结方法下另跑两稿。

标准登记提交在一个事务重新校验最新输入、核对完整、规则确认／按原文接受、关键阻断问题及正文一致。仅普通建议不阻断；评分总分资格与否决闸门分开。实际平台提交由人完成。

历史／线下事实补录独立类型，保留稿件、时间和出处，明确未经过系统完整检查。它可以成为档案和经过核验的训练资料，不能补造当时预测。提交和成绩更正追加新记录，截止后新稿不自动成为实交稿。

### 10.1 辅助功能与报告

前后矛盾和范围残留通过明确的检测器端口产生候选，记录实际运行范围。七个项目开关、默认值和不可关闭核心以PRD第7.4节为主记录；设置变化只影响新任务，不重写旧结果。

报价使用十进制纯函数计算，输入为经核实的计分公式和明确假设，保存方案由人确认；不引入内部成本利润。分数与报价换算带条件。投标正文、评审报告和批注审阅稿使用不同artifact_kind，标准提交验证所选正文身份，已发生错误文件提交走事实补录。正文构建不自动夹带系统风险、来源徽标或审查批注，原有有意正文引用不被笼统移除。报告从固定review_run及引用组装，Word可用python-docx，原PDF批注可用PDFium适配器；中文排版、坐标及生成失败须单独验收。

报告展示副本按review_run、presentation_revision和source_impact_revision定位并独立存储，设置或影响状态变化会使旧缓存不再满足当前下载；保留原产物而不原地改写，不声称能撤回用户已有离线文件。

业务对照以有效提交和核验结果为分母；候选人不当最终中标，未知不填未中标，零分母不显示效果百分比。导出和在线页面使用同一投影规则，保留历史轮次、覆盖、模型资格及来源后续失效提示。

### 10.2 章节编辑、模板与不可变生成

快速PDF评审与章节编制共用bid、review_run、finding、citation和operation身份。展开章节工作区只改变浏览位置，不复制项目、问题或样本；结果页和就地助手发出的同一操作统一幂等受理。自动运行的语义去重身份包括bid、目标正文、资料角色与修订、规则／事实、解析配置、方法和任务用途；不能只以blob摘要去重。现成稿评审接口不得依赖目录、编辑器、模板构建或任务模板已配置，新增编制服务可以分阶段启用。可选模块在页面、助手、报告与导出使用同一项目设置投影。

前端采用GovDash式项目页面、章节详情和随页助手，布局主记录为[交互与视觉设计](两版交互与UI风格对照.md)。编辑器保存结构化章节草稿及修订，服务端校验base_revision；自动保存失败保留未提交内容，发现并发冲突不得最后写入覆盖。AI修改提案绑定章节、基准修订、规则与事实身份和来源用途；应用时重查来源head及有效性，失效候选不新增有效引用。提案包含插入／替换／移动／删除范围；确认后事务保存新修订与来源，撤销也是新修订。上传PDF不就地改写。

默认构建衔接按自动开始设置选择，显式人工生成后评审请求独立表达任务意图；自动开始开关不禁止人工评审，同输入在途运行仍归一。构建请求必须携带已确认保存的draft_revision；有待保存内容时先保存取得revision，失败不回退上一版。服务端快照、当前评审、生成产物与实交指针分别保存，提交前按资料revision重新核对。

目录模板和版式模板分别版本化。构建操作冻结章节快照、引用、模板、字体／渲染配置与资料身份，产出不可变DOCX及PDF；两种格式分别记录状态、摘要和缺口。字体、图表、编号、目录、页数和暗标限制需要真实文档验证，不以编辑器估算替代实际版面。继续编辑不改变已启动构建；构建完成后旧任务不能覆盖更新的当前指针。

正式review_run绑定实际生成或外部上传的PDF及解析身份。构建来源绑定源DOCX／草稿摘要、渲染器与配置、输出PDF身份，外部同名双格式不自动建立已核验对应关系。DOCX外部编辑后须重新上传并渲染／取得对应PDF，旧PDF结果不继承。章节变更、模板更新和补遗影响通过依赖关系标记产物过期，不能凭章节关联就认定满足规则。补遗影响未完整定位时保留未判定范围，局部重跑不自动放行整份提交。

### 10.3 任务模板、来源与触发

预置和自定义任务统一固定任务模板修订、bid、资料／章节、用途与可执行动作。事件去重键包含模板版本、目标对象与输入revision；定时计划保存时区和下次时刻，触发即创建可追踪operation，复用选定执行器的调度能力，不另外建设隐蔽调度主记录。暂停仅阻止新触发，运行取消另记结果；错过计划不无界补发。

来源选择器和@引用只选择有身份的对象，服务端按用途重核；正式评分不接受任意来源覆盖白名单。模板说明不授予额外工具权限，输出是检查产物、草稿或待人工确认提案。运行记录回写具体领域对象，站内通知去重。以上对象和接口仍为技术提案，需同步正式契约、实现及故障验收。

### 10.4 终态与迟到回调

操作、任务尝试和业务决定分别保存。取消请求与完成提交在服务端按同一操作身份决定最终结果；已完成返回已有产物，已取消运行的迟到回调不得更新当前有效指针。执行器按有效尝试身份与revision核验提交，不只检查浏览器是否仍打开；已提交领域决定不因取消回滚。登录恢复只恢复查看，旧保存和确认重新校验对象，不自动重放。

## 11. 正式评分的上下文边界

### 11.1 输入构建器

ScoreInputBuilder只从冻结对象构造输入：当时生效要求、实际目标正文、允许的事前事实和受控方法数据。输入清单列所有源版本、用途、已知时间、派生来源和摘要；形成score_input_hash。不接收聊天历史、会话摘要、结果公示或任意工具文本直接拼接。

即使用户在同一会话已经看到正式成绩，正式评分仍由干净任务重新构建；能够证明未见目标标签的叫事前预测，否则为回测。对已公开的历史测试项目，基础模型可能在预训练中见过资料，无法仅靠本系统白名单排除该风险；优先采用此前未公开的公司资料和时间前瞻试点，并披露限制。

### 11.2 参考与锚点

普通内容建议默认只取允许的参考正文和知识，不把案例成绩拼入。受控锚点是监督输入，必须有独立来源库或按训练折重建，不从全库拿若干相似成绩即可使用。目标、同项目、同模板／近重复连通组、未来已知成绩及测试派生知识均按协议隔离。

缓存键包含输入摘要、数据用途、策略、分组／时间边界、解析、提示、模型、embedding／重排profile和锚点清单摘要。即使底层文件相同，跨用途和跨实验不得重用带标签结果。

### 11.3 输出资格

评分条款先形成有出处的结构化判断与缺口，部分分值覆盖只显示部分估计。总分需要评分结构、必要证据、适用且验收通过模型等资格；区间还需独立覆盖与宽度验证。原始逐项合计、正式模型预测和官方成绩使用不同数据类型。

关闭显示预测分数时，统一输出投影对聊天、卡片、复制、图表和新导出隐藏预测数值与区间及其派生比较，不隐藏正式结果登记字段；后台可保留预测用于合格回流。模型输出与软件错误不填0分。技术分、综合分、未知及真实零分分别校验。

## 12. 评分数据、训练与业务发布

评分方法唯一维护在[四层评分路线](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/评分预测训练与验收方案.md)：评分细则结构化与章节准备→逐项完整章节判断并重复3次→正式成绩监督的统计打分→受控比较锚定。运行层分别实现RubricPreparation、ChapterPackageBuilder、ItemJudgment、FeatureBuilder和ScoreTrainer，不由一般聊天RAG的top-k片段替代评分输入。

ChapterPackage至少记录评分项、章节ID、完整源范围、实际输入子节／图页、未读取范围、解析与模型方法摘要。超过上下文时层级处理并记录覆盖，不静默截断；摘要不能独自证明完整阅读。三次判断的档位、覆盖、针对性、具体性、引文和分歧进入统计特征，最终区间由独立成绩验证。

### 12.1 数据配对

sample以唯一有效实际提交为单位，绑定正文、当时生效要求、正式技术分／满分、聚合口径、来源、核验和时间。缺成绩档案仍可归档；待核验台账、综合分或未给分的否决记录不进入正式主验收标签。

登记提交时固定预测ID：同冻结输入、实际提交前最新成功且可证明未见标签的一条。正式结果到来后不能重选最接近的一条；重跑作为回测。在线误差按方法／模型和适用范围计算，样本数只决定统计展示资格，不授权模型业务发布。

### 12.2 科学实验流程

1. 确认来源与准入，构造项目／模板／重复正文的连通组，保存成员和取得时间。
2. 保留较新独立项目作最终测试；跨边界连通组按协议剔除或整体划分，不能拆开。
3. 训练／开发内比较基线与候选，所有填补、标准化、特征选择、检索邻居和超参数只用训练来源。
4. 需要预测区间时单独保留合格校准组；分组依赖与时间漂移下先检验适用假设，不默认宣称分布无关覆盖。
5. 冻结方法、参数、适用范围和业务验收协议；最终测试只做最终判断，后续调优换新的独立证据。
6. 报告全部应评、成功、失败、拒绝估分、无标签和来源子集，按项目等权及原量尺分层；不靠筛去难例取得低误差。

首批数据少，优先成熟的sklearn Pipeline和简单监督模型，比较均值／中位数／评分办法分组基线、原始判断、线性、岭回归和保序。更复杂模型或微调只有在独立数据和部署预算上胜出才采用。

### 12.3 区间与发布

同场排名与技术入围概率按训练方案第1.1节单独定义数据和验收；同场正文不足不能声称完整名次，事后入围线不能作为事前已知特征。概率需要独立校准和Brier等检验，不从点分或80%区间直接换算，也不等同于中标概率。

MAE、P90、偏差、接近比例、基线增益、稳定性、预测覆盖和区间宽度分别验收。精度数值沿用[训练与验收方案](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/评分预测训练与验收方案.md)的建议作为开发参考，最终业务认可的门槛在最终测试前冻结，不在此假定已经同意。

合格校准组少到无法取得指定覆盖的有限分位数时，不硬裁到最大残差；可以拒绝区间或展示业务允许的完整范围并说明无判别价值。区间限制在0到满分内也不等于具备有用精度。

模型包包含不可变模型文件、特征定义、训练／划分／方法摘要、适用评分办法、地区／工程、验证报告及依赖。研究侧可用MLflow记录，业务只使用固定摘要和PG中的model_acceptance。禁止加载未经信任的任意pickle；优先可审阅参数格式，非线性模型采用受控序列化并校验摘要。

发布从候选、验证、观察到业务使用，路由用revision事务切换，记录替代与回退对象。评分办法／范围不匹配回退到明确未验收的逐项判断或拒绝总分。错误成绩或输入更正会定位受影响数据和模型，暂停新增使用并重评，保留旧预测和更正链。

## 14. 模型适配、安全、数据出口与观测

### 14.1 类型化端口与能力配置

领域代码调用模型端口，不依赖供应商SDK对象。适配器负责协议转换、能力核验、调用调度与结果归一化，评分输入构建器和领域服务仍负责来源隔离、证据与业务资格。统一端口不意味着供应商能力相同，也不把模型接口兼容误认为质量等价。

| 端口 | 输入与输出 | 能力检查 |
| --- | --- | --- |
| Generate | 类型化消息、允许工具和流式选项，输出文本或工具意图 | 上下文、输出上限、工具协议、流式结束和用量 |
| JudgeStructured | 冻结证据包、输出schema与采样配置，输出候选结构化判断 | 原生schema／JSON约束、视觉输入、结束原因；本地再做结构和证据校验 |
| Embed | 文本批次与embedding_profile，输出同维向量与逐项状态 | 维度、批次上限、截断策略、归一化与模型版本 |
| Rerank | 查询、候选ID和rerank_profile，输出候选分数与顺序 | 最大长度、批次限制、分数语义及候选身份完整性 |

model_profile固定供应商、端点配置引用、模型身份／可用版本、适配器与协议版本、能力记录、上下文及输出预算、视觉和结构化模式、采样参数、超时、重试及费用策略；密钥只用服务端引用。能力表区分官方声明与实际探测，未验证能力不能按“兼容OpenAI”自动开启。

JSON输出仍需本地schema校验，且结构正确不等于引文真实或判断正确。无原生schema的模型可通过明确的提示解析路线作为候选；该路线单独记录与评测，不能静默替换已验收的结构化方法。未知上下文或视觉限制先拒绝不兼容任务，不猜测可读完整输入。

### 14.2 调用与结果契约

| 对象 | 必需内容 | 处理规则 |
| --- | --- | --- |
| LogicalCall | operation／review、purpose、score_input_hash或一般输入摘要、profile、schema与提示摘要、评分项及重复序号、截止时间与预算 | 一次逻辑判断可有多次尝试；重试不算新增有效重复 |
| Attempt | call_id、attempt_id、供应商request_id（如有）、开始／结束、状态、重试原因、实际响应模型标识 | 供应商不支持幂等时不承诺外部只执行一次；成功产物复用前验证摘要与用途 |
| Result | 状态、类型化内容／产物引用、finish_reason、结构及证据校验状态、使用的profile与实际模型身份 | 截断、缺字段、拒答、引用不匹配分别保留，不输出伪成功或默认0分 |
| Usage | 输入／输出／缓存及其他供应商明确提供的计量、费用币种、价目版本、估算或结算身份 | 未返回的用量和未结算费用为未知，不能填0；估算与供应商结算分别记录 |

JudgeStructured的输出交给ItemJudgment验证：要点ID来自当前评分结构，档位属于对应规则，引文可定位至输入章节包；无效结果按失败或待复核处理。内容质量和缺失判断仍需真实基准验证，字符串存在不能证明工程判断正确。

正式评分的方法包绑定LLM profile、提示、schema、章节处理、特征、统计模型及校准配置，输入与发布包均记录该身份。三次有效判断使用同一冻结方法，供应商超时后的重试保留同一重复序号。供应商仅提供可变模型别名时记录实际返回身份与调用时间，不能宣称底层权重已冻结；检测到变化须重验证，无法稳定识别时披露可重复性限制并限制发布资格。

### 14.3 重试、路由、流式与故障

按供应商和用途控制并发、速率、总token及费用预算。429、可恢复5xx和网络故障按分类有限重试，遵守可用的Retry-After，并受逻辑调用截止时间与预算约束；认证、参数、能力不符不盲目重试。预算计入可能已执行但未回执的尝试，未知费用保守预留，防止每层重试叠加放大费用。

Kafka消费协议与PG阶段收据管理任务级恢复，适配器管理明确上限的调用尝试；任务记录两者的累计尝试和预算。取消传递给支持的供应商，但不能保证对方停止或停止计费；已返回而不再适用的产物不得写成当前结果。

正式评分故障返回等待重试、失败或拒绝估分，不静默更换供应商、模型、提示、采样、章节范围或视觉通道。需要备用方法时，必须已有对应方法包及适用验收，按明确路由生成独立方法身份；跨方法分差不能解释成改稿收益。一般对话可使用允许的备用路线，但记录并显示实际方法；不能把这种宽松策略继承到正式评分。

流式delta只用于临时展示，成功结束后保存完整结果；finish_reason为截断或schema无效时不能发布正式判断卡。工具调用只是候选意图，经封闭注册表、参数、对象与用途校验后交给领域命令；供应商返回的工具名称或前端流式消息不授权执行。重连与持久事件仍遵循第7节。

Embedding／重排方法变更遵循第9节的profile和索引切换，不与旧距离直接混排。评分供应商选择、提示及回退方法只在开发数据中比较；不能看最终测试成绩后切换供应商并复用原验收结论。

未验证：真实模型API、视觉和schema能力、取消、限流、流式异常、版本漂移与结算。验证方法为先执行可控故障的端口契约测试，再用实际供应商沙箱和获准真实材料验证；模拟响应或SDK安装成功均不作为真实兼容或质量证据。

### 14.4 身份、数据出口与观测

内部统一登录，一期不增加岗位分权。账号口令使用成熟哈希算法，服务端可撤销会话、httpOnly／Secure Cookie、CSRF与登录限流；所有对象在服务端验证归属和状态。关闭工作会话不撤销登录，停用成员则影响新操作与长连接。

工具使用封闭注册表和类型化输入输出。模型不能执行任意SQL、shell、文件路径或外部URL；引用文本里的指令没有执行权限。对象授权、数据用途和实验隔离是程序校验，提示词只作辅助。上传内容、检索结果和模型输出均视为不可信数据。

模型出口按供应商、数据用途和业务认可范围配置。密钥只在服务端管理，不进入会话、工作流输入、日志或模型产物。默认不把原件全文、成绩和提示记录发到外部tracing。需要云模型时先核验资料范围与供应商处理约定；本次实验全部无外部模型调用。

日志按request／bid／operation／workflow／review／model摘要关联。审计是领域决定记录，tracing是诊断，两者分别保留。观测记录延迟、错误和资源以定位故障，不增加聊天量等业务绩效指标。OpenTelemetry和MLflow等工具不可替代业务审计与发布授权。

## 15. 部署、成本与恢复

### 15.1 起步部署

推荐一个代码库、若干部署进程：web静态资源、API、文档／评审／实验Worker、Outbox投递与对账；PG业务与pgvector检索库、Kafka集群、私有对象存储为基础依赖。实验追踪可独立部署。初期不要求Kubernetes，生产可选托管数据库和Kafka以减少运维。

Python3.12和Node22作为候选运行基线。PostgreSQL17.11、pgvector0.8.7以及Temporal SDK1.34.0已用于本次机制验证；Temporal CLI1.9.1仅开发实验，不是生产镜像。正式依赖锁定发布版本、镜像digest、模型权重与配置摘要；不部署调研时的任意main分支。

生产Kafka拓扑、客户端、TLS／SASL、ACL、再均衡和消费位点需要另外验证；此前Temporal开发机制实验不作为Kafka生产证据。React／组件／Vite候选包需完成适配、构建和浏览器验收后锁定，不只根据npm peer范围宣布可用。

### 15.2 容量与费用

以PRD的300个历史案例、1000条知识、5名在线成员和2个并行评审为初始测量负载，记录实际页数、图表、chunk、向量维度和并发。容量根据元素量和模型调用量测量，不用案例数量推断必然够用。

调用预算至少估算规则数×判断次数、正文长度、解析／OCR页数、embedding token、重排对数和重跑比例。上传导入不自动触发全库付费预测；批量任务先给范围与费用估算，再按明确请求执行。外部超时可能重复计费另列预算。

初始Agent工具循环和检索轮次设置上限，限制从配置读取并保存于运行清单；超过限制返回可继续的阶段结果，不无限反思。同步反馈和列表延迟按PRD测量；本次小机制实验不是容量或全栈时延测试。

### 15.3 备份与灾难恢复

业务PG保存事实、操作、收据、Outbox和发布路由；原件／模型字节在对象存储。二者关联一致地备份；Kafka日志副本和保留保障投递恢复，但不是永久档案。向量索引可重建，embedding模型与profile身份必须保留。

恢复时先暂停派发与消费者，恢复对象与业务数据库并核验引用，再核对Kafka消费位置与未完成收据、提升旧fence、补发缺失Outbox、重建索引，验证后恢复流量。PG恢复点与Kafka位点可能不一致，必须按幂等收据对账，不盲目跳过或重做正式决定。

RPO／RTO由正式部署演练冻结。本次未执行服务端灾备、云存储恢复或Kafka再均衡与消费恢复，均为正式运行门槛。开发和试点也从第一批真实材料起启用备份，不能等规模化后补做。

## 16. 代码组织与实现顺序

建议全新代码空间，不在旧表或旧路由上假装新生命周期已经存在：

~~~text
apps/web/                    项目工作区、历史、知识、证据与卡片
apps/api/                    认证、OpenAPI、命令与查询
packages/domain/             业务实体、决定、版本、事务与来源策略
packages/contracts/          API、事件、工具与产物的版本化契约
workers/consumers/           Kafka消费、位点与阶段调度
workers/activities/          文档、模型、检索、评审、导出及幂等提交
research/                    准入、划分、训练、独立评测与发布包
deploy/                      隔离环境、配置、备份、恢复与升级
~~~

| 阶段 | 实施内容 | 退出条件 |
| --- | --- | --- |
| T0契约与骨架 | 身份、版本、操作、证据、事件、领域事务与模型端口；候选执行器验证环境 | 并发重复、提交乱序、授权恢复与基础备份能重复验证 |
| T1当前项目闭环 | 真实上传、解析端口、评审、卡片、证据、改稿复评、提交及补录 | 真实资料＋实际用户完成流程；新旧版本不串用；核心闸门存在 |
| T2评分数据优先 | 首批案例、异常队列、实际稿与官方成绩核验、干净评分输入 | 来源和配对可追溯，重复不增加独立样本，历史回测身份明确 |
| T3模型有效性 | 基线、分组时间划分、校准、固定独立测试、观察与发布 | 满足已冻结真实协议才发布，不达标保持未验收 |
| T4知识可靠复用 | 少量高价值条目、发布、适用检索、来源闭包和失效影响 | 无出处不产生公司事实；撤回与派生知识隔离有真实场景证据 |
| T5稳定运行 | 全量容量、云直传、升级回放、备份恢复、回退和迁出 | 正式拓扑与真实负载通过，不用机制PoC代替 |

表中阶段表示业务集成与正式交付依赖，不要求等T1全部完成才做评分实验。T0具备身份、证据、用途隔离与模型端口后，可并行建立受控实验入口，先做T2首批10—20份资料核验和第12节的完整章节／三次判断链，再进入T3开发基线与消融。该入口只产出研究产物，不获得正式提交或模型业务发布资格。

T2、T3与T1最小项目工作区协同推进：评分侧先给真实资料质量、判断、成本及误差证据，业务侧接入原文卡片、复评、实交稿与正式结果。正式业务使用仍要求T1核心闸门和对应模型验收成立。知识基础身份可以并行，但不能先建全量知识平台阻塞真实成绩配对；没有指定未经估算的周数和人天。

## 17. 全新初始化与资料入库边界

系统从空库、空存储和空检索索引独立建设；没有旧系统数据迁移、旧接口兼容、旧状态映射或双系统切换要求，也不要求复用旧代码。初始化建立schema、受限账号、默认配置与方法身份。

历史招标、实际提交正文、官方技术分和出处按新系统规则作为新资料入库；dry-run只检查这批文件、标签和关联，不连接旧业务数据库或承接旧模型验收。资料缺失或待核验如实保留，训练准入另行检查。

档案导出、备份恢复和未来结构升级属于运行能力；不引入旧库映射、legacy_reference或旧系统切换工程。原件、样本、方法与模型从第一批新资料起可追溯。

## 18. 验证、反对意见与发布门槛

### 18.1 已执行的机制实验

从零编写的隔离程序分别验证Temporal真实开发服务、LangGraph持久中断、PostgreSQL17事务／并发／事件／来源过滤、pgvector ANN过滤和sklearn分组评测。程序与输入版本、结果和限制见[验证与自审](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/04-验证与测试/全新技术方案验证与自审.md)。没有从旧应用导入实现以证明新方案。

### 18.2 主动反对推荐方案

| 反对意见 | 当前处理与可推翻条件 |
| --- | --- |
| Kafka集群增加运维成本 | Kafka是用户确定的消息基础设施；可选托管集群，明确控制器、副本、监控、保留与故障成本，开发单节点不冒充生产HA |
| PG同时事务与向量会互相影响 | 首批精确检索与限额；语义索引按收益启用；压测超出预算才迁检索服务，不提前假定PG足够 |
| PG与Kafka仍有双写风险 | Outbox＋固定event_id＋幂等领域收据＋提交后offset＋对账；不称分布式恰好一次 |
| 知识来源闭包会复杂且昂贵 | 先保证原始边和正确性，按规模物化闭包；本次仅验证小图过滤，百万级关系性能仍需测 |
| 解析器还未选出优胜者 | 建立统一证据契约和真实基准，保留候选；默认解析未通过前不宣称全量表格图页可读 |
| 300份样本可能仍不够准确 | 报独立组数、标签分布、学习曲线、评委不确定性；方法不达标就不发布，补数据或收窄范围 |
| AI基础模型可能见过公开历史成绩 | 严格输入隔离仍不足以证明预训练无污染，补私人资料和前瞻试点，披露残余限制 |
| 自定义卡片与组件适配可能拖慢交付 | 先用真实API完成一条上传至复评路径，组件可替换，领域协议不绑定组件库 |

### 18.3 必须关闭的门槛

实施前冻结API／DDL、来源和工具契约；解析默认方案须有真实资料评测；模型业务发布须有经认可协议和独立官方成绩证据；正式运行须完成供应商连通、生产Kafka与消费协议、RAG检索质量、容量、升级、备份与恢复。可以分阶段开发与有限试点，任何未完成门槛都要明确限制对应能力。
