# 另一路实现的评估与取舍

文档编号：GOV-004  
类型：方案比较与吸纳清单

用户曾让 Codex 与 Claude 分别推进本项目，并要求比较两者、定夺最终形态。本文记录比较依据、结论和吸纳清单。Codex 的全部成果保存在五个仓库的 `handoff/2026-10-17` 分支，入口为 `tender-app` 该分支的 `workbench/docs/handoff-20261017/START_HERE.md`；本文引用的 Codex 文档均指该分支上的文件。

## 1. 两者对照

| 维度 | `main`（基线） | `handoff/2026-10-17`（Codex） |
| --- | --- | --- |
| 产品范围 | 上传即评审；两个 P0（废标／否决风险、技术评分预测）及问题、依据、报价、提交与结果闭环 | 在此基础上扩展为 GovDash 式工作台：章节编制与 Word 生成、AI 助手与交互卡、任务模板与定时运行、历史项目库、企业知识库、模型治理、应用恢复 |
| 实现位置 | `tender-app/backend`、`frontend`、`deploy`、`contracts` | `tender-app/workbench/`（另起的一套系统），并对 `main` 前端改了 3 个页面 |
| 源码规模（`.py/.ts/.tsx`） | 后端约 1.2 万行、前端约 1.8 万行、后端测试约 0.4 万行 | 后端与包约 6.1 万行、前端约 3.8 万行、测试约 3.8 万行；另有约 3 万个验证证据与冻结快照文件，`tender-docs` 增加约 900 万行 |
| 技术栈 | FastAPI、PostgreSQL 16、Kafka、OSS、Milvus（未接入，检索只有关键词）、MLflow；整套 Dockerfile 与加固 compose | FastAPI、PostgreSQL 17＋pgvector、Kafka、SeaweedFS（开发）；compose 只含基础设施，应用进程手工逐个启动 |
| 完成度 | 前后端、迁移、契约、部署手册齐备，能作为整体部署 | 其交接自述“不是最终交付”；统一运行环境未建立，各模块分别冻结候选，存在未执行的初始化 SQL、被判“不可执行”的数据库角色越权问题、成稿误判完整的反例 |
| 验证 | 前端 292 项本机通过；后端与研究在 Linux 环境的既有记录全部通过，Windows 本机结果见验证报告 2.8 节 | 各模块有独立机制测试与大量留证；未在本机运行 |

## 2. 结论

以 `main` 为最终形态的基线，`workbench/` 不整体合入，`handoff/2026-10-17` 分支保留为存档。

理由：本系统是公司内部长期维护的工具，最终价值取决于真实标书读得准、风险查得全、技术分预测得准。`main` 已形成可部署的完整闭环，规模适合少量人员维护；Codex 一版的单个模块质量不差（如检索的分块与引用），但流程负担与范围扩张使其没有收敛为可运行的整体。两版对评分采用同一条四层路线（用户提供），`main` 已经实现。
