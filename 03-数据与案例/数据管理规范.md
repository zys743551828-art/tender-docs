# 案例与数据规范

文档编号：DATA-002  
类型：案例入库、标注配对与数据规则

## 1. 数据现状与需要补充的数据

系统的流程、规则核对和报价计算已能在合成资料上跑通；决定它在真实投标里是否有用的，是真实数据的数量与质量。数据是当前最主要的瓶颈：废标／否决检测能否抓住真实的违反项、评分预测与官方技术分差多少，只有拿真实资料逐项比对才能回答，这些评价依赖服务器与数据到位，尚未进行。

需要补充三类数据，三类彼此配对才有用。

| 数据类别 | 内容 | 用途 | 入库要求 |
| --- | --- | --- | --- |
| 历史标书正文 | 企业实际提交的技术标正文（PDF，需有文字层） | 作为评审输入跑废标／否决检测、一致性与范围残留检测、评分预测；与官方成绩配对后用于校准 | 必须是实际提交的那一版；同一项目的修改稿各自登记，不互相替代；扫描件无文字层时系统无法解析，需要提供可复制文字的版本 |
| 招标文件与补遗 | 招标文件正文、答疑澄清、补遗、评分办法 | 提取废标／否决、强制性要求和评分条款；是所有判定的依据 | 招标文件与全部补遗成套收集，缺任何一份补遗都会让规则不完整；补遗的取得时间与文内日期分别记录 |
| 官方评分表与结果 | 评标委员会的技术标得分表、各评委分项、否决名单、入围与中标公示 | 作为技术分的真值，以及废标／否决的事实标注 | 必须是官方原件并记录页码；只披露入围者成绩的公示存在选择偏差，不能用来推断全体投标人的分布 |

图纸与工程量清单按需上传，作为资料保存；系统目前不解析图纸，也不从图纸中提取事实。

没有对应正文的公开成绩不能形成“内容—得分”配对；没有对应招标文件的正文无法验证规则判定。因此收集时以“同一次投标的三类资料成套”为单位，而不是分别堆积。

## 2. 标注与配对方式

### 2.1 配对单位

一个样本对应某项目／标段下某企业的一次实际提交，包含：

- 招标文件与补遗的全部版本（招标方发布顺序）；
- 提交的技术标正文（一个确定版本）；
- 官方技术分及满分、分值来源页；
- 官方否决、不入围或中标结果。

同项目不同企业各自编号；同企业在同项目的修改稿，只有实际提交的那一版与官方成绩配对。系统里的对应关系是：正文版本与招标资料经评审的输入（snapshot，界面写作“本轮评审的输入”）冻结，登记提交时锁定该输入，登记开标结果时关联该次提交；预测与成绩的配对通过“提交所用的输入”建立，不靠人工对表。

### 2.2 废标／否决检测的标注

评价检测能力需要事先由熟悉评标办法的人员，针对每份招标文件的废标／否决项和强制性要求，对照实际提交的正文给出参考判定：

| 参考判定 | 含义 | 依据要求 |
| --- | --- | --- |
| 满足 | 正文有明确响应 | 记录正文页码与原文 |
| 违反 | 正文与条款冲突，或缺少必须的内容 | 记录条款原文、正文页码或缺失说明；若有官方否决记录，另记录官方否决理由与页码 |
| 无法判断 | 正文没有涉及，或需要外部材料（证书、业绩合同等）才能判断 | 注明缺的材料 |

参考判定与系统响应矩阵的四类判定（满足、违反、无法判断、检查失败）对照时，“无法判断”不计为“满足”。违反样本天然稀少：有 k 个违反样本时，召回只能分辨到约 1/k 的粒度，样本越少估计越不可信，所以优先收集带有官方否决记录的投标文件，以及评审人员已知存在违反项的稿件。

一致性（同一个量在正文不同位置取值不同、大段重复）和范围残留（正文出现招标文件及补遗没有的工程对象）的参考标注由同一批人员对正文通读后给出：列出每处矛盾的位置与取值、每个应当报出的残留对象及页码，同时记录“明确不应报出”的对象（例如招标文件里确有的泵站），用来度量误报。用系统结果与参考标注比对时，先看该轮核对产物的 `checks` 字段：项目关闭了对应检测的轮次没有运行这项检测，不能计为漏报。

### 2.3 评分预测的训练样本与在线对照

**训练样本**。打分模型用历史投标训练：一份样本是某项目／标段下某企业的一次实际提交，包含招标文件与全部补遗、实际提交的技术标正文、官方技术总分与满分。样本按[入库模板](https://github.com/zys743551828-art/tender-datasets/blob/main/入库模板/README.md)批量登记（一行一份样本），由 tender-research 的 `intake` 校验、归档并生成评分配对集。除技术总分外，下列信息让同样数量的样本价值更高，收集时尽量一并取得：

| 信息 | 用途 | 登记位置 |
| --- | --- | --- |
| 逐项得分（每个评分项的得分，有各评委分更好） | 标签数量约增加十倍，可以检验逐项判断是否准确，数据足够后可训练逐项打分的小模型 | 分项得分表 |
| 同场全部投标人的技术分（公示或评分汇总表，不需要他人标书） | 扣除评委宽严造成的项目整体偏高偏低，评价在场内的相对位置 | 登记表“同场技术分” |
| 入围分数线与入围结果 | 评价“能否入围”的概率是否可信 | 登记表“入围分数线”“结果” |
| 同一项目多家企业的正文 | 评价同场排名 | 每家各登记一行 |

连续收集普通、未入围、被否决与高分稿件，不只挑高分；正文须有文字层。成绩来源分为官方原件、公司台账与口头报送三类，评测协议的 `label_sources` 写明本次准入哪几类，报告同时给出全部准入标签与已核验官方原件子集的结果。同一项目的多份样本、近重复正文与同源模板在评测中归为同一组，不跨训练与测试。

**在线对照**。产品上线后，预测与成绩配对的条件由系统固定：每个有效提交（未被后来的提交取代）只配一组；提交所用的输入上存在候选预测（取最新一条）；该提交存在目标为“技术分”、有分值且满分大于零、核验状态不是冲突、且未被更正记录指向的成绩（有多条时取最新一条，例如先登记入围、后登记中标时只算一组）。系统只排除“冲突”状态，不区分未核验与已核验，也不区分用户报送与官方来源，所以未经核验的成绩会被计入校准；入库时应先完成官方核验再登记结果。配对后按满分折算为百分制比较。产品里的配对用 `bidwb-admin export-score-pairs` 导出为评分配对集与系统预测，与历史样本合并后重新训练。

项目级功能开关对配对的影响：关闭“显示预测分数”的项目，预测照常生成，只是界面与导出不展示分数，照样形成配对；关闭“提示登记开标结果”的项目，系统在提交后不提示登记结果，结果需要按本规范主动登记，否则这个项目不会形成配对。校准样本稀缺，入库负责人应定期核对已提交但没有结果的项目。

| 配对组数 | 在线对照状态 | 系统输出 |
| --- | --- | --- |
| 0 | 未校准（`uncalibrated`） | 不给误差 |
| 1 至 19 | 样本不足（`insufficient`） | 只显示已有组数与所需组数，不给误差 |
| 20 及以上 | 已校准（`calibrated`） | 平均绝对误差（`mae`）与平均偏差（`bias`） |

20 组是在线对照开始给出误差数字的最低门槛，不是精度结论（打分模型的精度结论来自研究侧按冻结协议的评测）：平均绝对误差的标准误差大致随组数的平方根缩小，20 组时的数字仍有较宽的不确定范围，不能据此把预测当作对结果的承诺。组数越多越好；评价预测在不同工程类型、不同评分办法之间是否稳定，需要每一类各自有足够的配对，不能用跨类混合的平均误差代替。

只有综合总分、不能拆出技术分的成绩不能参与配对（登记时目标须选“技术分”）。官方成绩未披露的项（公示写“/”）保留未知，不记为零。

### 2.4 编号、目录和命名

一个案例对应某项目／标段、某企业的一次提交及结果，编号 CASE-001 起按入库顺序递增，不按得分重排、不复用。同项目不同企业或独立提交分别编号，用招标编号、标段及日期关联。

统一目录：`tender-datasets/案例编号_地区_工程简称/`，包含 README.md、资料清单.json、01-招标资料、02-投标文件。取得官方成绩来源后使用 03-评审结果，产生分析后使用 04-分析记录；不提前创建空白成绩或报告文档。

文件名格式：`案例编号_类型_必要主体_文件内日期.原扩展名`。

- 招标：`CASE-001_招标文件_20260820.pdf`。
- 技术标：`CASE-001_技术标_安徽秉一市政_20260910.pdf`。
- 补遗、图纸、清单及成绩文件用实际类型和有据可查的版本／分册标识。
- 日期不明用“日期未注明”，不按文件修改时间推断；企业简称仅用于文件名，元数据保留全名。
- 多个文件版本使用有依据的版本号或日期区分，不标注未经确认的“最终版”。

入库流程：接收 → 确认项目与企业 → 分配编号 → 登记原名及 SHA-256 → 统一命名归档 → 核对版本与缺口 → 对应成绩 → 复核 → 更新索引。相同校验值的重复文件保留来源关联，不当作独立样本。

批量入库由 `intake` 按上述目录与命名自动完成：登记表逐行校验，原件按文件名定位、核对校验值与文字层，案例编号接着库内最大编号递增，已入库的样本重复运行时跳过；问题行不分配编号，列在入库报告里，修正后重跑。

**原件存放**。原件以对象存储为准（内容寻址，键为 `originals/sha256/<前两位>/<SHA-256><扩展名>`，写入防覆盖，上传与下载后核对），本地缓存（`TENDER_DATASETS_CACHE`）按相同目录保存工作副本；数据集仓库只保存资料清单、案例说明、评分配对集与入库报告，`.gitignore` 排除原件格式。新环境用 `store fetch` 按清单取回原件，`store verify` 核对对象存储是否齐全。

## 3. 信息维护位置

| 信息 | 主记录 |
| --- | --- |
| 全部案例索引与比较状态 | `tender-datasets/README.md` |
| 案例元数据、文件校验、版本与真实结果 | 每个案例的资料清单.json |
| 阅读说明、文件链接、结果摘要和缺口 | 每个案例 README.md，与 JSON 同步 |
| 参考判定与标注（第 2.2 节） | 案例的分析记录目录，标注人、日期、依据页码齐全 |
| 评分训练样本、同场成绩与分组 | `tender-datasets/评分配对集.json`（由 `intake` 从全部资料清单重建，不手改） |
| 每次入库的问题与待上传原件 | `tender-datasets/入库报告.md` |
| 原件 | 对象存储（键记在资料清单的 `storage`），本地缓存为工作副本 |

JSON 记录 case_id、完整项目名称、地区、标段／招标编号、企业、日期、assessment 和 file_records。assessment 保存有依据的满分、实际成绩、来源、排名和结果。文件记录稳定 file_id、来源名称、相对路径、文档日期、字节数、页数、SHA-256 及存储键；确定的文件版本另加版本属性。批量入库的资料清单（schema 1.3）另记工程类型、是否本公司、提交日期、官方成绩（含逐项得分）、同场成绩与入围线，以及正文的文字层检查与模板相似度签名。

未提供的信息不设置空字段，资料缺口在案例说明里集中记录。零分须有成绩依据。取得官方成绩文件后保存到评审结果目录，并登记发布与核实日期。

## 4. 成绩与可比性

用户报送结果、已核验官方成绩、人工标注和系统预测分别保存，口径不混用：

- 用户报送先在 assessment 中登记报送日期、原话含义、目标口径、分值满分及关联提交；缺官方来源时标注“官方来源未核验”。取得官方原件后另记核验与更正链，不覆盖已运行的预测。
- 系统里对应的记录：结果（来源为用户报送或官方、核验状态为未核验（`pending`）／已核验（`verified`）／冲突（`conflict`））；官方来源的结果须附官方成绩原件和页码、聚合办法才能核验；更正以新记录指向被更正的记录，旧记录始终可查。
- 事后观察到的入围门槛、成绩公示和中标结果属于评价端数据，任何情况下不进入评审输入。系统在冻结评审输入时拒绝官方成绩类资料，项目截止时间之后取得的资料版本也不允许进入。
- 技术总分保留满分、原分及出处，优先同项目同规则比较；跨项目比较要按地区、工程类型、评分办法、规模分组，换算百分制不消除项目难度与评分差异。
- 综合总分只有在公式与必要分项齐全时才计算技术贡献，并保留过程；无法拆分的综合分不作为技术分真值。缺少评分项明细时，从招标文件评分条款建立检查项，不推定官方分项或扣分原因。

候选人公示不等于最终中标，结果登记时分别统计“入围”“被否决”“中标”“未中标”（对应系统的结果状态），不把候选人记为中标。

## 5. 完整性与分析样式

核对招标、最终补遗、正文、图纸清单及结果是否同项目、标段和版本。原件只读，入库前后校验；正式结论标注来源及原页；抽取和渲染的中间文件在工作结束后清理。

案例说明固定包含基本信息、文件及版本、实际结果、资料缺口、分析入口。分析记录的问题表至少包含发现编号、问题分类（废标／否决风险、强制性要求、前后矛盾、范围残留、改进建议）、条款、正文位置、证据、判断状态、所需事实、建议及复核结果。区分事实、疑点、建议和评分结果；未完整审核时标注实际范围。

评价集按项目、日期和模板相似性分组：同一项目、近重复稿件及同源模板不跨组使用。评价集变更要记录成员、划分口径、理由和日期，已用于调整提示词或检测规则的案例转为开发用例，不作为独立评价集。

## 6. 公开规则资料

政策、公开招标及公示附件没有对应企业完整提交正文时，作为研究资料保存在 `tender-datasets/公开规则资料/`，不分配 CASE 编号。一个项目的招标、答疑及结果以项目编号关联，来源编号与[市场研究](../01-背景与市场研究/市场研究.md)一致。

资料清单记录原名、相对路径、官方页面及下载地址、文件日期及精度、发布与核实日期、适用范围、版本说明、页数、字节数及 SHA-256。未列文件日期的附件不以公示日期替代文内日期；文件名使用公示日期时注明依据。网页顶部编号、正文编号与封面不同的，记录冲突及确认依据，不静默修改原件。

这些原件可用于规则提取的检查和结果登记的验证；没有提交正文的公开成绩不能形成“内容—得分”配对。公示列写“/”的保留原始含义及未知状态。

## 7. 研究侧程序与产出

规则检索回归、扫描页识别、模型公开规则评测和全文评测的程序与输出保存在 [tender-research](https://github.com/zys743551828-art/tender-research/tree/main/results/)，对应的方法与边界见[验证报告](../04-验证与测试/验证报告.md)；其中的合成夹具不得导入案例库或作为校准数据。
