# 业务需求说明书

文档编号：BRD-001  
类型：业务需求与立项依据

本文维护业务目标与需求来源；融合产品行为和FR-001—FR-040／NFR-001—NFR-014统一以[AI投标工作台PRD](AI投标工作台PRD.md)为准。下文既有单正文流程不替代整包规格，技术和供体边界见[目标规格入口](../00-项目管理/融合目标规格与供体映射.md)。

## 1. 立项判断

建设公司内部的工程投标标书工作台，当前以市政工程验证，目标是**中标**。整份投标文件是工作对象，施工组织设计（下称施组）是技术部分中的一种内容；范围、分册与当前单正文实现的差距见[一期方案第 1.1 节](一期方案与验证计划.md#11-目标与优先级)。核心价值按以下三项确定优先级：

1. **不被淘汰**：废标、否决项、强制性要求、实质性响应。一项违反整份作废，得分再高也没用。
2. **技术分尽量高**：按招标文件的评分条款逐条评估，找出最可能丢分的地方。
3. **价格分与技术分合理换算**：评标价规则下不同报价的价格分，以及一个技术分约等于多少报价。

据此，一期有两个并列的 P0：**废标／否决项检测**与**评分预测**。响应矩阵、前后矛盾检测、范围残留检测、报价模拟、评审报告与导出、规则与事实、结果登记与校准都是围绕这两件事的辅助能力。最终目标、分工及实施阶段统一按[项目总纲](../README.md)执行，需求规格与验收见[一期方案与验证计划](一期方案与验证计划.md)。

立项依据：公司明确技术评分不稳定或无法入围这一业务问题；官方评标表显示废标、否决是真实且常见的淘汰原因；合肥官方原文证明评审路径、补疑变化和价格衔接存在差异。现有证据支持需求成立，不支持承诺提升多少中标率，也不支持把任何预测分数当作对结果的承诺。

公司的中标基线、完整的历史标书与官方成绩依赖公司提供；用官方成绩训练、评测通过的打分模型登记之前，评分预测标注“未校准”，详见[第 8 节](#8-风险依赖与业务放行)。

## 3. 价值假设与度量

系统的价值只用中标导向的结果度量，**不统计过程类指标**。系统不管投标人的内部成本；报价模拟只依据招标文件的评标价规则，不涉及成本与利润。

| 价值假设 | 应观察的证据 | 不成立时的处理 |
| --- | --- | --- |
| VAL-001：提交前发现并处理废标／否决风险，减少被否决 | 评审发现数、提交前已解决或驳回数、提交时仍未处理数、招标方实际否决数 | 提交时仍未处理数偏高时，检查闸门与提示是否到位；被否决但系统未发现的，补充规则提取与检测 |
| VAL-002：评分预测帮助排出最可能丢分的地方，整改后得分上升 | 每个项目逐轮的预测得分估计、未处理与已解决问题数，以及实际技术分；预测与官方技术分配对后的误差与偏差 | 误差大或样本不足时保持“未校准”，不用于决策；调整评分条款提取与评估方式 |
| VAL-003：报价模拟让报价决策考虑价格分与技术分的换算 | 保存的报价方案、风险提示触发情况，以及实际结果中报价阶段的表现 | 评标价规则表述不被覆盖时扩展基准价取法；平均值法对手报价只是估计，不夸大 |
| VAL-004：结果登记形成闭环，投入集中到真正影响中标的环节 | 入围率、中标率、各阶段淘汰数 | 已入围却持续未中标时分析报价与后续评审环节，调整优先级 |
| VAL-005：减少前后矛盾与模板残留这类低级失分 | 一致性与范围残留问题的发现与处理数，整改后是否再现 | 误报多时收紧检测规则 |
| VAL-006：允许按项目关闭或跳过非核心模块，让不愿完整跟随流程的团队仍然使用核心检测 | 各项目的开关取值（审计 `project.update` 记录），以及关闭了某些模块的项目的废标／否决风险闭环；只用于复审开关，不进入度量页 | 某个开关几乎总被关闭时复审对应模块；开启“规则按原文接受”的项目出现否决时复审其适用条件 |

度量指标（定义唯一见[一期方案第 7 节](一期方案与验证计划.md#7-指标与验收口径)）：

- **结果**：提交数、已出结果数、入围数、不入围数、被否决数、中标数、未中标数、入围率、中标率。
- **废标／否决风险闭环**：评审发现数、提交前已解决或驳回数、提交时仍未处理数、招标方实际否决数。
- **预测校准**：打分模型的评测误差与适用范围；上线后预测与官方技术分的配对数、平均绝对误差和偏差（配对不足 20 组不给误差）。
- **整改动作与得分变化**：每个项目逐轮的预测得分估计、未处理问题数、已解决问题数、未处理的废标／强制类问题数，以及实际技术分（如已登记）。

离线质量、预测分数、候选人公示都不能单独证明最终中标增益。少量试点保留样本量与归因限制，没有真实试点结果时不声称提升中标率。

## 4. 目标业务流程与责任

```
创建项目 → 上传招标文件（含补遗）与技术标正文 → 自动评审 → 评审报告（落地页）
        → 处理问题 → 报价 → 登记提交 → 登记开标结果 → 校准
```

| 环节 | 输入与业务产出 | 责任及控制点 |
| --- | --- | --- |
| 创建项目与上传资料 | 招标文件、补遗、技术标正文，可附图纸与清单；产出项目、资料版本与解析状态 | 投标团队创建项目、上传资料。上传新版资料自动开新一轮评审 |
| 自动评审 | 资料齐了自动解析、提取规则、冻结本轮输入、逐条核对、评分预测；产出评审报告 | 无需人工点步骤；失败时由人点“重新评审”。项目关闭“自动开始评审”时，资料照常解析，评审等人点“开始评审” |
| 评审报告 | 废标／否决风险、强制性要求满足情况、预测得分区间、报价最优候选、下一步 | 报告是项目落地页，所有页面围绕它展开；规则依据未确认时报告明示 |
| 处理问题 | 五类问题：废标／否决风险、强制性要求未满足、前后矛盾、范围残留、改进建议 | 市政工程师复核；按建议改稿；采纳不等于已解决 |
| 规则确认（按需） | 废标／否决／强制类规则 | 登记提交前须**人工确认**或驳回；评分条款、建议性要求不强制确认 |
| 报价 | 评标价规则、竞争对手报价估计、候选报价 | 试算后人工保存方案，保存留审计 |
| 登记提交 | 提交闸门通过后登记所提交的正文与评审输入 | 人工登记；正式签章、上传、解密和询标由公司责任人在交易平台完成 |
| 登记开标结果与校准 | 阶段结果、官方技术分与满分、来源 | 人工登记，核实来源；官方技术分与预测配对后用于校准 |

流程中可跳过或可关闭的环节：开始评审可以设为手动；前后矛盾检测、范围残留检测、报价、开标结果登记的提示可以按项目关闭；废标／否决／强制类规则的确认可以按项目选择“按原文接受”；事实库始终可选。废标／否决检测、响应矩阵、证据溯源与提交闸门不可关闭。开关的默认值与行为见 FR-013。

专业意见有争议时保留争议并由公司工程人员复核。正式提交版本与当次评审输入绑定，避免拿修改前的报告解释修改后的成绩。

## 5. 业务需求与优先级

P0 为一期必须交付并验证的核心能力；“辅助”围绕两个 P0；“支撑”承载它们；NFR 为约束。字段、交互和验收标准的具体规格见[一期方案第 4 节](一期方案与验证计划.md#4-功能需求与验收)。

### 5.1 功能需求

| 编号 | 优先级／关联障碍 | 业务要求与输出 | 业务验收证据 |
| --- | --- | --- | --- |
| FR-001 | P0；OBS-002、003 | 废标／否决项检测：提取废标、否决、强制类规则，逐条核对正文，识别违反与无法确认的条款，并在登记提交前设置闸门 | 已知否决条款被违反的稿件能被报出并定位到原文；未确认的这类规则或未处理的相关问题会阻止登记提交；检查失败不被显示成通过 |
| FR-002 | P0；OBS-001、006 | 评分预测：大模型按评分标准对每条带分值的评分条款逐项定档、核对得分要点，必要时与已知分数的历史标书比较；用公司官方成绩训练、评测通过的打分模型给出技术标得分与区间，列出最可能丢分的条款与正文证据 | 估计、区间与失分点齐备并带证据；已校准时写明训练组数、误差与适用范围，未校准时“未校准”标签与原因始终展示；不被说成对结果的承诺 |
| FR-003 | 辅助；OBS-002 | 响应矩阵：每轮对每条规则给出满足、违反、无法判断、检查失败；废标／否决与强制类、评分条款分别计数 | “满足”必有正文依据；“无法判断”与“检查失败”被看见而非被当作满足 |
| FR-004 | 辅助；OBS-001、004 | 前后矛盾检测：同一个量在正文不同位置取值不同；大段重复 | 同一量的不同取值与页码一并列出；型号不同的同类量不误报 |
| FR-005 | 辅助；OBS-001、004 | 范围残留检测：正文出现招标文件及补遗没有的工程对象，多为套用其他项目模板 | 列出残留对象与页码并请人确认；招标文件里有的对象不报 |
| FR-006 | 辅助；OBS-005 | 报价模拟：按评标价规则（满分、高于与低于基准价每 1% 扣分、最高限价、异常低价线、基准价取法）计算候选报价的价格分，给出风险提示、价格分曲线和技术分与报价的换算关系；方案人工保存并留审计 | 算例与手算一致；超过最高限价、异常低价被提示；平均值法注明对手报价只是估计；不涉及成本与利润 |
| FR-007 | 辅助；OBS-001 | 评审报告与导出：报告为项目落地页；导出 Word 评审报告和在正文原位高亮问题的批注版 PDF | 导出内容与页面一致；批注版 PDF 在原位标出问题 |
| FR-008 | 辅助；OBS-002、003 | 规则与事实（依据）：规则按性质分组并区分已确认与未确认，评分条款显示分值；事实库记录确认的工程事实；资料更新沿用已有人工决定 | 驳回或暂缓规则后评审引用的规则包不改变；报告标明依据状态 |
| FR-009 | 辅助；OBS-006、007 | 结果登记与校准：登记提交与开标结果（阶段结果、技术总分、综合总分、官方来源），技术总分与预测配对校准 | 官方分与预测分开；综合分不当技术标签；未知不作零；更正不覆盖旧记录 |
| FR-010 | 辅助；OBS-001 | 问题复核与改稿：人工确认、驳回、暂缓、请求补充事实；对已确认问题生成局部修订建议并采纳或驳回 | 每个动作留理由与对象版本；采纳不等于已解决 |
| FR-011 | 辅助；OBS-007 | 度量：入围率、中标率、废标／否决风险闭环、预测校准、整改动作与得分变化 | 口径与一期方案第 7 节一致；分母为零时不给值 |
| FR-012 | 支撑；OBS-003 | 项目、资料与自动评审：上传即评审，资料更新自动开新一轮，规则或事实更正由人决定何时重新评审，失败可重试 | 缺资料时说明缺什么；失败的环节点名；重复触发不产生重复评审 |
| FR-013 | 支撑；OBS-008 | 项目级功能开关，降低使用门槛：在项目设置里按项目开关“资料齐了自动开始评审”“规则按原文接受”“前后矛盾检测”“范围残留检测”“显示预测分数”“报价模块”“提示登记开标结果”；除“规则按原文接受”默认关闭外均默认开启；废标／否决检测、响应矩阵、证据溯源与提交闸门没有开关 | 关闭的模块不出现在导航、报告、“下一步”和 Word 报告里；关闭自动开始时资料照常解析，评审等人点“开始评审”；关闭检测时不产生对应问题；关闭分数时只列失分点、预测照常进行；按原文接受时未确认规则不阻止登记，但未处理的关键与废标／响应类问题仍阻止；改动留审计 |

| NFR-007 | 可访问性：键盘可达、焦点可见、状态不只靠颜色、对比度达标，手机宽度可阅读报告与问题 | 按设计文档检查项验收 |

## 6. 范围外

- 投标人的内部成本：系统不管投标人的内部成本，报价模拟不接受任何成本输入。
- 自动编标、模板起草与交易平台代提交、代解密；公司全面经营管理。
- 技术栈取舍的讨论：沿用既定技术栈。
- 岗位分权与项目成员管理：一期只有一道登录门槛，登录成员可查看全部项目、执行全部操作，关键操作留审计记录。
- 单点登录（公司统一身份）：登录方式是账号加口令，账号由管理员创建。
- 端到端真实环境跑通与真实数据评测：依赖服务器与数据，尚未验证。
- 一期工程验证以道路、管网及综合市政为主；园林、监理、土地整理只作规则边界参照。扩展工程类别前补充当地规则、完整样本及专业复核。

## 7. 参照与建设策略

市场供给、代表性产品与统一演示问题见[市场研究](../01-背景与市场研究/市场研究.md)，不在本文重复厂商清单。市场上的施组审查、模拟评审、查重和投标协作产品只作能力参照：用于对照废标检测、评分预测、报价和结果登记各环节的做法，不构成采购或排名结论。宣称“模拟官方评分”的产品，需要有可核验依据、适用版本及独立成绩对照，才能用于校准参考。

## 8. 风险、依赖与业务放行

**数据是瓶颈。** 两个 P0 的可靠性取决于数据，当前的数据状况如下，如实写入风险与依赖。

| 实际风险或不确定性 | 影响 | 处理与放行条件 |
| --- | --- | --- |
| 历史标书与官方技术分尚未到位（第一批约 300 份即将提供） | 打分模型尚未训练，预测是未校准的逐项合计 | 样本到位后按入库、批量预测、冻结协议评测的流程建立第一版模型，通过后先影子运行再上线；此后每次提交后登记官方技术分，产品数据回流重训 |
| 公司历史结果尚未取得、完整案例供给不足 | 无法评价当前中标率与真实瓶颈；只选高分稿会产生选样偏差 | 连续登记正式投标与结果，普通、未入围、被否决的都保留；试点前固定基线周期与范围 |
| 综合总分混合、无官方分项 | 不能把总分变化全部归于技术内容 | 成绩按口径分开；不反推分项 |
| 公开结果只披露部分成绩且无正文 | 不能从公开入围分数学习可靠的得分规律 | 公示用于规则与阶段观察，评分预测的校准使用有真实配对的公司案例 |
| 原文编号、日期、补疑存在冲突 | 自动关联或期限判断可能出错 | 保留原文并提示冲突，由人确认；每次实际投标检查全部生效附件 |
| 废标与评分条款依赖模型提取 | 提取遗漏会造成漏检 | 规则分未确认／已确认两种依据；废标／否决／强制类规则提交前必须由人确认；“无法判断”与“检查失败”让人看见 |
| 范围残留检测依赖工程对象词表 | 词表之外的残留对象不会被发现 | 词表随自有稿件检验扩充；报告中说明检测范围 |
| 项目开启“规则按原文接受” | 模型提取错误的废标／否决／强制类规则不经人工把关，可能漏检或误报 | 默认关闭；开启后报告依据说明、Word 报告与审计都写明“按原文接受”，问题的规则依据仍记为未确认；未处理的关键与废标／响应类问题照常阻止登记 |
| 平均值法基准价取决于对手报价，而对手报价只是估计 | 价格分与最优候选可能偏离开标结果 | 界面注明；以开标结果为准，保存多个情景 |
| 真实服务器与数据尚未到位 | 端到端真实环境与真实数据评测尚未验证 | 依赖服务器与数据，到位后按[验证计划](一期方案与验证计划.md#8-验证计划)执行；之前不声称准确率与中标效果 |

依赖及责任人唯一跟踪在[决策与依赖](../00-项目管理/决策与依赖.md#2-业务依赖)。资料未取得不妨碍已具备原件的规则验证；没有完整案例与工程复核，不能宣称废标检测通过验收；没有官方技术分配对，不能宣称预测可靠；没有最终业务记录，不能宣称中标效果。已执行的验证与结果见[验证报告](../04-验证与测试/验证报告.md)。
