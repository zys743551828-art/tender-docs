# 从PDF资料切片到完整产品的交付计划

本计划由产品Owner收口，给PM排期及前后端、测试、架构和用户角色直接执行。目标仍为全新内部市政AI投标工作台，否决风险与评分预测双P0；不增加迁移、CRM、履约、对外SaaS或岗位审批。本计划是待实现交付单，不是软件通过记录。当前已验收范围仅见[PDF资料切片验收](../首个PDF资料切片验收.md)与[产品03增量复核](../implementation-product-review/候选03增量产品复核.md)。

业务语义以[PRD](../../02-业务与产品/AI投标工作台PRD.md)为准，接口字段以[目标契约](../../05-技术与设计/detailed-design/README.md)为准；当前实际API单独见`tender-workbench/packages/contracts/implemented.openapi.json`。目标有接口不等于已实现，连接DeepSeek／OSS成功不等于评审、RAG或评分成功。产品Owner本次不读取凭据、不执行收费调用。

## 1. 可交付批次与依赖

按纵向切片交付，每批都有可运行页面、真实API、成功／失败状态和独立验收，不先堆完整平台菜单。工期由实际进度判断，不预设无依据的周数。

| 批次 | 后端／执行交付 | 前端可用交付 | 完成证据与依赖 |
| --- | --- | --- | --- |
| 已验收资料片 | 登录、项目、单传核验、批次／绑定、PDF页与文字依据、文件版本及只读历史 | 建项目→上传→核对范围→真实原页／历史／直接下载，390px可用 | 保留原验收证据及范围，不要求重做旧工程；不能称A1完整 |
| P 真实服务适配 | PM与开发完成DeepSeek能力与OSS实际读写、配置隔离、超时／重试／预算和未配置行为 | 文件上传及模型服务失败有准确恢复说明，不暴露供应商细节／密钥 | 调用与对象读写真实证据、错误边界；不能以连通替代质量。产品不执行收费探针 |
| A1.1 核对结果 | 自动／人工RequestReview；生效规则提取；必要来源／完整相关正文核对；四层覆盖、逐行状态、风险及当前结果身份 | 上传后真实进度→简洁风险结果／一个下一步→矩阵→两侧原页；规则／事实按需查看 | 有已知正反例、非法引文／数字、缺范围与失败测试；未配置不返回演示结论。保留矛盾／范围残留两个可选检测 |

| F 辅助报价／业务复盘／任务 | Decimal报价曲线和版本、真实结果分母／风险走势、预置任务到可配置手动／事件／定时运行 | 报价可关，多候选与历史方案；真实业务复盘；模板／运行记录分开，不造假触发按钮 | 手算、旧方案快照、未知分母及隐藏预测测试；不纳内部成本利润；任务不能自动做人工正式决定 |
| E 完整运行交付，贯穿各批 | 分片与SSE、运行观测、容量、私有资源、全量导出、备份恢复、结构升级、生产故障与回退 | 状态恢复／任务通知／取消语义、键盘与窄屏、明确支持范围及错误恢复 | 登录、审计和基本备份从真实资料首批启用；后续真实恢复与生产能力独立验收。PM按用户既有授权收口，不把开发单节点外推生产 |

GovDash的长处保留在项目工作面、矩阵／章节／原页联动、同页AI建议与来源、差异预览、版本用途和任务运行记录；本产品的快速PDF、风险优先、确认后置、外部改稿、证据真实性、完整评分与事前事后隔离同样是完成条件。未实现的工作面不提前摆可点击空菜单。

## 2. A1本批拆分与交接

1. 后端先给A1.1实际OpenAPI与生成类型，提供本轮冻结身份、source／rules／facts／matrix／findings／operation真实投影；前端同步开发真实状态及空／错／过期分支，不硬编码演示结论。
2. A1.2把已审事务落业务应用：人工决定、补漏与保留、补遗关系、事实更正、跨轮复检。产品动作字符串已与后端统一，见[界面与数据交接](A1验收与界面数据交接.md)。不能以通用string让两端各自猜。
3. A1.3联调标准登记与有据补录、报告和批注，再走外部改稿完整长路径。实际提交由人去交易平台完成，系统只作事实与检查登记。
4. 测试独立执行API／Worker及浏览器，产品／用户角色review真实页面，架构review权限、输入与事务；PM绑定最终来源和证据放行。真实标注、真人体验和模型精度各自留待对应条件满足，不伪造通过。

## 3. 原13项应用验收的交付归属

原记录[application-acceptance.json](../design-remediation-checks/application-acceptance.json)保持原ID与pending；本目录仅提供执行拆解。详见[13项执行清单](a1-acceptance.json)，每项列夹具、动作、界面结果、真实后端断言、目标operation／字段及所属批次。

A1核心与提交覆盖PPR-AC-01／02／03／04／03-B／03-C及U01-A／U03-A／U04-A；PPR-AC-05随C真实研究产物组合演示，PPR-AC-06是各批缺资料时的诚实交付边界。U02-A在实际接收DOCX并具备转换路径后执行，PDF切片诚实拒绝Word不能冒充此用例通过；U05-A在B正式结果登记模块执行。分批没有取消任何一项，也不因等待DOCX或官方成绩暂停A1独立可用。

同一执行清单另列6个首批串联任务，补足原13项之外的基本路径：`A1-S01`一键准备接续与新稿竞争、`A1-S02`矩阵与诚实失败、`A1-S03`事实从空集到补替撤、`A1-S04`规则后置单条与显式批量确认、`A1-S05`外部改稿复检及旧轮回看、`A1-S06`标准登记／线下事实与恢复。这些是已有PRD行为的执行拆解，不增加新的审批或另改原验收编号。

## 4. 需求完整性与验收状态

[计划追踪数据](delivery-plan.json)覆盖FR-001—040，并将13项与现有Schema／operation对应。[check_plan.py](check_plan.py)仅检查计划引用、字段与原ID完整性，不执行软件、不证明业务正确。所有新增执行条目仍为`pending_application`；当前已验收资料片是单独证据，不能给未来条目自动盖章。

现有产品主记录没有必要新增流程，故本计划不改冻结PRD或技术设计。已有行为缺少具体读取／决定入口的地方，在交接文档明确列为下一批实际契约需要闭合的点，由开发与架构给唯一协议，产品收敛语义；不让前端用缓存、固定文案或猜字段补洞。
