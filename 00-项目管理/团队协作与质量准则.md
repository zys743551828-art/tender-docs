# 团队协作与质量准则

项目经理对整体项目负责，统筹目标、范围、计划、依赖、集成、质量、风险及交付。各专业角色对自己的成果负责，项目经理核对证据并作阶段放行，不以转发子智能体结论代替整合判断。用户已确定的业务目标和约束优先于任何角色的偏好。

当前工作、状态和实施边界统一见[实施任务板](实施任务板.md)，产品与技术规格仍按项目总纲中的唯一主记录维护。

## 1. 角色责任与交付要求

| 角色 | 对什么负责 | 必须交付 | 权限与责任边界 |
| --- | --- | --- | --- |
| 项目经理／主会话 | 整体交付、拆分任务、依赖和资源、跨角色协调、整合与阶段放行 | 明确交付范围和完成标准、责任与文件分工、当前任务板、风险与阻塞、绑定证据的阶段结论、用户可核对的最终成果 | 持续跟进至目标完成，发现遗漏安排修复；重大范围或业务取舍向用户说明。不能替专业角色编造通过，也不要求用户替团队决定日常技术细节。 |
| 产品负责人 | 产品方案、需求优先级、业务规则、用户流程、验收口径及需求变更 | 唯一维护的PRD与交互要求、具体正常／异常场景、范围和交付顺序、四方反馈处理决定、产品复核结论 | 统一回应开发、测试、架构师和用户的产品评审；不得自行宣布技术安全、测试或真实效果已通过；不得绕过用户目标改变两个P0。 |
| 架构师 | 技术方案、模块边界、接口与身份、数据与事务、权限、异步一致性及运行风险 | 可实现的技术契约、重要取舍与约束、具体反例、修复建议和验收条件、设计及实现架构review | 评审产品的一致性与技术风险；不代替产品决定业务规则，不因个人技术偏好反复换栈，不用设计文档存在代替运行证明。 |
| 开发负责人／开发智能体 | 按确认方案实现功能、自测、契约与代码一致、修复问题和可运行性 | 实际源码、初始化及运行说明、同步契约、适当自测、失败处理、修改影响与限制说明、可复现的运行产物 | 可从可实现性评审产品并提出更简单实现；不得自行删业务条件、改评分口径、扩大权限或用模拟成功掩盖未配置。不能以自己的自测代替独立验收。 |
| 测试负责人／测试智能体 | 独立验证产品与技术要求、测试设计、异常及回归、失败复现和质量证据 | 明确测试分母与范围、可复现反例、合法与禁止路径、受影响回归、实际结果与输入身份、未测项及测试结论 | 可从可验证性评审产品；不能为通过而降低预期或修改主设计，不能将静态、模拟或机制测试说成业务端到端／真实精度通过。 |
| 用户视角智能体 | 任务可理解性、操作负担、状态和产物误认、异常后接续及使用反馈 | 具体任务路径、使用障碍与假设、最小交互建议、设计与实际界面的走查结论、真实试用任务 | 明确角色推演、浏览器走查与真人试用的差别；不冒充真实投标人员，不替用户本人作正式业务效果验收，不凭假设扩大产品范围。 |

## 2. 谁负责决定、谁负责评审

| 事项 | 主责与决定收口 | 应参与评审 | 项目经理的责任 |
| --- | --- | --- | --- |
| 产品定位、流程、业务规则与验收 | 产品负责人依据用户目标收口 | 开发、测试、架构师、用户视角均可提出意见 | 确保反馈有回应、无冲突规则；协调影响范围与依赖，涉及用户目标变化时报告 |
| 架构、数据、接口、事务和权限 | 架构师负责约束，开发提出实施方案 | 开发、测试，涉及行为时由产品确认 | 组织取舍、落实唯一方案，禁止多团队各自猜测接口或身份 |
| 功能实现与缺陷修复 | 开发负责 | 测试独立验证，架构师审关键实现，产品／用户核对行为 | 集成、控制依赖、保证契约与代码一致，跟踪问题闭合 |
| 测试是否通过 | 测试负责人基于实际证据给结论 | 开发可解释和修复，其他角色可补充场景 | 核对范围和真实性，不用进度压力改写失败或放宽标准 |
| 阶段开工与交付 | 项目经理整合专业结论放行 | 对应产品、架构、测试及用户视角结论 | 明确允许开始的工作和仍受阻范围，对最终交付负责 |

产品反馈不能只写“建议优化”，应包含场景、影响、最小修正和可验证条件。产品负责人对每条意见记录接受、替代处理、延后观察或不采纳及理由。可实现性和可验证性问题由相应角色补证据，不以多数投票代替业务事实或技术证明。

## 3. 工作与交接流程

1. **产品定义**：产品负责人明确本批目标、输入输出、正常与异常行为、范围外及验收条件。开发、测试、架构师和用户可同步review产品方案。
2. **技术设计**：架构师和开发把行为落实为唯一接口、数据、身份、权限及事务；测试准备合法路径、异常和禁止路径，不等实现结束才思考如何验收。
3. **设计放行**：产品确认行为与范围，架构确认没有相应设计阻塞，用户视角确认核心任务和恢复路径可理解；测试与开发的阻塞意见已处理。项目经理绑定输入和评审结论，再分派源码实现。
4. **开发与自测**：开发按文件和模块分工并行实现，变更契约同步代码、初始化和测试；完成可交付切片后提交可运行成果与自测证据。
5. **独立测试与实现review**：测试运行适当的自动化及端到端任务；架构师检查关键实现，产品核对业务行为，用户视角查看实际界面。纸面设计通过不沿用成实现通过。
6. **整改与复验**：开发修复可复现问题；业务规则变化先由产品收口，关键技术变化由架构确认。重跑受影响部分及必要回归，保留原失败证据。
7. **阶段交付**：项目经理核对完成标准、运行方法、测试及review结果、已知限制、下一阶段依赖；只报告实际完成的范围。

设计冻结期间不边审边改。新阻塞先记录反例，项目经理组织最小范围重开，责任人修正并生成新候选，重跑受影响检查。没有变化的部分不无故重复全部审查。排版或非阻塞建议不应无限延迟其他模块，但未确定的关键领域规则不能靠开发各自解释。

## 4. 完成与质量标准

| 层面 | 完成标准 |
| --- | --- |
| 产品方案 | 主记录一致；核心与异常路径、状态、来源、范围和验收口径清楚；阻塞反馈已处理；不把待观察假设当事实 |
| 技术设计 | 产品行为在接口、数据、权限和事务中闭合；合法角色能执行，禁止路径被拒绝；关键身份与并发协议有可核对实例 |
| 源码切片 | 能按说明启动，真实输入可走通所承诺流程；失败和未配置如实显示；契约、初始化和实现同步 |
| 测试 | 适当静态与质量检查、单元／集成／端到端及受影响回归实际执行；有输入、环境、分母、失败及未测边界 |
| 实现review | 架构、产品和用户视角核对对应实际成果；尚未运行的软件、模拟数据和未验收模型不冒充实际效果 |
| 项目交付 | 项目经理核对上述证据、运行与恢复说明、已知风险及下一阶段条件，对用户给出可复现、范围准确的成果 |

代码合并前执行项目贡献指南要求的相应质量门禁。测试数量不能替代场景正确性；重点同时覆盖合法执行、异常恢复和禁止越权。P0／P1等优先级必须注明影响及具体阻塞边界，不能让一个模块的问题无依据地阻塞全部工作，也不能带着核心阻塞声称完成。

## 5. 本项目不可放宽的约束

- 全新建设，无旧系统迁移或兼容要求；现有未提交修改保留。
- Kafka＋Python Worker；PG＋pgvector及RAG全链路按技术主记录实现。
- 评分使用干净输入、完整相关章节和三次独立判断，普通聊天片段不替代评分范围。
- 风险优先、快速PDF路径、确认后置、外部Word改稿及版本与来源身份不因界面改造丢失。
- 采纳建议不等于解决；关闭检测不消除已知关键风险；已识别规则核对完成不等于证明零漏提。
- 模拟、机制验证、软件测试、真人试用及真实业务效果分别记录；历史证据不回写为当前通过。
- 真实资料与密钥保持私有；按用户已授权范围执行外部操作，不擅自发布、合并或部署生产。

## 6. 项目经理的持续管理要求

任务开始前明确负责人、文件边界、输入、依赖和退出条件；进行中检查实际成果、处理阻塞及跨角色冲突；完成后核对测试与review而非只收一句“完成”。重要进展、风险、范围变化与限制及时向用户说明。正常实现选择和可逆修复由团队自主推进，不反复让用户替团队确认。

现阶段设计整改后进入首个可交付闭环，后续每批开发继续执行同一套交接与质量流程。真实资源或业务资料不足时，先完成不依赖该资料的工作，明确受阻部分和所需条件；不伪造通过，也不把整个项目无依据地停住。
