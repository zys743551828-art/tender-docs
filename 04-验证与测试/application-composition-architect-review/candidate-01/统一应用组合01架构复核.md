## AC01 / P2：生命周期强 ETag 未覆盖真实响应

定位（均为本候选固定源）：[lifecycle_routes.py](/workspace/tender-workbench/docs/application-composition-development-checks/runtime-preview-01/apps/api/lifecycle_routes.py:21) 返回 `service.view`，却以 `bid_etag` 标记；同文件第63、67行在写命令中也使用 BidView 的条件投影。[service.py](/workspace/tender-workbench/docs/application-composition-development-checks/runtime-preview-01/packages/lifecycle/service.py:173) 的生命周期表示包括未完成上传、批次、操作和归档阻断信息；[views.py](/workspace/tender-workbench/docs/application-composition-development-checks/runtime-preview-01/apps/api/views.py:97) 的 BidView 摘要没有这些字段。

独立反例使用真实会话、CSRF 和非 owner PostgreSQL：读取 lifecycle → 通过实际上传批次 API 创建 open 批次 → 再读取 lifecycle。响应 `unfinished_batches` 从空变为一个真实批次，两个强 ETag 完全相同。原始前后响应见 [lifecycle-counterexample.json](lifecycle-counterexample.json)，可运行驱动在自有运行副本 `runtime/tests/test_application_composition_integration.py` 的独立反例中。

影响：客户端持有旧生命周期表示仍可能通过条件头检查，条件更新与缓存验证无法准确表达该资源是否变化。**未复现归档绕过**：归档仍在锁内重新检查阻断条件，本轮原有实际 API 场景确认 open 批次会阻止归档。

建议：使用生命周期完整响应的专属强 ETag；GET 同一快照读取表示并生成标记，POST 在 bid 锁内以同一投影核对，成功标记覆盖实际返回表示。原 Command 成功 ACK 应优先重放；其他 Bid CAS 保持自己的资源投影。验收：未完成批次变化使 lifecycle 标记变化；旧标记412，新标记合法动作成功；原成功命令同键重放保持原 ACK；归档阻断仍有效。
