# 交互与视觉设计

文档编号：DESIGN-001  
类型：信息架构、交互与视觉规范

## 1. 设计判断与范围

产品目标是中标，不是产出一份看起来合规的文档。界面按三件事的重要性组织：先让人看见会不会被淘汰（废标／否决项、强制性要求、实质性响应），再看技术分还能在哪里多拿，最后看报价与技术分怎样合理换算。整个产品围绕一份评审报告展开：资料上传后系统自动评审，落地页就是报告，其余页面都从报告进入、处理完回到报告。

界面不出现“提取规则”“冻结快照”“开始诊断”之类的步骤按钮，也不要求用户判断下一步该点什么：上传即评审，进度由流水线横幅显示，下一步由报告给出。唯一可选的人工步骤是“开始评审”，只出现在关闭了“资料齐了自动开始评审”的项目上（第 3.9、4 节）。

用户不一定愿意完整跟随流程，所以核心之外的模块可以按项目关闭：关闭的模块从导航、报告、“下一步”和导出里消失，而不是留下一块空白或一个灰掉的入口。废标／否决检测、响应矩阵、证据溯源和提交闸门始终存在。内部对象 snapshot 在界面写作“本轮评审的输入”。

词汇固定为：评审（一轮对招标规则的核对加评分预测）、核对、判定、响应矩阵、废标／否决风险、强制性要求、评分条款、依据（规则与事实）、报告、功能开关。

流程、登录与产品范围的完整定义见[一期方案](../02-业务与产品/一期方案与验证计划.md)，接口与数据见[系统架构与数据契约](系统架构与数据契约.md)。设计稿在 [tender-design](https://github.com/zys743551828-art/tender-design) 仓库，页面文件为 index、report、pipeline、findings、rules、price、submit、metrics、materials、settings 的 HTML（pipeline 汇集流水线横幅的各种状态，含等待手动开始；settings 为项目信息与功能开关），十个静态页面共用一份 `styles.css`，令牌与实现一致，浅色与深色随系统（`prefers-color-scheme`）切换，截图宽度 1440px，数据均为虚构。

## 2. 信息架构

导航分两级。全局导航只有“项目”和“度量”；进入项目后侧栏切换为项目侧栏：项目名片（名称、状态、截止）、三个常用入口（评审报告、上传资料、处理问题）和“更多功能”。更多功能包含依据、报价、提交与结果、检索、设置；访问其中页面时自动展开，保留当前位置。系统只有一道登录门槛，登录后所有页面与动作对每个人可用，界面不按岗位隐藏或禁用入口。

| 位置 | 页面 | 路由 | 回答的问题 |
| --- | --- | --- | --- |
| 全局 | 项目 | `/projects` | 哪些项目最急、哪些有废标风险没处理 |
| 全局 | 度量 | `/metrics` | 入围率、中标率、废标风险闭环、预测校准、逐轮变化 |
| 常用 | 评审报告（落地页） | `/projects/:id` | 这一轮评审的结论是什么，下一步做什么 |
| 常用 | 处理问题 | `/projects/:id/findings` | 逐个处理评审发现的问题 |
| 更多 | 依据 | `/projects/:id/basis` | 评审依据的规则和事实是否正确、是否确认 |
| 更多 | 报价 | `/projects/:id/price` | 不同报价下的价格分，一个技术分约等于多少报价；项目关闭报价模块时不出现在导航中 |
| 更多 | 提交与结果 | `/projects/:id/submit` | 能否登记提交；开标后登记结果 |
| 常用 | 上传资料 | `/projects/:id/materials` | 上传招标文件、补遗、正文，查看版本与解析状态 |
| 更多 | 检索、设置 | `search`、`settings` | 在资料中查证据；项目信息与功能开关 |

另有原件查看（`files/:versionId`）和证据查看（`evidence/:evidenceId`），从问题、响应矩阵、预测失分点的“正文依据”进入，用 PDF.js 渲染原页并高亮引文，可翻页、缩放。

项目状态在侧栏名片和项目总览中以文字加色块显示：资料待补充（`materials_pending`）、待开始评审（`ready_to_analyze`，仅出现在手动开始评审的项目上）、评审中（`analyzing`）、评审中断（`analysis_failed`，可重试）、问题待处理（`issues_open`）、可登记提交（`ready_to_submit`）、已提交（`submitted`）、已归档（`archived`）；另有已取消（`cancelled`）、流标（`failed_tender`）。

前置条件未满足的页面仍可点开：页面说明还差什么并给出跳转，不隐藏入口。关闭的模块是唯一的例外：关闭报价模块后导航不出现“报价”，直接打开报价页的地址时，页面说明“本项目关闭了报价模块”并给出“去项目设置”的入口。例如没有完成的评审时，“问题”“报价”等页面照常可读，报告页则显示流水线进度或“上传资料”引导。

## 3. 页面规范

### 3.1 项目总览

项目清单每个项目一行：名称（含标段与轮次）、否决风险（未处理的废标／否决风险数，例如“1 个未处理”）、预计技术分（区间带“未校准”，并写明覆盖程度，如“只覆盖 8 / 60 分”；项目关闭“显示预测分数”时不显示分数；无预测时写“尚无预测”）、状态、截止时间（临近用文字提示，不只用颜色），行尾是与报告同源的下一步按钮（如“处理否决风险”）。按截止时间升序，已提交与已归档沉到列表后部。页面唯一的实心主按钮是“新建项目”：只需填写名称，招标编号、标段、轮次、地区、工程类型、截止时间都是选填，可以收起，之后在“设置”里补充。没有项目时说明能做什么，不展示示例数据。

### 3.2 资料

- 拖拽或选择文件上传，一次可放入多个文件。系统按文件名猜测每个文件的用途（招标文件、补遗／答疑、技术标正文、图纸、工程量清单、已提交文件、官方结果、其他资料）与版本（同用途同名视为该文件的新版本，唯一一份正文默认是它的新版本），上传前可以逐个修改；从其他页面带着用途进入时以带来的用途为准。上传后提示“已记为 X 的第 N 版”。
- 上传队列逐个显示进度，失败的文件可单独重试，地址过期自动重取。
- 列表显示每个文件的版本、取得时间、解析状态（解析中、已解析、部分页无文字层、解析失败及原因），不显示校验值等内部信息。解析失败的文件给出“请转换为可复制文字的 PDF 后重新上传”的明确提示。
- 页面顶部是流水线进度；已有评审任务时提供“查看评审进度”，完成后提供“查看评审报告”，都返回当前项目报告。没有“下一步”按钮。资料齐了（至少一份招标文件和一份技术标正文）自动开始评审；只有招标文件时显示“还缺技术标正文”。项目关闭了自动开始评审时，进度在资料解析完成后停在“等待开始评审”，并给出“开始评审”按钮（第 4 节）。
- 上传新版招标文件、补遗或正文后，进度提示“资料已更新，正在基于最新资料开新一轮评审”。
- 单文件最大 100 MiB；分片 8 MiB、浏览器最多 4 个分片并行。浏览器分片通过同源 API 转传；分片校验失败如实提示重试，不要求用户配置桶跨域。

### 3.3 报告（落地页）

数据来自 `GET /projects/{id}/report`。从上到下依次为：

1. **流水线横幅。** 以步骤条显示资料、规则、核对、预测四步，见第 4 节。
2. **结论卡片。** 一句话回答会不会被否决：有未处理的废标／否决风险或强制性要求类问题时写“有 N 个可能导致否决或不满足强制要求的问题还没处理”（危险色）；没有风险但有条款在正文里找不到明确响应时如实说明（警示色）；都没有时写“没有发现否决风险”，并注明依据状态（例如“依据的 12 条规则里有 3 条还没核对，暂按原文判断”），不得写成“没有风险”。下方是关键数字：
   - 废标／强制要求“满足 X／Y”：X 为判定“满足”的条数，Y 为废标／否决与强制类规则总数（`qualification.total`）。
   - 预计技术分（已校准／未校准／超出校准范围）：区间 `low`–`high`；未校准时写明覆盖程度（如“只覆盖 8 / 60 分”），见第 5 节。
   - 报价最优候选及其价格分：来自最近保存的报价方案；没有方案时显示“还没填报价”入口。
   - 关键数字随功能开关变化，见第 3.3.2 节。
3. **下一步。** 按接口返回的 `next_actions` 顺序显示首条主要动作，其余待办可展开，折叠标题标明剩余关键问题与其他建议数量；每条带标题、说明和按钮，按钮文字说明要做什么，落点具体到问题分类或响应矩阵。顺序即重要性：废标／强制类问题、无法判断的条款、未确认的关键规则、其他问题、填写报价、登记提交（只在评审完成、且资料规则事实都没有更新时出现）、登记开标结果。开始、重新评审与等待由流水线横幅承担。一屏只有一个实心主按钮：横幅有“开始评审”或“重新评审”时，下一步全部为描边按钮。
4. **逐条响应（响应矩阵）。** 见第 3.3.1 节。
5. **技术分预测。** 估计与区间条（满分为轴的全长），标签写明“已校准”或“未校准”；已校准时区间写“约 80% 把握在 a–b 分之间”，并写出打分模型的训练组数、评估误差与适用范围，未校准时写出原因与覆盖了多少分；失分点列表（每条含条款、档次、满分与估计失分、缺失的要点、评估说明、正文证据链接、局限）；在线对照的状态说明。
6. **全部问题。** 按分类（废标／否决风险、强制性要求未满足、前后矛盾、范围残留、改进建议）列出待处理数与总数，点击进入“问题”页并带分类过滤；宽屏时这一块在右侧随页面滚动保持可见。
7. **导出。** “下载评审报告（Word）”（`/report.docx`）、“下载批注审阅稿（PDF）”（`/body.annotated.pdf`，在正文原位高亮问题）。正文不是 PDF 时批注版按钮不可用并说明原因。

没有完成的评审（接口返回 404 `report_not_ready`）时，不显示空报告：评审进行中显示流水线进度；资料不齐显示“上传资料”引导；评审中断显示失败环节与“重新评审”；手动开始的项目资料已就绪时显示“资料已就绪，等待开始评审”与“开始评审”按钮。

#### 3.3.1 响应矩阵

页面标题为“逐条响应”。每轮评审对每条参与评审的规则给出判定，默认只展开需要关注的行（违反、无法判断、检查失败、依据未确认），其余收起为一行计数，可展开查看全部。表头：条款、类型（否决项、强制性要求、评分条款、建议性要求、例外）、判定、正文依据、规则是否已确认。

- 排序：违反在最前，其次无法判断与检查失败，最后是满足；同一判定内按类型（否决项、强制性要求在前）排。
- 判定用文字加图标加底色三重表达，不只靠颜色：满足、违反、无法判断、检查失败。“无法判断”和“检查失败”不得使用与“满足”相近的绿色或对勾，应使用中性或警示样式，并附一句说明（“正文没有明确响应”“模型输出不可用，未能完成检查”）。
- 满足必须显示正文依据（页码与原文摘录，可点击进入原页）；违反显示关联的问题链接（`finding_ids`）。
- 规则未确认时在判定旁标“依据未确认”，并给出“评审暂按提取的原文判断”的提示；该行可直接点“按原文确认”，不必离开报告。
- 上方并排显示两组计数：废标／否决与强制类（`qualification`），评分条款（`scoring`），各含满足、违反、无法判断、检查失败。
- 覆盖度不是“完整”时，表头显示“有 N 条规则未能完成检查，结论不完整”，不得显示成检查通过。

#### 3.3.2 报告在各功能开关下的呈现

报告读取项目当前的功能开关（第 3.9 节）裁剪内容。关闭的模块不留空卡片，也不出现在“下一步”里；没有开关的部分（结论句、废标／强制要求满足数、响应矩阵、依据状态）始终显示。

| 开关取值 | 报告页 | 导出的 Word 报告 |
| --- | --- | --- |
| 关闭“资料齐了自动开始评审” | 资料齐了而还没有评审时，横幅为“资料已就绪，等待开始评审”并给出“开始评审”；已有评审、资料又有更新时，报告照常展示上一轮，横幅为“资料有更新，等待开始新一轮评审”并列出更新原因，“开始评审”由横幅给出 | 导出最近一轮已完成的评审，不受影响 |
| 开启“规则按原文接受” | 结论卡片的依据行写“N 条规则按原文接受（项目设置）”，不出现“核对规则”入口；“下一步”不出现“确认规则”；响应矩阵中未确认的规则仍标“依据未确认” | 评审依据一段写明“本项目设置为按原文接受未确认的规则”；判定表里未确认的规则仍标“规则未确认” |
| 关闭“前后矛盾检测”或“范围残留检测” | 问题分类计数不显示对应分类 | 问题清单按该轮实际产生的问题列出；关闭之后新开的一轮不产生这类问题 |
| 关闭“显示预测分数” | 结论卡片的“预计技术分”换成“可能的失分点 N 处”；预测面板标题为“可能的失分点”，只列条款、评估与正文证据，没有估计值、区间条、估计失分和校准说明 | 第三部分标题为“可能的失分点”，表格只有“评分条款”“评估”两列 |
| 关闭“报价模块” | 结论卡片没有报价最优候选；“下一步”不出现“填写报价” | 没有第四部分“报价” |
| 关闭“提示登记开标结果” | 登记提交后“下一步”不出现“登记开标结果” | 不受影响 |

所有开关都关掉或打开时，报告的结构与顺序不变，只是对应的数字、分类或条目出现或消失。

### 3.4 问题

- 分类标签页：废标／否决风险、强制性要求、前后矛盾、范围残留、改进建议；叠加状态筛选（待复核、已确认待修改、已驳回、暂缓、修改中、待复检、已解决）。列表使用键集分页（默认每页 25），可用 J／K 键在问题之间上下移动。
- 列表项：分类与状态在首行，随后是问题陈述；规则来源的问题标注规则依据状态（已确认、依据未确认）；前后矛盾和范围残留标注“检测”，没有规则链接。
- 详情区：问题陈述；“招标文件要求”与“施组正文写法”左右并排，引文高亮，窄屏上下排列；处理进度（问题在生命周期中的位置）；所需事实；处理决定；改稿建议。点击引文打开原页，PDF 页内高亮；无坐标时只定位到页，不画虚构高亮。
- 处理决定：确认问题、驳回、暂缓、暂缓待补事实（请求补充事实），以及重新打开、标记已解决。确认可以不写理由；驳回、暂缓、重新打开、标记已解决必须写明理由。所有动作携带当前问题的版本号，被他人处理时提示刷新并保留已输入的理由。
- 已被更新一轮替代的旧问题只读，页面提示“该问题属于已被更新的一轮评审，请在最新一轮处理”，不提供动作按钮。
- 改稿建议默认收起：选择问题和允许使用的事实后生成局部修改（原文、替换文、使用的事实），标“AI 建议 · 待人工确认”，由人采纳或驳回；正文有新版本后旧建议显示为过期，不能采纳。PDF 正文不能被自动改动：采纳后提示到 Word／WPS 中改稿并上传新版本。采纳不等于问题解决，解决由人在复核后标记。

### 3.5 依据（规则与事实）

两个标签页：规则、事实库。

- **规则**按性质分组，顺序为否决／废标、强制性要求、评分条款、建议性要求、例外。每条显示条文、条件、例外、出处引文、确认状态；评分条款显示分值。
- 确认状态：已确认；未确认（显示“评审暂按原文判断”）；已驳回；已暂缓。驳回的与暂缓的规则不参与评审。
- 动作：确认（可不写理由，不弹窗）、驳回、暂缓（后两者必须写明理由）。页首有一键“全部按原文确认（N 条）”，一次确认全部待核对的规则，已确认的不在其中。
- 提示规则：确认一条没有改变参与评审的规则集合时，不出现提示。驳回、暂缓或把它们改回确认会生成新的规则包，页面随即提示“规则已更正，建议重新评审”并给出重新评审入口，由人决定何时重新评审。
- 从规则提取的候选标“AI 建议 · 待人工确认”，人工确认后回到中性样式。沿用上一版决定的规则带徽标。评标办法里提取到技术分满分与评标价规则时，给出原文出处和去报价页的入口。
- 废标／否决／强制类规则的未确认数在页首突出显示，因为这些规则必须在登记提交前确认。评分条款和建议性要求不强制确认。
- **事实库**：录入带证据的事实（名称、对象、范围、数值与单位、陈述、至少一条证据），可撤回；录入时可直接检索当前资料作为证据。事实变化后，流水线横幅提示“事实有更新，重新评审”，不自动开新一轮。

### 3.6 报价

页面左侧输入，右侧实时试算。

输入：

- 评标价规则：从招标文件提取到时已预填，页首写“已按招标文件填好评标价规则，请核对”并给出原文页码；招标文件里没有找到评标价办法时，可以从常见办法的模板开始。字段为满分、高于基准价每 1% 扣分、低于基准价每 1% 扣分、最高限价（可空）、异常低价线（低于基准价的百分比，可空）、基准价取法（固定值；竞争对手报价的平均值；去极值平均值，需填去掉的比例）、系数、平均值法是否计入己方报价。
- 竞争对手报价估计：逐行填写，或批量粘贴（按换行、逗号、制表符分隔，无法解析的行标红并指出行号）。最多 200 个。
- 候选报价：逐行填写，最多 20 个。
- 备注（至多 500 字）。

右侧试算结果：基准价；各候选报价的相对基准价偏差（%）、价格分、风险提示；价格分曲线（横轴报价、纵轴价格分，标出候选与基准价）；最优候选；换算句。

- 换算句固定写法：“报价每高于基准价 1%，失去 X 个价格分；约 Y% 的报价相当于 1 个技术分。”（Y 为 X 的倒数；高于基准价不扣分时只写前半句。）
- 风险提示用文字：“超过最高限价，将被否决”“低于异常低价线，有异常低价风险”。有风险的候选不会被选为最优；全部候选都有风险时在结果上方提示。
- 平均值法的基准价取决于其他投标人的报价，页面在结果上方固定说明“竞争对手报价只是估计，实际基准价以开标为准”。
- 没有竞争对手报价且基准价取平均值法时，不显示基准价，提示先填写估计。
- 试算在输入变化后短暂延迟调用 `POST /projects/{id}/price:simulate`，不保存；输入不合法时就地提示，不发请求。
- “保存方案”追加一个版本（`price_plans`），保存后显示“上次保存于……”并进入历史版本列表，可查看任一历史版本的输入与结果。
- 页面不涉及成本或利润，也没有这类输入项。
- 项目关闭报价模块时，页面只显示“本项目关闭了报价模块”的说明（报价由其他部门负责时可以关闭）和“去项目设置”按钮；已保存的方案保留，重新开启后照常显示。

### 3.7 提交与结果

同一页两个标签页：登记提交、登记结果。

- **登记提交**：表单字段为提交的正文版本、提交时间（必须带时区且不晚于当前）、回执文件（可空）。表单上方是登记前检查清单，逐项列出条件：废标／否决／强制类规则未确认的条数；未处理的关键问题和废标／强制响应类问题的条数；评审覆盖不完整；评审输入已过期；正文不是最新版本。未通过的每一项都给出处理入口（“处理问题”“去依据页”“回到报告”）；全部通过后才出现登记表单，提交时间默认填好当前时间。还有未结案的其他问题时，须勾选“已知晓”才能登记。提交时仍以接口返回的错误码为准（如 `qualification_rules_unconfirmed`、`critical_findings_open`、`diagnosis_incomplete`、`snapshot_stale`），错误信息就地显示并链接到对应页面。“无法判断”的判定不阻断闸门，但在报告“下一步”里提示核对。项目开启“规则按原文接受”时，闸门清单中“废标／否决／强制类规则已全部确认”一项视为满足，并注明“按原文接受（项目设置）”；其余各项不变。
- **登记结果**：先选择对应的提交；来源（用户报送或官方）、目标（技术分、综合分、无分数）、分值与满分（十进制校验，满分必须大于 0 且分值不超过满分，未知选“无分数”并说明）、聚合办法、阶段结果（待定、技术标入围、未入围、被否决、候选人、中标、未中标、取消、流标）、公布时间、官方原件与页码。官方来源的结果可以核实（需要官方原件、页码、聚合办法与理由）。更正以新记录指向旧记录，历史记录始终可查。候选人不是中标，分别统计。
- 登记结果后页面提示“结果会用来校准预测”，并显示当前校准状态。项目关闭“提示登记开标结果”时，报告不提示登记，本标签页照常可用。

### 3.8 度量

只呈现与中标有关的数据，不含过程类指标。图表用 Recharts 绘制，图表库只在报价与度量页按需加载；每张图都有完整的文字描述，同样的数字也出现在表格或正文里。还没有登记过提交时说明数字从哪里来，不画空图表；比率无分母时显示“暂无”，不用 0 代替。

- 结果：提交数、已出结果数、入围、不入围、被否决、中标、未中标，入围率与中标率。已出结果不足时写“样本不足，仅供参考”，不画趋势线。
- 废标／否决风险闭环：评审发现数、提交前已解决或驳回数、提交时仍未处理数、招标方实际否决数。
- 预测校准：状态（未校准、样本不足 x/20、已校准），已校准时显示平均绝对误差与平均偏差（按满分折算为百分制）。
- 逐轮变化：每个项目逐轮的预测得分估计、未处理问题数、已解决问题数、未处理的废标／强制类问题数，以及实际技术分（如已登记）。用折线图和表格并列，表格是图的文字等价物。

### 3.9 设置（项目信息与功能开关）

设置页有两块：项目信息与功能开关，各自保存。项目信息只提交改动的字段，名称必填，清空的选填项记为空。

**功能开关**位于项目信息下方，标题下一句说明：“只用需要的部分。废标／否决检测与证据溯源是核心，没有开关；其余模块可以按项目关闭。”七个开关按下表顺序排列，每行是一个开关控件、开关名称和一行说明（说明通过 `aria-describedby` 与开关关联）：

| 开关 | 默认 | 说明文案 |
| --- | --- | --- |
| 资料齐了自动开始评审 | 开 | 关闭后资料照常解析，评审等你在报告页点“开始评审”，避免资料没传完就开始 |
| 规则按原文接受 | 关 | 开启后，未人工确认的废标／否决／强制类规则按提取的原文接受，不阻止登记提交。把关强度降低，适合非常熟悉的标段 |
| 前后矛盾检测 | 开 | 同一个量在正文不同位置取值不同、大段重复。关闭后报告不出现这一类 |
| 范围残留检测 | 开 | 正文出现招标文件里没有的工程对象，多为套用其他项目模板。关闭后报告不出现这一类 |
| 显示预测分数 | 开 | 关闭后报告只列可能的失分点，不显示分数估计与区间（预测照常进行） |
| 报价模块 | 开 | 报价由其他部门负责时可以关闭，导航和报告里不出现报价 |
| 提示登记开标结果 | 开 | 开标结果用来校准预测；关闭后提交后不提示登记 |

- 拨动开关只改本地草稿；下方显示“将修改：……”列出改动的开关，没有改动时写“开关没有改动。”，“保存开关”和“放弃修改”在有改动时才可用。
- “保存开关”一次提交全部七个开关（`PATCH /projects/{id}`，`settings` 整体替换，带当前项目版本号）。保存中开关与按钮禁用；成功后提示“功能开关已保存”，导航与报告随即按新取值呈现；失败时显示“功能开关未保存”与原因，草稿保留。项目已被他人修改（412）时显示错误原因，重新进入设置页取得最新版本后再保存（设置页每次打开都会重新读取项目）。
- 开关改动写入审计；修改检测开关不会重新评审，页面不需要额外提示。重新打开“资料齐了自动开始评审”时，资料已就绪而等待开始的项目立即开始评审，横幅随即进入进行中。资料、规则或事实在最近一轮之后有变化时，项目状态不会停留在“可登记提交”，报告“下一步”也不出现“登记提交”。

## 4. 流水线横幅

数据来自 `GET /projects/{id}/pipeline`，以步骤条位于报告页与资料页顶部。四步依次为：资料、规则、核对、预测。每步状态为等待（`waiting`）、进行中（`running`）、完成（`done`）、失败（`failed`），用图标、文字和颜色同时表达。

| 情形 | 表现 |
| --- | --- |
| 资料不齐（`missing` 非空） | “还缺招标文件”或“还缺技术标正文”，链接到资料页；其余步骤为等待 |
| 等待开始（`stage=waiting_start`，项目关闭了自动开始评审） | 醒目样式的横幅：没有评审时写“资料已就绪，等待开始评审”，已有评审时写“资料有更新，等待开始新一轮评审”并列出 `stale_reasons`；说明本项目设置为手动开始评审、可以在项目设置里切换回自动，以及开始后系统会依次提取规则、核对并预测得分；给出“开始评审”按钮。资料步骤为完成，规则、核对、预测为等待 |
| 进行中 | 当前步骤显示进行中并带“预计完成后报告会自动更新”；其余未开始的步骤为等待；区域为 `aria-live="polite"`，状态变化被朗读 |
| 全部完成 | 收起为一行“第 N 轮评审已完成”，可展开查看各步 |
| 某步失败 | 失败步骤标红，显示失败原因（解析失败的文件名、规则提取失败的原因等）和“重新评审”按钮；已完成的步骤保持完成，重新评审只重试失败的环节 |
| `stale_reasons` 非空 | 提示“资料／规则／事实有更新，重新评审”，具体写明原因（正文已更新、招标文件或补遗已更新、规则已更正、事实已更新），并给出“重新评审”按钮；不自动开新一轮的原因（规则或事实更正）要说明由人决定时机 |
| 没有失败也没有更新 | 不显示“重新评审”按钮 |

“重新评审”与“开始评审”调用同一个接口 `POST /projects/{id}/analysis`，带幂等键；点击后按钮进入加载态，横幅回到进行中。

## 5. 评分预测的校准状态

预测不是对结果的承诺，界面必须一直如实表达分数从哪里来：

- 预测数字（估计值、区间、失分点）出现的每个位置（项目总览、报告结论卡片、预测面板、导出的 Word 报告）都写明校准状态，标签是文字，不用图标代替，不只靠颜色：
  - **已校准**（`validated_in_scope`，绿色标签）：分数由验收通过的打分模型给出。区间写“约 80% 把握在 a–b 分之间 · 技术标满分 M 分”，下方写“打分模型用 n 组官方成绩训练与评估，平均绝对误差 m 分（满分百分制）；适用：工程类型与地区”。
  - **未校准**（`not_validated`，琥珀色标签）：没有生效的打分模型，分数是逐项评估的合计，同时显示接口返回的 `reason` 原文；评分条款满分之和小于技术分满分时写明覆盖程度（如“只覆盖 8 / 60 分”）。
  - **超出校准范围**（`out_of_scope`，琥珀色标签）：有模型但本项目的工程类型或地区不在其适用范围内，显示逐项合计与不适用的原因。
- 在线对照（预测与登记的官方成绩）的写法，作为监控信息显示在预测面板下方：
  - 0 组：“还没有官方成绩可以对照……”
  - 1 至 19 组：“已有 x 组官方成绩对照，攒到 20 组才能给出误差……”
  - 20 组及以上：“上线以来已有 n 组预测与官方技术分的对照：平均绝对误差 m 分（百分制），平均偏差 b 分。”
- 区间条形图以满分为全长，估计值用标记线，区间用带底纹的区段；条形图的读屏描述与旁边的文字写出相同数值。
- 不使用“预计得分”“保证”“必得”“提分成功”之类措辞；使用“估计”“可能的失分点”。
- 预测状态为弃权（`abstained`，评分条款没有提取到分值）时，显示 `reason`，不显示数值，也不画空的区间条。
- 区间包含“该项评估失败，按 0 到满分全幅计入”的条款时，在失分点列表中对应条目写明“该项评估失败”。
- 项目关闭“显示预测分数”时，任何位置都不出现分数估计、区间与估计失分，只列可能的失分点（第 3.3.2 节）。

## 6. 状态、空态与错误

| 状态 | 页面表达及恢复动作 |
| --- | --- |
| 没有项目 | “新建项目”入口，不显示虚构统计 |
| 资料待补充 | 报告页显示缺少的资料和上传入口；其他页面照常可读 |
| 待开始评审 | 报告页显示“资料已就绪，等待开始评审”与“开始评审”按钮 |
| 模块已关闭 | 关闭的模块不出现在导航、报告和“下一步”中；直接打开报价页时说明“本项目关闭了报价模块”并链接到设置 |
| 评审中 | 报告页显示流水线进度；问题、依据页可以浏览已有内容，提示“评审完成后会更新” |
| 评审中断 | 显示失败环节与原因，“重新评审”；已完成的环节不重做 |
| 没有问题 | 分类标签上显示 0；报告写“未发现”并注明依据状态（规则 N 条，其中 M 条未确认），不写“无风险” |
| 没有评分条款分值 | 预测弃权，显示原因 |
| 没有报价方案 | 报告结论卡片的报价一项显示“还没填报价”入口 |
| 没有官方成绩 | 度量中校准显示“未校准”，不显示误差 |
| 模型输出不可用 | 对应判定为“检查失败”；覆盖度不完整的提示在报告与问题页同时出现 |
| 原件或存储不可用 | 证据无法打开时提示稍后重试，不把无法打开解释为没有问题 |
| 项目不存在 | 接口返回 404，页面显示“找不到这个项目”与“地址可能有误，或项目已被删除。” |

接口错误统一显示在触发操作的位置，附请求编号便于联系维护人员；保存成功、失败等结果另以页面角落的短提示告知。

| HTTP | 处理 |
| --- | --- |
| 401 | 跳转登录，登录后回到原页面 |
| 403 | `csrf_failed`：刷新页面后重试 |
| 404 | 对象不存在；`report_not_ready` 显示流水线进度或上传引导 |
| 409 | 显示冲突原因并链接到对应页面（提交闸门、输入过期、状态不允许的流转等），保留用户输入 |
| 412／428 | 对象已被他人修改：提示刷新并显示最新版本，保留用户输入的理由；缺前置条件视为程序错误并给出通用提示 |
| 422 | 就地显示字段级原因，不静默修正数值 |
| 429／503 | 提示稍后重试，已有内容保留 |

长任务（解析、规则提取、核对、预测、改稿建议）通过任务事件流（SSE）更新进度；浏览器关闭后重新打开，流水线横幅从服务端状态恢复，不依赖浏览器存储。

## 7. 视觉与组件规范

视觉方向为公司内部的审阅工作台：中性灰底、单一强调色，信息靠排版与细线分层，不靠色块与阴影。没有真实业务基线时保持任务界面，不用虚构趋势填满看板。界面由 Tailwind CSS v4 与 Radix UI 基础组件搭建，组件层在前端自行维护（`components/ui`），令牌集中在 `styles/index.css`；图标使用 lucide，随前端打包，无远程图标请求。

| 项目 | 规范 |
| --- | --- |
| 主题 | 浅色与深色两套各自调好的取值，默认跟随系统，可在用户菜单或命令面板里切换为浅色、深色或跟随系统 |

## 8. 响应式与可访问性

- 键盘可达：所有动作可用键盘完成；响应矩阵、问题列表、报价输入区的 Tab 顺序与视觉顺序一致；焦点始终可见。
- 状态不只靠颜色：判定、问题状态、流水线步骤、风险提示均有文字，必要时配图标。
- 对比度达标：浅色与深色两套令牌的前景与背景对比度按第 7 节核对，其他样式沿用令牌，不另取色值。
- 图标按钮带 `aria-label`；图表带完整的文字描述。
- 表单：标签与控件关联，错误信息与控件通过 `aria-describedby` 关联，必填项在标签里写明。
- 动态更新：流水线进度、保存结果、试算结果区使用 `aria-live` 通知，不打断当前输入。
- 文本放大到 200% 后保留阅读顺序与操作。
- 移动端宽度可用：1024px 以下侧栏收为顶部菜单栏；数据表在窄屏变为逐行卡片，整页没有横向滚动；问题详情的“招标文件要求”与“施组正文写法”上下排列；报价页输入与结果上下排列；手机以阅读报告、查看证据、处理问题和登记结果为主，长正文编辑转电脑完成。
- 已完成的核对是代表性桌面与手机布局、键盘任务和对比度计算；完整屏幕阅读器、触屏长文、真实 PDF 坐标与旋转缩放和真实使用依赖真实环境，尚未验证，不能声称通过完整的无障碍认证。

## 9. 评审方式与交接

设计稿用浏览器直接打开 `index.html`，不需要构建依赖，页面均为虚构数据，不是已部署的网站；随系统外观显示浅色或深色。建议评审顺序：项目总览 → 报告 → 流水线状态 → 问题 → 依据 → 报价 → 提交与结果 → 度量 → 资料 → 设置；最后在流水线状态页核对资料待补充、等待开始、报告尚未生成等空态的提示与跳转。

正式实现见 [tender-app/frontend](https://github.com/zys743551828-art/tender-app/tree/main/frontend)。页面字段、枚举和错误码以[接口契约](系统架构与数据契约.md#11-接口认证与错误)为准；设计稿与实现不一致时，以本规范和接口契约为准，反馈修改本文件与设计稿，不建立并列的另一份规范。
