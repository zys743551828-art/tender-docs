# 部署与交付手册

这里提供从空环境启动的基础设施、建库、配置和交付步骤。[compose.yaml](deploy/compose.yaml)只启动PG＋pgvector与Kafka，当前没有业务API／web／worker镜像，不能把基础设施健康当作产品完成。所有命令在专用开发环境执行。

## 1. 开发环境启动

准备Docker与Compose，至少预留4 vCPU、6GB内存和20GB磁盘。实际OCR、Embedding和reranker另外占资源；基础设施预算不是整套系统预算。镜像固定到已取得digest，版本身份写入机制检查记录。

在deploy目录复制`.env.example`为本地`.env`，填独立开发口令，不提交Git。运行：

~~~sh
docker compose --env-file .env up -d
docker compose ps
~~~

确认PG与Kafka healthy后，在deploy目录依次执行：

~~~sh
for script in core.sql domain.sql retrieval.sql worker-functions.sql roles.sql; do
  docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U tender_owner -d tender < "../$script" || exit 1
done
~~~

初始化是空库一次性脚本，重复执行应明确失败而不是吞掉已存在对象。开发重建只能对确认没有真实资料的专用环境进行；有真实资料时先备份，按结构升级流程处理，不能运行清库快捷命令。

宿主API开发连接PG localhost:55438、Kafka localhost:19092；Compose内进程用postgres:5432、kafka:9092。不要把Kafka宿主advertised地址用于容器内客户端。发布端口只绑定127.0.0.1；这里的Kafka明文与单节点仅用于开发，生产另配TLS／SASL／ACL和三节点容灾。

在deploy目录创建独立工具环境并初始化topic：

~~~sh
python -m venv .venv
.venv/bin/python -m pip install -r ../../../04-验证与测试/implementation-design-checks/requirements.lock.txt
.venv/bin/python init_topics.py --bootstrap localhost:19092
~~~

topic初始化使用[init_topics.py](deploy/init_topics.py)，读取执行策略，默认6分区、开发副本1／minISR1；生产必须显式传副本3／minISR2并使用相应受保护管理身份。脚本遇到已有topic会核对分区与关键配置，不静默宣布不匹配配置成功。

## 2. 业务服务配置契约

| 配置 | 消费者 | 校验与默认行为 |
| --- | --- | --- |
| COMPANY_PROFILE_MANIFEST | CreateBid | 部署时配置公司主体；项目首次使用只填名称，后台独立建工程与轮次 |
| APP_ORIGIN、SESSION_SECRET、CSRF_SECRET | API | 启动必填；不同环境独立；HTTPS生产Cookie Secure |
| API_DATABASE_DSN、WORKER_DATABASE_DSN、RESEARCH_WORKER_DATABASE_DSN、SCORE_READ_DATABASE_DSN | 各用途连接池 | 分别绑定能力角色；不得使用初始化owner／superuser；启动检验角色与schema |
| KAFKA_BOOTSTRAP_SERVERS、SECURITY_PROTOCOL | producer／consumer | 生产只接受配置的TLS／SASL路线；不向浏览器下发 |
| KAFKA_SASL_MECHANISM、KAFKA_USERNAME、KAFKA_PASSWORD、KAFKA_CA_FILE | Kafka连接 | 依环境选择；日志只打配置名与错误码 |
| OBJECT_STORE_BACKEND、BUCKET、REGION、ENDPOINT | 上传、原件与报告 | backend明确oss或s3，拒绝任意URL；原件私有；有真实读写探针才ready |
| OBJECT_STORE_ACCESS_KEY／SECRET等 | 对象存储SDK | 由密钥服务或工作负载身份注入；无凭据则明确未配置 |
| EMBEDDING_PROFILE_MANIFEST、RERANK_PROFILE_MANIFEST | RAG服务 | 权重digest、1024维、tokenizer、归一化、距离、资源；未配置索引状态不可用 |
| GENERATE_PROFILE_MANIFEST、JUDGE_PROFILE_MANIFEST | 模型适配器 | provider、model、API能力、提示digest、上下文预算、价格配置；评分固定方法不得静默替换 |
| DOCX_TEMPLATE_MANIFEST、FONTSET_MANIFEST、RENDERER_IMAGE | 构建服务 | 摘要与字体清单必填；无配置不能返回空Word／PDF冒充成功 |
| MAX_UPLOAD_BYTES、MAX_PAGES、REQUEST_BUDGET | 各入口 | 起始100MiB／1000页是防护配置，真实资料压测后调整；超限返回可理解错误 |
| LOG_LEVEL、AUDIT_RETENTION、TRACE_RAW_CONTENT | 观测 | 正文tracing默认关闭；不删正式审计以满足短期日志保留 |

Profile manifest至少含logical_name、provider／local_runner、immutable_model_id、artifact_sha256、capabilities、input_limits、timeout、pricing_basis和method_digest。模型供应商、对象存储地域、公司主体和真实资产摘要是部署参数，需要真实环境提供；领域ID、失败规则和任务协议不再留待环境决定。

开发可用本地S3兼容适配做协议检查，但正式OSS必须跑自己的分片、checksum、签名、条件写、版本保护与中文文件名验收。模拟接口不提高已验证范围。

## 3. 进程、健康与资源

| 部署进程 | 入口责任 | ready条件 |
| --- | --- | --- |
| web | 静态资源与项目路由 | 资源可加载，API origin正确，刷新深链接可返回SPA |
| API | 会话、查询、人工命令、SSE | schema就绪、用途角色正确、必要配置完整，关键依赖错误可解释 |
| outbox-relay | claim→publish→ack，续租 | Kafka可确认、PG可读写、无长期过期claim积压 |
| document-worker | 原件校验、解析、OCR、索引 | 所需解析资产可读、对象存储可用、独立临时目录 |
| review-worker | 核心核对、章节包与模型判断 | handler兼容、模型profile有效、评分只读角色隔离 |
| export-worker | DOCX／PDF与报告副本 | 模板、字体与受控渲染器已校验 |
| research-worker | 受控manifest训练与评价 | 仅取得已准入导出、环境锁和资源额度 |
| reconciler／scheduler | 失联接管、取消收尾、到期计划 | 单批上限与锁序正确，PG时钟判定，到期触发收据唯一 |

API先2进程、每进程PG池5；文档2并发，导出1并发，最多2轮在线评审、每轮4个模型在途；这些值来自设计预算，须负载试验确认。Embedding／rerank独立服务或内网端点，不与API进程争抢模型内存。CPU模式可用于机制验证但不承诺交互时延。

SIGTERM先停止新领取，保持poll与心跳处理在途；在优雅期限内提交或可靠交给PG重试，然后退出。超过期限由lease与fence恢复，不能仅为快速退出先提交Kafka位点。部署前查询未支持handler_version任务，保留旧处理器或明确取消后重新受理。

## 4. 监控、告警与处理动作

| 信号 | 起始告警条件 | 处置 |
| --- | --- | --- |
| 最老未发布Outbox | >60秒警告，>300秒告警 | 查Kafka连接／认证、claim续租和delivery失败，不清空Outbox |
| Kafka consumer lag | 连续增长5分钟，或处理最老任务>10分钟 | 查worker池、配额、失联与分区阻塞；按路线扩容，不随机新增group |
| Step heartbeat | lease过期120秒 | 对账接管并提升fence；检查OOM／外部超时，不手动重复正式决定 |
| 模型失败／预算 | 15分钟失败率>20%，单操作达到预算 | 暂停新增付费调用，保留失败与人工继续入口 |
| 来源／索引不一致 | 原件已verified但预期chunk缺失 | 重投明确parse/profile的索引任务，不创建新原件 |
| PG容量与备份 | 磁盘>75%预警；WAL归档中断 | 扩容／修复归档并验证恢复链，不能清理正式原件缓解 |
| 对象缺失／checksum不符 | 任一正式引用缺失立即告警 | 停止相关提交／下载，按manifest恢复，不用空文件替代 |

阈值是起始运行配置，须结合真实耗时调整。审计、日志与trace关联request／command／operation／step／model_call，不记录口令、签名URL查询串或原件全文。操作面板是运维能力，不能把处理速度当中标效果。

## 5. 备份恢复步骤

1. 从第一批真实材料起启用PG基线备份与WAL归档、对象原件版本保护和跨故障域备份；保存manifest及digest。
2. 恢复演练使用独立环境，暂停自动派发、消费者和写入口，先选定PG恢复点。
3. 恢复数据库，按被引用对象清单恢复字节并校验摘要，检查方法、模型、模板和字体资产。
4. 核对Kafka位点与PG收据；恢复点之后的消息不可直接跳过。旧worker停用、旧fence废止，补发缺失Outbox而不重做已确认业务决定。
5. 重建派生向量索引，核验至少一个实交稿、评审输入、知识来源链、官方成绩与模型路由。
6. 验证只读页、上传、后台任务与标准gate，再由运行负责人恢复流量。记录实际RPO／RTO与缺失项；目标15分钟／4小时未经演练不得称已达到。

## 6. 实施工单与依赖

每张工单都要有接口、真实持久化、页面或可运行入口、失败码及可复现验收。无真实数据的任务使用明确合成夹具，不能产出产品绿色资格。

| 工单 | 交付物 | 验收证据与前置 |
| --- | --- | --- |
| T0-01 建库与身份 | 初始化SQL、能力角色、登录与成员、CreateBid默认身份 | 空库初始化成功，评分账号不能读成绩；不要求用户先建工程档案 |
| T0-02 命令与操作 | ETag、幂等、操作查询、审计与SSE | 同键重放、不同内容冲突、旧revision拒绝、断线续传 |
| T0-03 Kafka执行 | relay、consumer、阶段计划、fence、重试与取消 | 提交后offset丢失、再均衡、worker kill、重复消息、过预算死信 |
| A1-01 资料与证据 | 分片上传、批次、解析、页与块、原件抽屉 | 扫描／表格／补遗失败不冒充完整，部分批次可明确接收 |
| A1-02 核心评审 | 规则与事实、响应矩阵、风险与主要下一步 | 全部规则左连接，无法判断独立，关键问题阻断gate |
| A1-03 实交结果 | 标准提交、线下补录、官方结果、更正与核验 | 同名不同稿拒绝，错传可如实补录，成绩未知与零分分开 |
| RAG-01 索引检索 | chunk/profile、Embedding、FTS／向量、RRF、引用与失效 | SQL过滤与权限先过，再用真实标注验检索质量 |
| C-01 评分判断 | 完整章节包、三次独立判断、调用预算与证据核验 | 超长分包覆盖、错误档位、伪引文、失败replicate与标签隔离 |
| C-02 研究发布 | 准入、划分、Pipeline、独立评价与模型路由 | 分组时间与来源闭包、冻结协议、影子观察与回退；依赖真实成绩 |
| A2-01 章节编辑 | 目录、串行保存、冲突恢复、来源补丁与撤销 | 保存失败不能构建，停用来源应用失败，旧提案不能覆盖新稿 |
| A2-02 DOCX／PDF | 模板、快照、渲染、对应链、分格式状态 | 图表／目录／编号／暗标检查，Word外部编辑后结果不继承 |
| D-01 知识与任务 | 候选发布停用、来源影响、模板版本和计划 | 旧引用可还原，暂停不取消，错过计划合并与去重 |
| E-01 上线运行 | 容量、备份、恢复、告警、升级回退与成员试点 | 实际环境演练与试点记录，不用设计检查代替 |

T0后A1、RAG和受控评分研究可并行推进；完整知识库与章节编制不阻塞首次PDF评审。正式模型业务发布仍需自己的独立精度验收，A1上线不自动授予。

具体开工范围、开发顺序与未验证事项见[开发准入检查](../../04-验证与测试/development-readiness-checks/README.md)。A1-01落实D01—D02，A1-02落实D03—D04和D06，A1-03落实D05，C-01／C-02落实D09—D10；报价及业务复盘落实D07—D08。字段和事务引用[保留功能实现规约](保留功能实现规约.md)，不让研发根据旧代码补猜目标行为。

## 运行账号与准入边界

新工程根为`/workspace/tender-workbench`，参考仓库只读。生产与开发均为API、普通Worker、研究Worker、正式评分读取各建独立非owner LOGIN，分别继承roles.sql对应NOLOGIN角色；LOGIN不得继承初始化账号或其他能力角色。研究Worker用RESEARCH_WORKER_DATABASE_DSN，取得bid行锁仍走固定入口，不因42501改用owner。新库按五份SQL顺序创建，研究调用预算与model_calls必须使用同事务入口；文档机制检查不替代实际Kafka Worker链路。

T0合并需非owner合法acquire/finish与越权禁止同时验证；A1需bindings冲突恢复、四层覆盖与关闭检测后已知关键风险浏览器验收；DOCX失败提供就地补PDF并正确保留未核验对应关系。A1可用、评分研究可运行、正式模型已验收为独立交付状态，不能以其中一个代表全部P0业务通过。
