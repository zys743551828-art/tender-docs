## 2. 目标、分工与原则

本项目是公司内部长期使用的市政工程投标辅助系统，**目标是中标**，不是产出一份看起来合规的文档。项目不设对外 SaaS 盈利、软件销售、付费客户增长或市场份额目标，也不为这些目标建设功能。

系统面向整份投标标书，施工组织设计是技术部分中的一种内容。资格、商务、技术、报价及附件按项目招标要求组织；范围与当前单正文实现的差距见[一期方案](02-业务与产品/一期方案与验证计划.md#11-目标与优先级)，两路代码的取舍见[详细对照](00-项目管理/Codex分支对照与整份标书吸纳建议.md)。核心优先级为不被淘汰（废标／否决项、强制性要求）、技术分尽量高（按评分条款评估）、价格分与技术分合理换算（评标价规则）。据此，一期有两个并列的 P0：**废标／否决项检测**与**评分预测**；其余功能——响应矩阵、前后矛盾检测、范围残留检测、报价模拟、评审报告与导出、规则与事实、结果登记与校准——都是围绕这两件事的辅助。需求与优先级见[业务需求说明书](02-业务与产品/业务需求说明书.md#5-业务需求与优先级)。

系统以“上传即评审、报告为中心”的方式工作：项目资料齐了就自动评审，落地页是评审报告；规则确认后置、按需，只有废标／否决／强制类规则在登记提交前必须人工确认；资料更新自动开新一轮；提交前有闸门。流程见[一期方案第 2 节](02-业务与产品/一期方案与验证计划.md#2-产品流程)。

用户不一定愿意完整跟随这套流程，所以核心之外的模块都可以按项目关闭或跳过：自动开始评审、前后矛盾检测、范围残留检测、显示预测分数、报价模块、提示登记开标结果默认开启，可以关闭；“规则按原文接受”默认关闭，开启后未确认的废标／否决／强制类规则不阻止登记提交。废标／否决检测、响应矩阵、证据溯源和提交闸门是核心，没有开关。开关的行为与理由见[一期方案第 2.7 节](02-业务与产品/一期方案与验证计划.md#27-项目级功能开关)与[决策与依赖](00-项目管理/决策与依赖.md)（DEC-019—DEC-021）。

效果只用中标导向的度量评价：入围率与中标率、废标／否决风险的闭环、预测校准、整改动作与得分变化；口径唯一见[一期方案第 7 节](02-业务与产品/一期方案与验证计划.md#7-指标与验收口径)。系统不管投标人的内部成本，也不统计任何过程类指标。

一期聚焦市政工程，以道路、管网及综合市政验证。历史案例具备完整提交正文，得分有技术总分和综合总分两种口径，暂缺评分项明细，实际入库可用性见[案例库](https://github.com/zys743551828-art/tender-datasets/blob/main/README.md#数据可用性)。**数据是瓶颈**：评分预测的打分模型要用“完整提交正文＋技术分＋满分”的历史样本训练，第一批约 300 份，逐项得分与同场成绩能显著提高样本价值；模型评测通过并登记之前，预测标“未校准”，不给误差。

共同原则：

- 结论有来源，事实、假设、建议及未决信息区分清楚；每个问题和判定都能回到原文页。
- 失败不冒充通过：解析失败、模型输出不可用、覆盖不完整如实显示；“无法判断”不等于“满足”。
- 预测不夸大：大模型只做判断，分数的量尺来自官方成绩训练、评测通过的打分模型；始终写明是否已校准，未校准时带标签与原因，不当作对结果的承诺。
- 官方成绩、人工标注和模型判定分别保存；评分明细缺失时不编造分项或扣分归因。
- 没跑过的验证不写成已验证；模板、目录和计划不代表实现或效果已验证。
- 沿用既定技术栈，按业界通行方案实现；技术内容只在[系统架构与数据契约](05-技术与设计/系统架构与数据契约.md)维护。
- 需求、证据、设计、技术决定、测试与真实效果可追溯；评审使用的输入冻结，规则与结果的更正追加新记录，旧报告可还原。
