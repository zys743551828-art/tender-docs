## AR04：初始bootstrap角色的REASSIGN机制须先收敛（静态运行前提，未PG实证）

位置：[cluster.py:151](/workspace/tender-docs/04-验证与测试/application-recovery-development-checks/code-02/frozen-inputs/deploy/application_recovery/cluster.py:151) 将随机owner作为POSTGRES_USER，用它完成新cluster initdb；[第301—315行](/workspace/tender-docs/04-验证与测试/application-recovery-development-checks/code-02/frozen-inputs/deploy/application_recovery/cluster.py:301) 又直接REASSIGN OWNED BY该初始角色到NOLOGIN schema owner。目标restore重复此模式。

PostgreSQL初始bootstrap超级用户是系统pinned角色，不是普通可整体重分配的临时业务DDL角色。只枚举database/tablespace归属不能证明其系统依赖可REASSIGN；此路径存在在完成新资源/SQL后才被PG拒绝的运行阻塞。本轮只读代码，没有连接PG或执行该语句，不能表述为已经观察到真实错误，也不能用原Mock未知共享对象用例证明这个正向机制可执行。

建议在另候选明确：初始管理员仅负责新cluster基础设施；业务对象/扩展由独立非pinned临时DDL/restore角色创建，再有限重分配到最终NOLOGIN非super owner。若临时角色必须创建非trusted扩展，权限只在该全新自有cluster的初始化窗口使用，完成后撤销，不给予业务LOGIN；不能修改pg_catalog或给最终schema owner SUPERUSER。必须验证初始系统对象仍归基础设施角色，自有业务及extension owner正确，SECURITY DEFINER/ACL/default ACL完整一致；未知共享对象仍失败。具体实现由Owner收敛，不能在02实际失败后热改其他库“补通”。
