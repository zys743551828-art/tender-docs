# 团队运行故障排查

本页对应 2026-10-30 团队反馈。已按截图像素核实四类描述，并只在内存中脱敏对照附件变量；截图是诊断摘要，不是原始网络/Worker 日志。没有使用附件凭据，没有检查或修改实际 OSS CORS，没有实际模型请求。不要提交或转发 `.env`、密钥、原文及完整签名 URL。

## 先确认启动的是哪套系统

| 项目 | 当前主系统 | 历史来源系统 |
|---|---|---|
| 源码/入口 | `workbench/README.md`、`workbench/apps` | 根目录 `backend/`、`frontend/`、`deploy/compose.yml` |
| 存储 | `OBJECT_STORE_*`；OSS 使用原生 oss2 V4 适配器 | `BIDWB_STORAGE_*`；boto3 S3 兼容适配器 |
| Compose 注入 | 以 workbench 对应 profile 为准 | `OSS_ENDPOINT_URL` 等映射到 `BIDWB_STORAGE_*`，不是任意 OSS 别名 |
| 数据库 | PG17、独立 API/Worker 非 owner 身份 | 旧 PG16 契约；不能把旧库交给新系统初始化器 |
| 上传 | fusion-full 为同源代理 | 当前前端也是同源 API 转传，不要求浏览器直连桶 |

截图中的 `backend/src/bidwb`、`/api/v1/tasks/{id}/retry` 属于历史系统。当前主线保留它作为来源，不表示其部署方式与 workbench 兼容。诊断还缺同事实际启动命令/Compose 路径及运行 Git SHA（或镜像 revision）；不能由附件推断部署版本。只收集这两项及脱敏错误类别，不收集密钥。

根后端 `Settings` 使用 `BIDWB_` 前缀且 `env_file=None`：仅保存 `.env` 不会自动加载。必须由现有启动器、IDE 或 Compose 明确注入。不要把包含敏感值的文件直接写入命令历史。`OSS_URL`、`OSS_ACCESS_KEY_ID` 等通用别名不会自动成为 workbench 的 `OBJECT_STORE_*`。根 Settings 未注入签名项时默认 `s3v4`；根 Compose 则默认 `s3`，所以只看文件不能确定进程实际值。先确认实际环境变量名称及是否设置，不打印值。附件的 `BIDWB_LLM_MODEL=deepseek-chat` 是根后端配置，不能自动替代当前工作台冻结的 /3 profile；本轮没有验证外部型号能力，也不替用户换型号。

附件不是完整 Compose 模板：缺少 Compose 必填的 `OSS_ENDPOINT_URL` / `OSS_PUBLIC_ENDPOINT_URL`，只有对应 `BIDWB_STORAGE_*` 不会满足这两项插值；若只以该文件启动根 Compose，应先在配置校验阶段失败。根 Compose 的模型来源是 `LLM_BASE_URL` / `LLM_MODEL` 和已有 secret 文件，而不是任意 `DEEPSEEK_*` 或宿主机 `BIDWB_LLM_*` 自动透传。按已确认启动入口使用对应模板及已有安全注入方式，不把密钥另写进仓库或新建访问。

## 四类现象、代码证据与最小处理

1. **分片 PUT 全失败**：离线调用实际 boto3 签名器已证明，virtual 寻址加桶名端点会生成双桶名前缀；新守卫在签名前拒绝标准 OSS 的该错误组合，并避免误拒桶名恰为 `s3` 的合法地域端点。附件中的 `BIDWB_STORAGE_ENDPOINT_URL` 与 `BIDWB_STORAGE_PUBLIC_ENDPOINT_URL` 已是无桶名前缀的 S3 兼容地域端点，不能把截图旧配置当成附件现状。先检查运行版本和加载方式，再看浏览器请求实际去同源 API 还是桶域名。不要复制完整签名 URL 到日志。
2. **CORS**：截图声称桶缺 CORS，但没有实际云端验证。当前两套同源上传路径均不应靠开放桶 CORS 修复。仅当已确认使用旧版浏览器直传时，才由有权限的运维按实际站点 Origin、必要方法和 ETag 暴露配置最小规则；不自动放开 `*`，本轮未执行云端操作。
3. **解析 `dependency_unavailable`**：本地实际 SDK（botocore 1.43.114）的 before-send 拦截（在网络发送前停止）复现 SigV4 默认可选 checksum 产生 aws-chunked/trailer，SigV2 没有该现象。历史适配器显式使用 `when_required`，保留必要 checksum 与应用内容 SHA 校验，不更换签名版本。附件已配置 SigV2，因此不能认定其当前失败就是 trailer。Worker 现记录安全类别 `handler` / `artifact_store` / `result_commit`、异常类型、任务及尝试号；保持原重试语义，不记录异常正文、正文材料或 URL。根据该阶段区分解析依赖、产物写入和事务提交，不把全部归为 OCR 缺失。根后端基础文本解析使用 pypdfium2；可选本地识别由 `BIDWB_PARSE_ENRICHMENT_ENABLED`（默认 false）、`BIDWB_PARSE_MODEL_DIR` 等控制，附件未提供这些项。Dockerfile 安装 parsing/retrieval extras，但模型文件就绪仍需独立检查。纯扫描件和缺原文证据应按解析覆盖状态处理，不因设置 DeepSeek key 就获得 OCR 能力；本轮不启用识别或下载替代模型。
4. **`no_rules_extracted`**：当前根后端 prompt 已是 p4，明确要求 conditions/exceptions 为字符串数组，截图 p2→p3 修法不能直接套用。保留严格结构和逐字证据校验，不把字符串强制包装成“合格规则”。失败提示改为封闭分类计数（结构、字段、引用、逐字出处、重复等）；失败不等于原文无规则。核对已部署 prompt/模型输出结构和解析证据后，只重试失败规则任务，不重跑已成功解析，也不把候选数量当模型质量。

S3 兼容 boto3 地域端点与原生 oss2 地域端点不同，不要混用：[阿里云官方兼容说明](https://www.alibabacloud.com/help/en/oss/developer-reference/use-aws-sdks-to-access-oss)。`when_required` 只限制 SDK 的可选完整性操作：[AWS 完整性配置](https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html)。离线序列化通过不等于实际 OSS 已兼容或云端验收。
