# 应用恢复执行协议 01（待架构审查）

本文件是新增实现协议，尚未执行建库、对象复制或应用验收。它不替换 generic/native 的旧冻结证据，也不宣布 FR032 或生产恢复完成。项目是全新系统，历史资料新入库与本次档案恢复都不是旧系统迁移。

## 1. 阶段、文件所有权与精确输入

OPS Owner 独占新增 `deploy/application_recovery/*`、`tests/test_application_recovery*.py` 和本专属证据目录。既有 `deploy/backups/*`、fresh02、共享 API/Worker、其他 Owner SQL 和既有私有 profiles 不修改。

阶段依次是：协议静审；离线拒绝路径与清单实现；自有最新 schema 合成源；完整一致备份；独立新实例恢复；非owner登录/读取/新工作；冻结开发候选；独立 QA 实做。架构确认初始化/角色/队列边界后才执行资源创建。每阶段生成不可覆盖收据，失败保留，不按数据库名前缀猜测自己拥有资源。

`baseline-inputs.json` 已逐字节核对后端07固定根308文件、Word14SQL加 historical input C 共15份顺序 SQL。后端 manifest SHA256 为 `71fe0fb2c9dbde7d85e62d20bef2da8e188e59ac00e9eb056cc021a1bd75274e`。SQL 不从 live 路径执行，也不因07未带最新两个表而漏掉它们；Word执行代码未包含在07时，只证明其 schema/档案与引用恢复，不声称 Word intake/renderer 功能已恢复。后续组合新增生产源或 DDL 必须另冻输入/另fresh，不覆盖01。

## 2. 资源和权限：新独立PG集群，拒绝任何原地恢复

选择独立 PG17+pgvector 容器和全新 volume，避免在现有PG集群改全局角色/成员关系。镜像用 `deploy/compose.external.yaml` 固定的 digest，新增自有 compose 文件不改原件；loopback空闲端口由plan预先指定并探针，不复用55439/55441或现有broker端口。集群、volume、容器和数据库均含随机 recovery UUID，保存 Docker 实际ID、PG `system_identifier`、新库OID与新库UUID收据；只允许工具本次自己创建且身份一致的资源。容器名/前缀本身不构成恢复授权。起容器前发现同名资源或非空卷立即拒绝，不使用外部已有卷。源owner DSN不提供给恢复目标工具，源读取仅API受限只读。

独立新集群 bootstrap owner 使用全新随机口令，仅私有600文件持有；所有连接在首DDL前验证 `current_database/current_user` 和本次cluster身份。DSN复用fresh02的严格libpq身份规范化策略：拒query/fragment/多host；不得靠URL替换path声明目标。容器 `PGPASSWORD` 仅继承子进程环境，不进入argv/日志；私有配置不进入导出。

完整恢复前先审查源快照角色标签、ACL和对象owner：只接受固定能力组 `tender_api/tender_worker/tender_score_read/tender_research_read/tender_research_worker/tender_model_train/tender_model_evaluate/tender_model_score`，以及清单明确列出的源对象owner标签。全部在这个新集群建立为 **NOLOGIN、非super、无createdb/createrole/replication/bypassrls** 的角色；不恢复任何旧LOGIN口令、原LOGIN成员关系、cluster globals或外部连接。源owner标签仅用于保留对象归属和 SECURITY DEFINER 的权限关系，绝不继承源owner的super属性。若标签撞上本次bootstrap owner、PUBLIC以外未知ACL grantee、扩展owner不支持或角色依赖不闭合，预检失败，不自动放宽。

`pg_restore --exit-on-error --single-transaction` 在本次随机新库执行，保留原schema、函数定义、对象owner、ACL、column ACL和default ACL；不能用一轮 `GRANT ALL` 代替原权限。允许source owner标签在新集群存在，故无需字符串替换pg_dump SQL。恢复owner是本次新bootstrap账号，普通API/Worker不成为对象owner。扩展必须与清单版本/namespace一致。完整恢复后核 `pg_get_functiondef`、SECURITY DEFINER/search_path、trigger、constraint、index、type、sequence定义及ACL；ACL的owner身份标签可以保留，LOGIN替换只发生在新集群的角色成员绑定。

随后只在这个新集群创建全新随机受限业务LOGIN。新API仅加入 tender_api，新Worker仅加入 tender_worker；研究/训练/评估等分目的新LOGIN可验证后保持不交付runtime。记录各新LOGIN当前DB/user/flags/继承角色/非owner。撤销PUBLIC对目标DB的CONNECT；最小验收仅给API CONNECT，其余LOGIN不发给运行harness且不能CONNECT该目标库。API正向登录/工作与DDL、角色管理、owner SET ROLE负向都要真实验证；不能将 `default_transaction_read_only=on` 当权限隔离。

源SQL是来源和审查身份，不在已恢复schema上再次执行。15份SQL用于创建另外自有的“空白参考库”，比较已知schema的结构/权限口径；不会在已有源库或旧readonly恢复库跑补权DDL。完整归档额外schema照常保留，无法解释其角色/函数依赖则拒绝应用可用标记。

## 3. 同一快照、完整档案和引用闭包

新 snapshot 入口独立实现，复用冻结 generic 的纯目录/摘要/对象校验函数，不修改旧实现。以API LOGIN开 `REPEATABLE READ READ ONLY`、`pg_export_snapshot`；目录、每表摘要、引用清单、ACL/owner、typed blob FK关系和队列分类都在同一事务读；pg_dump以同API LOGIN `--snapshot`，保持快照事务直至完成。源保持在线，不停服，不用事务开始时间冒称单调业务时序。

档案是完整用户schema目录、dump、逐表行数及摘要、完整 `design.blobs` 精确key字节与SHA/尺寸；所有非系统schema均发现。原有模型artifact、模型response、chapter输入包、模板/方法原件及其审计/登记关系全部保留；依据实际FK目录列出 `blobs` 的直接及多跳引用，而非只认document_versions。API任何表不可读、RLS/FDW/外部依赖不受控、blob缺失或SHA不符立即失败。新增typed blob例：model_artifacts、模型响应证据、章节输入包、模板方法原件至少各一条自有样本，独立回读关系和值，不能仅用空表计数证明其正确性。

未正式登记的 uploads/provider multipart 暂存不通过桶LIST发现；从快照的登记key逐项分类为 `registered_complete` / `registered_staging_unqualified` / `provider_upload_pending` / `key_missing_or_unknown`。本片保证正式blob字节完整；暂存不完整则在收据中明确不能续传/不能恢复在途，不隐去丢失。未知providerID不重建远端init，不清理原用户对象。

全档案目录700、文件600、排除Git；报告只出数量/哈希/合成UUID，不出正文、口令、签名URL、nativeUploadId。数据中本来存有的session/credentials/调用审计等仍属于私有dump，公开报告不能枚举这些值。备份上限沿用当前开发工具，超过限制明确失败，不能称容量验证。

## 4. 对象恢复和外部资产

目标OSS locator必须原生HTTPS endpoint/bucket并使用 **OBJECT_STORE_PREFIX** 新随机前缀，与源locator精确不同。数据库逻辑object_key不改；按manifest映射将每个已登记对象PUT到新prefix，然后独立GET并逐项SHA/尺寸核验。只能读取源manifest的精确key，不能LIST桶/改CORS/生命周期/公共ACL；任何引用对象保留，不因验证结束删除。重复执行若receipt已确认同一target对象，只允许校验，不能覆盖为不同字节。

外部资产单独形成 `runtime-assets.json`：RAG CPU dense/reranker权重、tokenizer/config/sentencepiece每文件尺寸与SHA、上游revision（不是只有模型名）；Parser/OCR各模型字节；PDF renderer/Word renderer镜像ID/digest、sandbox profile公开身份、字体文件与fontconfig SHA、转换器/库版本；Python锁定依赖及实际安装版本。仅从已知配置声明的目录逐文件固定，不扫描任意主机目录，也不在线重新下载/执行remote code。大权重不计入2GiB业务blob上限：资产可由单独私有本地/持久化资产包或显式已存在只读挂载提供，但恢复时必须真正逐字节复核，缺失/变化为该能力 `unavailable`，不能默默使用另一版。

Word renderer源码当前固定image ID需单独匹配，不因宿主soffice存在认定可用；sandbox不可用时保留原件与原转换关系，明确转换能力pending。私有endpoint credential/session密钥/providerkey不导出。业务配置按允许字段重建，新的SESSION_SECRET/CSRF_SECRET/上传授权密钥随机生成；新SESSION_SECRET使旧cookie无效，原session行不重写。模型/OCR远端凭据默认不放入恢复runtime；没有模型调用资格，费用0。

## 5. 应用验收与来源不变

第一轮只恢复自有新源样本，源也由15份已审SQL在自己的新资源初始化；用API业务身份创建合成成员、项目、知识、报告/模型blob关系和队列边界样本，不能owner替业务建记录。正式报告/模型资格不伪造；必须标明合成结构样本。源合成成员口令单独600文件，既不导出在manifest，也不改写任何真实账号。对于外来档案没有合法口令时，真实登录验收为pending，不自动重置旧credential宣称成功。

所有目录/表/对象/hash/权限核验在任何应用写入前完成。启动固定07根的真实 ASGI app，外包仅本片恢复harness：路由白名单为health、真实auth login/me/logout、已指定合成项目/知识/报告的精确只读入口、create_bid及该新UUID的无后台副作用读取/修改。白名单之外的方法/路径先拒绝；不启动通用uvicorn公开端口、不启动lifespan外的后台runner/relay/consumer。白名单核到实际endpoint，任何GET有派发或重新生成副作用就不开放。新工作最低正例是原API真实登录（创建session/audit）→读取恢复的项目和知识/报告记录/精确原件→创建新的合成投标项目→带CSRF和幂等键保存一个无后台任务的项目字段→读回并重放，不以直接SQL INSERT替代。

新LOGIN无owner权限、原cookie无效、CSRF/Origin/幂等校验照原实现。验证写入仅为新session/audit/command和新合成项目；原历史记录按恢复前逐行身份摘要做子集差分，已有行不得被修改/删除。对原队列、model_calls和原真实history做精确前后摘要。源DB对本次合成源全量before/after摘要相等，源对象逐个GET字节相等；并发源的测试则比较既有不可变样本，不能把合法并发提交误报本工具污染。报告明确是哪一种情形。

## 6. Kafka与旧队列恢复边界

恢复epoch UUID记在私有恢复收据及每个新测试工作审计上下文，只作为本次演练身份，**不冒称已有Worker具备数据库级epoch fence**。最小runtime profile的 KAFKA_BOOTSTRAP_SERVERS 为空，且没有Worker/purpose DSN或模型key。恢复harness拒绝所有enqueue入口；原outbox（published/unpublished/leased）、operations/receipts、模型账本unknown/reserved状态保留且前后相同。不将published改成pending，不重置lease/generation，不自动reconcile，不重发未知费用。

如要验证队列基础设施，另建自有独立Kafka broker/clusterID/volume/空闲loopback端口（已有19095/19096/19097均不可复用），仅创建原固定topics，核0consumer groups/0消费。不要把该broker地址写进本片API恢复runtime；不启consumer。旧cluster/group/offset只记来源，不能移到新集群冒充原有投递位置。

该设计只证明“归档历史可读＋隔离新同步工作可写”，不证明原在途任务可续跑或全开放工作台。未来启用新异步工作前须由backend另片实现并审：数据库持久recovery epoch、outbox/claim/renew/publish同epoch fence、新操作与历史隔离、同费用调用幂等/unknown人工对账、迟到旧worker反例、只派发明确新epoch的事件。没有此钩子时禁止启动原relay/worker，shell环境变量不足以安全恢复旧队列。

## 7. 失败与恢复CLI契约（拟实现）

命令统一 `python -m deploy.application_recovery <command>`；公开参数只允许plan/归档路径/receipt路径，不接受任意target DSN或existing DB。私有base/credentials只能路径输入，不echo。

- `plan --baseline <json> --assets <json> --output <private-dir>`：无远端写，验证输入字节、角色/权限allowlist、资产、空间预算和目标计划；无秘密的public-plan可供审查。
- `snapshot --plan <private-plan>`：受限API同快照新档案；并发插入反例证实快照后提交不进dump/manifest；所有objects严格精确key。
- `restore --plan <private-plan> --archive <private-dir>`：先完整本地校验和源身份拒绝，再创建自己全新PG cluster/volume/DB/LOGIN/targetprefix；逐阶段不可覆盖receipt；失败不产runtime可用标记。
- `verify --receipt <private-receipt>`：先DB/用户/cluster/locator身份，再全目录/摘要/关系/对象/权限；只有全部符合才可进入app check。
- `application-check --receipt <private-receipt> --credential-file <private-file>`：仅固定根白名单ASGI，无模型/consumer，产明确分能力结果。
- `inspect-queues --receipt <private-receipt>`：只读状态分类/数量/摘要，不reset/replay。

任何目标复用都拒绝，工具失败后不自动DROP/删对象。重试根据自己创建resource-ID收据，仅允许从明确阶段续**校验**；不能重放未知CREATE/PUT/restore。阶段不明给安全失败收据，保留新资源给人工审查。清理如未来需要只接受精确本次resource IDs，单独显式命令且不列桶；本片默认保留全部已引用对象和恢复库。
