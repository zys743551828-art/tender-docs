# 助手未知费用下的独立新问题

产品决定：阻止未知调用的补发，不把一项未知调用变成整条会话永久停用。仅在服务器能够按下述受限条件区分独立意图时，允许用户明确发送新问题。原调用、原结果状态、未知费用和预算预留始终保留。

这是后续独立候选的产品协议。前端10的独立用户证据及前端11仅修长会话可达性的预期保持原样；本协议不表示新行为已经实现或通过。主PRD本轮不改：其重试、取消及费用约束仍适用；实施候选进入前由PM绑定本补充协议并安排影响范围复验。

## 服务端意图与判定

服务器冻结 `logical_intent_id`、`request_mode`、操作／用途、规范化完整问题、业务目标、完整来源上下文、原执行身份及预算。客户端不能选择意图摘要或宣称自己已经取得独立资格。

- `request_mode=retry/continue` 必须关联原意图，原调用 `reserved/unknown` 时拒绝再次收费。已完成动作卡的执行身份同样不能被新问题包装成第二次执行。
- `request_mode=new_question` 只表示用户明确提出新问题，尚不等于服务器认可独立性。服务器使用真实可读对象建立目标，不能接受自由填写的UUID、另建会话或新nonce作为独立性证明。
- 问题规范化只做确定性 Unicode NFKC、换行和空白归一、全半角等价符号；保留数字、单位、否定词和完整正文。不得截断为摘要后判重，也不能删除会改变含义的词。
- 除精确请求身份外，另有防补发关联键：规范化问题＋服务器业务目标＋已登记操作／用途。来源换版、历史消息、token上限、provider/model/profile、客户端消息ID和nonce变化不能独自解除原意图的锁。完整上下文仍逐件冻结，以便来源资格核验和审计，不能为规避判重伪装为原上下文。
- 同一受理范围的排队／运行请求返回原任务；原未知请求返回原账本和待核清状态。并发判定和预留须在同一服务端串行边界完成，API受理及Worker预留前各核一次，不能只靠按钮禁用。

首片只认可两类可审计的独立性：

| 条件 | 具体判断 |
| --- | --- |
| 不同实际业务目标 | 用户显式切换到另一个真实项目／标段轮次，或选择不同的已有规则、问题、章节等具体对象。服务器核对对象可读、真实身份和作用范围；同对象新修订、复制项目壳、仅换来源不是不同目标。项目身份不足、两个壳不能证明业务目标不同，则保守拒绝付费并保留输入。 |
| 同目标、不同登记用途 | 服务器支持的明确用途和作用对象均可校验，且该用途不属于原调用的重试、接续或同一动作效果。例如对具体否决问题“解释此问题”与对另一个明确章节“起草修改建议”具有不同目标／效果；只把问答改标为“解释”而没有可信对象或效果差异不合格。首片不允许用户任意改用途标签绕过同一问题。允许的用途组合由actual能力投影列出，未列出的组合按不能证明独立处理。 |

同一目标、同一用途，仅改写自然语言问题，首片不声称可以判断语义是否不同。即使用户确有不同问题，也先保留可编辑草稿，提示选择明确的新业务对象／用途，或等待原调用核清；不另发收费LLM分类。该保守限制须公开，不用相似度阈值、关键词黑名单或用户单独勾选“不是同问”宣称已经证明语义独立。后续可扩受控问题类型，仍需独立验收，不降低防补发边界。

`继续／重试／还有呢／同问` 等显式接续操作引用原意图，不能重新解释成独立目标。自然语言出现这些词不是唯一检测手段：原卡片、原任务和原意图引用以及效果身份的关系更优先；无法确定关系则不付费。新的只读问答不得自动执行其提到的业务动作。

## 实施缺口与开启条件

当前 `jobs.same_intent` 使用包含冻结context的意图，`global_runtime.reserve` 又按intent＋profile查未结调用；它们不等于本协议所需的跨来源修订／profile防补发关联键。现有 `max_tokens` 单次上限也不等于聚合预算。本协议要求后端补出持久原意图关联、防补发键和原Action效果身份检查，不能让前端先解除禁发。

聚合账本至少可核读：调用／原意图／成员／项目及全局预算桶身份、冻结金额或可计算的最坏上限与币种／计价版本、预留状态、实际usage／费用、核清与释放记录；预算配置须有明确限额／窗口／当前修订及缺配置行为。原调用无可信上限时不能用当前新价推一个更低数清掉原预留。具体实际API／字段形状由技术Owner形成新actual契约，独立QA必须核持久预留及并发扣额，不能只数按钮点击或检查token上限。

独立性或聚合预留能力尚未实现、未配置或未验收时，保留现有付费暂停，给可读的缺口原因和草稿编辑能力。前端11只收长会话可达性，新行为在后续前后端共同冻结的独立候选中启用；不得用本产品决定冒称当前服务端已经保障它。

## 预算和界面

旧未知调用按冻结的最坏上限继续预留，纳入相应成员、项目和全局预算；不能按零费用计算，也不能通过移会话、改项目或新意图清掉。新问题须在扣除所有未结预留后仍满足本次独立上限。服务端不能可靠获得旧上限或聚合余量时，先显示预算待核清并拒绝新的收费调用；只读原件、历史、草稿和非收费工作仍可使用。不能把本协议当作自动提高预算或重复付费授权。

常驻卡显示“此前这次请求的结果或费用尚未核清，未再次发送”，带原问题、范围、时间、状态及可用预算说明。编辑区始终可达且保留草稿；有可验证新目标／用途时显示“发送新问题”，同时显示“原请求仍待核清，本次单独计入预算”。这是一次明确发送，无第二次聊天确认。自动发送、普通重试和刷新均不能走该入口。

拒绝独立性时显示“暂不能确认这与待核清请求无关，输入已保留。请选择明确的新对象／用途，或等待原请求核清”；预算不足单独说明，不把两种失败混成无响应。原件、正式记录、旧产物和原未知账本不会因为新请求而变更。新回答不得以缺失的原答案为已知事实。

## 必须执行的增量验收

| ID | 输入／情境 | 期望 |
| --- | --- | --- |
| UNK-01 | 原问题unknown，普通重试、刷新、失ACK恢复 | 回读原任务／账本，零新预留、零新发送。 |
| UNK-02 | 原问题不变，仅换nonce、消息ID、会话、token、模型或来源修订 | 不取得独立资格；预算／来源变动不能洗掉unknown。 |
| UNK-03 | 同项目同问题的自然语言改写、泛化的“还有呢” | 首片不证明独立，保留草稿、提供明确目标／用途选择，零新付费；不能声称通用语义去重。 |
| UNK-04 | 同问明确改到另一真实且有据不同的工程标段轮次 | 服务端建新意图，仍扣原预留；新预算足够才发送一次。近名或复制壳不足以证明不同则拒绝。 |
| UNK-05 | 从原问题转到另一真实finding／section，明确支持的不同任务效果 | 核对象和效果身份后可建新意图；仅改标题或用途标签不合格。 |
| UNK-06 | 新问题仍引用原操作卡／未知结果要求继续执行 | 关联原意图拒绝补发，不因文本不同重复原Action效果。 |
| UNK-07 | 两个并发新问题各自看似预算足够、合计超额 | 聚合锁下最多放行合法预算，unknown上限持续占用，不出现负余量。 |
| UNK-08 | 新问题取消、失租或来源失效后旧调用迟到 | 实际usage照记，旧结果不成为当前有效答案；不回收尚未核清费用以开放新调用。 |
| UNK-09 | 原unknown核清为成功／失败／确认未发出 | 由可信服务端核清记录更新实际预算；保留原账本、引用链与更正审计，不能客户端清账。 |
| UNK-10 | 1440与390长会话恢复／切换／返回 | 输入可达、分范围草稿不串、原unknown常驻可查；独立新问题失败不清空输入，不改前端10／11原证据。 |

本片退出：冻结后端、前端actual能力及预算字段后，独立QA在显式Mock下观察预留与发送次数，独立用户角色复验可达性和新／旧意图区分。真实付费及供应商账单对账另行授权验证；本产品文档没有执行软件、浏览器或模型调用。
