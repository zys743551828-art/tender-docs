# 一期方案与验证计划

文档编号：PROD-001  
类型：一期 PRD 与验证计划

## 1. 目标与业务输入

### 1.1 目标与优先级

系统是公司内部使用的工程投标标书工作台，当前以市政工程验证，目标是**中标**。工作对象是整份投标文件，施工组织设计（下称施组）是技术部分中的一种内容。招标文件及补遗是依据；资格、商务、技术、报价及附件按项目要求组织，可以分册或合卷。核心价值按以下三项确定优先级：

| 顺序 | 要解决的问题 | 对应能力 |
| --- | --- | --- |
| 1 | 不被淘汰：废标项、否决项、强制性要求、实质性响应，一项违反整份作废，得分再高也没用 | 废标／否决项检测（P0） |
| 2 | 技术分尽量高：按评分条款逐条评估，找出最可能丢分的地方 | 评分预测（P0） |
| 3 | 价格分与技术分合理换算：评标价规则下不同报价的价格分，一个技术分约等于多少报价 | 报价模拟（辅助） |

**两个 P0 并列：废标／否决项检测与评分预测。** 响应矩阵、前后矛盾检测、范围残留检测、报价模拟、评审报告与导出、规则与事实（依据）、结果登记与校准都是围绕这两件事的辅助能力；项目与资料管理、自动评审流水线和项目级功能开关是承载它们的支撑能力。需求编号与优先级的完整清单见[第 4.1 节](#41-需求总表)，业务侧的来源与取舍见[业务需求说明书](业务需求说明书.md)。

范围与当前实现分别表达：已部署链路仍主要核对一份技术正文，尚无整套分册文件包的完整检查与提交身份。整份标书须补文件包、条款适用范围、缺件及跨册核对；单正文无风险不代表整份投标文件已通过。近期吸纳和架构边界见[Codex 分支详细对照](../00-项目管理/Codex分支对照与整份标书吸纳建议.md)。现有技术分预测的标签和验收资格保持，不将商务、价格或综合分混入技术分。

### 1.2 业务输入

以下是公司负责人对业务的陈述，随真实投标记录的积累逐项核实。

| 项目 | 已取得的信息 | 使用口径 |
| --- | --- | --- |
| 市政投标量 | 约 20 个项目／月 | 规划口径，不是核验后的月度统计；不外推市场规模 |
| 首要痛点 | 技术评分不稳定或无法入围 | 两个 P0 的来源；具体原因（废标、响应缺漏、针对性不足、工程矛盾、竞争排序）需要结果登记之后区分 |
| 当前中标基线 | 实际中标数量、中标率与未中标原因分布尚未取得 | 由系统的结果登记逐项目积累，不以月投标量推算中标率 |
| 历史样本形态 | 公司说明为不同项目的自家稿件及各自成绩，逐案例配对入库仍在核验 | 评分预测的校准按“已登记的官方技术分＋对应预测”配对计数，见[第 4.3 节](#43-评分预测p0) |

### 1.3 范围外

下列内容不做、不写、不度量：

- 投标人的内部成本。报价模拟只依据招标文件的评标价规则计算价格分，不涉及成本和利润。
- 自动编标、模板起草、交易平台代提交与代解密。正式签章、上传、解密和询标由公司责任人履行。
- 技术栈取舍的讨论：沿用既定技术栈，实现方式见[系统架构与数据契约](../05-技术与设计/系统架构与数据契约.md)。
- 端到端真实环境跑通与真实数据评测：依赖服务器与数据，尚未验证，见[第 9 节](#9-验证状态与数据依赖)。

## 2. 产品流程

本节描述当前单正文评审链路；整份标书的文件包与包级检查按[详细对照第 6 节](../00-项目管理/Codex分支对照与整份标书吸纳建议.md#6-目标结构与接入次序)接入，尚未实现的部分不算已交付。

### 2.1 端到端流程

```
创建项目 → 上传招标文件（含补遗）与技术标正文 → 自动评审 → 评审报告（落地页）
        → 处理问题 → 报价 → 登记提交 → 登记开标结果 → 校准
```

流程的设计原则是摩擦最小：人只做三类事——上传资料、处理报告里的问题、登记提交与开标结果。解析、提取规则、冻结输入、逐条核对、评分预测都由系统自动衔接，界面上没有“提取规则”“冻结”“开始诊断”这类需要人去点的步骤，也没有“下一步”按钮。唯一可选的人工步骤是“开始评审”：项目关闭“资料齐了自动开始评审”时，资料照常解析，评审等人点“开始评审”（第 2.7 节）。

### 2.2 上传即评审

资料齐了就开始：项目里至少有一份招标文件和一份技术标正文（补遗可有可无）。系统依次完成四个环节，报告顶部的流水线横幅逐项显示 `waiting`（等待）、`running`（进行中）、`done`（完成）、`failed`（失败）：

| 环节 | 关键字 | 做什么 |
| --- | --- | --- |
| 资料 | `materials` | 解析招标文件、补遗与正文；招标文件和补遗各取最新版本，正文取最近上传的正文的最新版本 |
| 规则 | `rules` | 从招标文件及补遗提取规则，性质分为废标／否决、强制、评分、建议、例外五类 |
| 核对 | `review` | 冻结本轮评审的输入（对象名 snapshot，界面写作“本轮评审的输入”）；逐条规则核对正文，生成响应矩阵判定与问题；同一任务内运行前后矛盾与范围残留两项确定性检测 |
| 预测 | `prediction` | 逐条评估带分值的评分条款，汇总成技术标得分估计与区间 |

推进的性质：

- 推进是幂等的：每个环节的任务带确定的幂等键，重复触发（上传完成、任一任务成功、规则或事实变化、定时回收器兜底）不会产生重复任务或重复的输入冻结。消息或回调丢失时，回收器会把仍处于评审中的项目再推一步，不会卡住。
- 失败如实显示：某份资料解析失败，横幅指出是哪份文件并提示重新上传；任一环节失败，项目进入“评审中断”（`analysis_failed`），出现“重新评审”按钮（`POST /projects/{id}/analysis`）。重新评审只重试失败的环节，已完成的环节不重做。解析失败、模型输出不可用都不会被显示成“未发现问题”：对应规则的判定是“检查失败”，覆盖度标为不完整。
- 同一项目的推进串行执行，同样的输入不会产生两个相同的评审轮次。
- 项目关闭“资料齐了自动开始评审”（`auto_start`）时，资料环节照常解析（解析不调用模型）；规则、核对、预测三个环节等人点“开始评审”。项目还没有任何一轮评审时，状态为“待开始评审”（`ready_to_analyze`），横幅的阶段为 `waiting_start`；已有评审、资料又有更新时，报告继续展示上一轮，横幅与“下一步”提示开始新一轮。

### 2.3 规则确认后置且按需

规则未确认也照常评审，报告里标明“依据未确认”。参与评审的规则是人工确认过的规则，加上还没有人看过的规则；被驳回或暂缓的规则不参与评审。

| 规则性质 | 是否必须确认 | 说明 |
| --- | --- | --- |
| 废标／否决（`disqualification`）、强制（`mandatory`） | 登记提交前必须人工确认或驳回 | 这两类决定能否入围，未确认时评审按提取的原文判断，结论标“依据未确认” |
| 评分（`scoring`）、建议（`recommendation`）、例外（`exception`） | 不强制 | 可以随时确认，不影响登记提交 |

确认动作对规则包的影响：

- 把一条尚无人审核的规则确认下来，或重复确认，没有改变参与评审的规则集合，直接追加审核记录，不产生新规则包。
- 驳回、暂缓，或把被驳回的规则又确认，会改变参与评审的规则集合。而评审引用的规则包永不改变（旧一轮结果必须能复现），所以系统把规则包复制成新的一份，更正落在新包上，并提示“规则已更正，建议重新评审”，由人决定何时重新评审。
- 招标文件或补遗更新后重新提取规则时，系统对上一版规则包里人工已决定的规则，按“性质＋条文”匹配，沿用其决定（审核理由前缀为“沿用自上一版规则集：”），避免重复劳动。
- 项目开启“规则按原文接受”（`accept_rules_as_written`）时，废标／否决／强制类规则在登记提交前不必确认，报告不催确认；规则依据仍如实记为未确认，确认动作照常可用（第 2.7 节）。

### 2.4 资料更新自动开新一轮

上传新版招标文件、补遗或正文后，系统自动基于最新资料开新一轮评审，包括重新提取规则（招标文件或补遗变化时）、重新冻结输入、重新核对和重新预测。旧一轮的问题、判定、预测和审核记录保持不变，可以回看。

规则或事实的更正不自动开新一轮：这时报告的流水线横幅提示“资料／规则／事实有更新，重新评审”，原因由 `stale_reasons` 给出（`body_updated`、`tender_updated`、`rules_changed`、`facts_changed`），人决定什么时候点“重新评审”。

### 2.5 提交闸门

登记提交（`POST /projects/{id}/submissions`）有一道闸门，任一条件不满足即拒绝，并逐项说明原因：

1. 所选输入是项目最新的一轮，并且基于最新资料：招标文件、补遗和技术标正文的最新版本都在本轮输入里，所提交的正文是该文件的最新版本；规则包和事实集也是最新的。图纸、清单、回执等其他资料不影响提交。
2. 这一轮的核对已完整完成（覆盖度 `complete`，没有规则检查失败或遗漏）。
3. 没有未确认的废标／否决／强制类规则。项目开启“规则按原文接受”时跳过这一条，其余三条不变。
4. 没有未处理的关键问题，也没有未处理的废标／否决风险和强制性要求类问题。“未处理”指问题状态为待复核、已确认待修改、暂缓、修改中或待复检。

提交时冻结所提交的正文版本与对应的输入，之后迟到的补充和更正都不覆盖。

### 2.6 项目状态

| 状态 | 键 | 含义 |
| --- | --- | --- |
| 资料待补充 | `materials_pending` | 缺招标文件或正文 |
| 待开始评审 | `ready_to_analyze` | 资料已齐并解析完成，项目关闭了自动开始评审，还没有任何一轮评审，等人点“开始评审” |
| 评审中 | `analyzing` | 解析、提取规则、核对或预测在进行 |
| 评审中断 | `analysis_failed` | 某个环节失败，可重试 |
| 问题待处理 | `issues_open` | 本轮还有未处理的问题，或核对覆盖不完整 |
| 可登记提交 | `ready_to_submit` | 本轮所有问题都已处理、核对覆盖完整，且资料、规则、事实在本轮之后没有变化；有变化时项目回到“问题待处理”，直到基于最新输入重新评审 |
| 已提交 | `submitted` | 已登记提交 |
| 已归档 | `archived` | 项目归档，只读保存 |
| 已取消／流标 | `cancelled`／`failed_tender` | 项目取消或招标流标 |

“可登记提交”比闸门更严格：它要求本轮所有问题都处理完；闸门只要求关键和废标／响应类问题处理完，仍有改进建议未处理时可以由人自行决定提交。

### 2.7 项目级功能开关

使用者不一定愿意完整跟随上面的流程。为了降低使用门槛，核心之外的模块都可以按项目关闭或跳过，让团队只用自己需要的部分，而核心检测仍然在每个项目上运行（需求 FR-013，决策 DEC-019—DEC-021）。

开关在项目设置的“功能开关”里（`PATCH /projects/{id}` 的 `settings`，七个键整体替换）；每次修改写一条审计 `project.update`，记录修改后的全部取值。新建项目时取默认值：全部开启，只有“规则按原文接受”关闭。

| 键 | 开关 | 默认 | 改变默认后的行为 |
| --- | --- | --- | --- |
| `auto_start` | 资料齐了自动开始评审 | 开 | 关闭后资料照常解析（不调用模型），新一轮评审等人在报告页点“开始评审”（`POST /projects/{id}/analysis`）。首轮之前项目状态为“待开始评审”（`ready_to_analyze`），流水线阶段为 `waiting_start`，报告“下一步”第一条为“开始评审”（`start_analysis`）。已有评审时资料更新，报告继续展示上一轮并提示开始新一轮。重新打开这个开关时，等待中的项目立即开始评审 |
| `accept_rules_as_written` | 规则按原文接受 | 关 | 开启后，未人工确认的废标／否决／强制类规则不阻止登记提交，报告“下一步”不催确认，报告的依据说明与 Word 报告注明“按原文接受”。问题与判定的规则依据仍如实记为未确认 |
| `consistency_check` | 前后矛盾检测 | 开 | 关闭后核对时不运行该检测，不产生前后矛盾类问题，报告不显示这一分类 |
| `scope_check` | 范围残留检测 | 开 | 关闭后核对时不运行该检测，不产生范围残留类问题，报告不显示这一分类 |
| `show_score` | 显示预测分数 | 开 | 关闭后报告与 Word 报告只列“可能的失分点”，不出现分数估计与区间。预测照常进行，用于校准 |
| `price` | 报价模块 | 开 | 关闭后导航、报告头部、“下一步”和 Word 报告都不出现报价；直接打开报价页时说明模块已关闭并给出去设置的入口 |
| `outcome_tracking` | 提示登记开标结果 | 开 | 关闭后登记提交之后报告“下一步”不提示登记开标结果；“提交与结果”页的结果登记照常可用 |

可跳过或可选的环节因此是：开始评审（可设为手动）、废标／否决／强制类规则的确认（可按原文接受）、前后矛盾与范围残留检测、分数的展示、报价、开标结果的登记提示。事实库本身就是可选的：不录入事实也照常评审，界面不催促录入。

没有开关的核心：

- **废标／否决检测与强制性要求核对**：一项违反整份作废，这是系统存在的理由。
- **响应矩阵**：每条规则的判定（含“无法判断”和“检查失败”）都要让人看见，否则“未发现风险”没有意义。
- **证据溯源**：每个问题和判定都回到原文页，这是人复核模型输出的唯一凭据。
- **提交闸门**：开启“规则按原文接受”只放宽“未确认规则”这一条；未处理的关键问题和废标／强制响应类问题、过期的输入、不完整的覆盖照常阻止登记。

检测开关在核对时读取：修改它不改变已完成的评审，之后新开的一轮核对才按新取值执行，核对产物记录本次实际执行了哪些检测；已经产生的前后矛盾或范围残留问题保留在问题页和 Word 报告的问题清单里，报告页的分类计数按当前开关隐藏对应分类。其余开关在读取报告、导出和登记提交时按当前取值生效，修改后立即体现。“规则按原文接受”默认关闭的理由是：规则由模型从招标文件提取，提取错误会直接变成漏检或误报，人工确认是对决定能否入围的规则的最后一道人工把关；只有团队对标段非常熟悉、主动选择放宽时才开启，放宽在报告和审计里都可见。

## 3. 登录与审计

系统只有一道登录门槛：所有接口都要求登录会话，未登录返回 401。登录的成员可以查看全部项目，执行全部操作——上传资料、开始或重新评审、确认规则、复核问题、采纳或驳回改稿、录入事实、保存报价方案、编辑项目与功能开关、登记提交与开标结果；一期不做岗位分权与项目成员管理。

身份只取自服务端会话（`Actor`），请求体里的任何“操作者”字段都不被采信；规则审核、问题复核、报价保存、开关修改、提交与结果登记都按会话身份写审计记录。项目不存在时返回 404（`project_not_found`）。账号由管理命令 `bidwb-admin create-member` 创建；登录方式是账号加口令，不接入单点登录。

### 4.2 废标／否决项检测（P0）

**目的**：在登记提交之前找出可能让整份标书作废的问题，并保证没有人把“没检查出来”当成“没有问题”。

**行为**：

1. 规则提取按性质区分废标／否决、强制、评分、建议、例外，每条规则保留招标文件原文页码、条件与例外；评分条款同时提取分值 `max_points`。
2. 每一轮评审对每条参与规则逐条核对正文，给出判定（见 FR-003），违反或信息不足时生成问题。问题必须引用正文证据，并经程序校验：证据必须属于本项目、引用片段必须真实出现在原文里；通不过校验的候选问题被丢弃，丢弃数记入覆盖度统计（这是拦截模型编造的引用，不影响覆盖度是否完整；整条规则的模型输出不可用才使覆盖度变为部分或空）。
3. 问题分类：规则性质为废标／否决的产生 `disqualification`（废标／否决风险）问题，强制性要求产生 `response`（强制性要求未满足）问题，二者影响环节均为 `qualification`；评分条款与建议性要求上的可改进之处归 `improvement`（改进建议）。问题带 `rule_basis`，标明所依据规则当时是否已人工确认（`confirmed`／`unconfirmed`）。
4. 同一轮评审里，规则、性质与证据相同的问题只保留一条，重跑不产生重复问题，也不覆盖已有的人工复核。
5. 提交闸门见[第 2.5 节](#25-提交闸门)。这一能力没有开关；“规则按原文接受”只放宽闸门中“未确认规则”一条。

**验收标准**：

- 一份含已知否决条款的招标文件和一份违反该条款的正文，评审后报告头部的“废标／否决风险”显示未处理数大于 0，并列出对应问题；每个问题可跳到正文原页和规则原文。
- 没有发现废标风险时头部显示“未发现”，同时注明依据状态（规则 N 条，其中 M 条未确认），而不是只写“通过”。
- 存在未确认的废标／否决／强制类规则时，登记提交被拒绝，错误说明条数；存在未处理的废标／响应类问题时同样被拒绝，错误列出问题编号。
- 模型输出不可用的规则，判定为“检查失败”，覆盖度不是 `complete`，项目不会进入“可登记提交”。
- 某条规则被驳回后，下一轮评审不核对它；驳回前已产生的问题保留在旧一轮里。
- 项目开启“规则按原文接受”后，存在未确认的废标／否决／强制类规则时登记提交成功，报告“下一步”不出现确认规则，Word 报告注明“按原文接受”；问题的规则依据仍为 `unconfirmed`。

### 4.3 评分预测（P0）

**目的**：估计技术标能拿多少分，并指出最可能丢分的地方。大模型负责判断（对应章节、定档、要点核对、与已知分数的标书比较），分数的量尺由公司官方成绩训练出的打分模型给出。

**行为**：

- **逐项判断**：每轮评估全部带分值的有效评分条款。每条条款带上正文里对应章节的全文，按评分标准原文先定档、再在档内给分，逐条判断得分要点是否写到（要点写到必须引用正文），并判断正文是否针对本项目，增加具体性与有效性、前后一致性及双侧证据；长章节分节读取并保留覆盖清单，不按固定字数抽样。图页及表格结构仍属解析缺口；每条独立判断 3 次，失败次数与有效次数分开记录，取均值，区间取各次得分与所定档次的并集。模型输出不可用的条款按 0 到满分全幅计入区间；评分条款没有提取到分值时预测状态为 `abstained` 并说明原因，不给数值。
- **失分点** `topics`：按“满分 − 估计”从大到小至多 10 条，每条带档次、缺失的要点、正文证据与局限；依据未确认的评分条款标注“依据未确认的评分条款”。
- **打分模型**：研究侧用官方技术分训练、按冻结协议验收通过（误差达标且显著优于“取历史平均分”等基线）的模型登记后，适用范围内的项目由模型给出分数与约 80% 区间，标“已校准”，并写明训练组数、评估误差与适用范围；没有模型或项目不在范围内时给出逐项合计，标“未校准”并说明原因。
- **比较式锚定**：登记了锚点包（已知官方分的历史标书）时，对分值最大的几条条款与挑出的锚点逐份比较“哪份写得更好”，拟合出的分数作为打分模型的一个输入。
- 项目关闭“显示预测分数”（`show_score`）时，报告与 Word 报告只列可能的失分点（条款、评估、正文证据），不出现估计值、区间与估计失分；预测照常进行，照样形成配对。
- **在线对照**：已登记的官方技术分与对应提交的预测配对（每个有效提交只配一组，取它最新的一条带技术分的结果；按各自满分折算为百分制，只取目标为技术总分、未被后续更正记录替换、核实状态不是冲突的结果）。**所需配对数 `needed_pairs=20`**：0 组为 `uncalibrated`；1–19 组为 `insufficient`，不给误差；达到 20 组为 `calibrated`，给出 `mae` 和 `bias`（百分制）。在线对照是上线后的持续监控；产品里的配对可导出给研究侧合并重训。

**验收标准**：

- 没有生效的打分模型时，报告与 `GET /projects/{id}/prediction` 的预测带“未校准”标签与 `reason`；登记了验收通过的模型后，适用范围内的项目显示“已校准”、约 80% 区间、模型的训练组数与误差，范围外的项目显示“超出校准范围”与原因。
- 在线对照的配对数不足时不出现误差数字，并显示“已有 X 组，需要 20 组”。
- 评分条款没有提取到分值时，预测为 `abstained`，报告显示原因，不显示 0 分。
- 估计值、区间满足 `0 ≤ low ≤ estimated_value ≤ high ≤ maximum`。
- 每个失分点能跳到正文证据；没有引文支持的要点不出现“已写到”的表述。
- 登记同一提交的官方技术分后，度量页的配对数增加；达到 20 组后出现 MAE 与偏差。
- 关闭“显示预测分数”后，报告头部卡片显示“可能的失分点 N 处”，Word 报告第三部分标题为“可能的失分点”且不含技术标估计的字样。

### 4.4 响应矩阵（辅助）

每轮评审对每条参与评审的规则给出判定，汇总成表（`GET /projects/{id}/compliance`，也是报告的一部分）：

| 判定 | 键 | 含义 |
| --- | --- | --- |
| 满足 | `satisfied` | 正文满足规则，**必须引用正文依据**；没有可核对依据的“满足”被降为无法判断 |
| 违反 | `violated` | 正文与规则冲突；必须伴随至少一个通过校验的问题，否则降为无法判断 |
| 无法判断 | `unclear` | 正文没有涉及或信息不足，也包括缺少事实 |
| 检查失败 | `failed` | 模型输出不可用，这条规则没有被检查 |

废标／否决与强制类单独计数（`qualification`），评分条款单独计数（`scoring`）。**“无法判断”不等于“满足”**，必须让人看见：矩阵排序时违反和无法判断排前，每行标注规则是否已确认。

验收：任一判定为“满足”的行都有正文证据；总数等于参与评审的规则数；“检查失败”计入覆盖度的缺口；违反与无法判断排在满足之前。

### 4.5 前后矛盾检测（辅助）

不调用模型的确定性检测，读取解析出的正文片段，给出带出处的候选问题，分类为 `consistency`（前后矛盾）：

- **数值矛盾**：同一个量（以数值前面的名称加型号限定为键，单位相同）在正文不同位置取值不同，例如同一管径的管长、同一工序的最大开挖深度、同一工种的人数。每个量只报一条，列出至多 4 个取值及其页码；型号不同的同类量（如 DN300 与 DN500 的管长）不互相比较。
- **大段重复**：不同页的两段文字高度重复（共享的 24 字片段占较短一段 80% 以上，且较短一段至少 120 字），归为改进建议，每对只报一条，至多 10 条。

项目关闭“前后矛盾检测”（`consistency_check`）时，核对不运行这项检测，核对产物的 `checks` 记录 `consistency=false`。

验收：同一量在两页取不同数值时报出一条问题并列出两个页码；DN300 与 DN500 的同类量不被误报为矛盾；重跑不产生重复问题；关闭检测后新一轮不产生前后矛盾类问题，报告不显示该分类。

### 4.6 范围残留检测（辅助）

不调用模型的确定性检测，归类为 `scope`（范围残留）：正文反复出现、招标文件及补遗里却完全没有的工程对象，是套用其他项目模板最常见的失分点。检测用一份与项目无关的工程对象词表（泵站、沉井、调蓄池、变电站、调度平台、隧道、顶管、盾构等）在正文里找词，再看招标文件和补遗是否出现过同一对象；没出现的，列出正文页码，由人确认它是否确实不属于本项目的招标范围。另外检测路名、街名等地名在正文出现而招标文件没有的情况（严重度较低）。每轮至多报 8 条，出现多的排前面。没有招标文本时不检测，不猜。

项目关闭“范围残留检测”（`scope_check`）时，核对不运行这项检测，核对产物的 `checks` 记录 `scope=false`。

验收：正文提到招标文件和补遗都没有的“泵站”时报出一条范围残留问题，列出页码并要求确认；招标文件里有“泵站”时不报；词条被更完整的词条包含时只报更完整的一个；关闭检测后新一轮不产生范围残留类问题，报告不显示该分类。

### 4.7 报价模拟（辅助）

**输入**：评标价规则 `PriceParams`、竞争对手报价估计、候选报价。

| 参数 | 含义 |
| --- | --- |
| `full_score` | 价格分满分 |
| `above_deduct_per_pct` | 报价高于基准价，每高 1% 扣的分数 |
| `below_deduct_per_pct` | 报价低于基准价，每低 1% 扣的分数 |
| `max_limit`（可选） | 最高投标限价，超过将被否决 |
| `abnormal_low_pct`（可选） | 低于基准价该百分比视为异常低价风险 |
| `benchmark` | 基准价取法：固定值（`fixed`），或竞争对手报价的平均值（`average`）／去极值平均值（`trimmed_average`，各去掉 `trim_pct`% 的最高与最低报价）乘以系数 `coefficient`；可选把己方候选报价计入平均（`include_own`） |

竞争对手报价至多 200 个，候选报价至多 20 个；每个金额与参数的十进制字符串至多 24 个字符，超长被拒绝。

**输出**：基准价；各候选报价相对基准价的偏差百分比和价格分（扣到 0 为止，不超过满分）；风险提示（`over_max_limit` 超过最高限价将被否决、`abnormal_low` 异常低价风险）；价格分曲线；**换算关系**（高于基准价 1% 失去几个价格分，即 1 个分约相当于多少 % 报价）；最优候选（在没有风险提示的候选里取价格分最高者）。

示例（仅说明算法）：满分 30，高于基准价每 1% 扣 0.5 分，基准价取竞争对手报价 1000、1100、1200 的平均值 1100；候选报价 1166 高于基准价 6%，价格分 27；换算关系为高于基准价每 1% 失去 0.5 分，即 1 个分约相当于 2% 的报价。

**保存与试算**：每次保存追加一个版本（`price_plans`），可看历史，保存按会话身份留审计；页面另提供“不保存、实时试算”（`POST /projects/{id}/price:simulate`）。平均值法的基准价取决于其他投标人的报价，竞争对手报价只是估计，界面要说明这一点，实际基准价以开标为准。所有金额和分数用十进制精确计算。

项目关闭“报价模块”（`price`）时，导航不出现“报价”，报告头部没有报价卡片，“下一步”不提示填写报价，Word 报告不含报价部分；已保存的方案保留，重新开启后照常显示。

验收：固定基准价算例与手算一致；平均值法没有竞争对手报价时提示无法计算基准价；超过最高限价或低于异常低价线的候选带风险提示且不会成为最优；未登录保存返回 401；保存两次产生两个版本，历史按时间倒序；全部候选都触发风险提示时给出说明。

### 4.8 评审报告与导出（辅助）

报告（`GET /projects/{id}/report`）是项目的落地页，只汇总已有事实，不产生新判断。内容依次为：

1. 流水线横幅（`pipeline`，含 `stale_reasons`）。
2. 头部结论卡片：废标／否决风险（未处理数）、强制性要求满足 X／Y、预测得分区间（写明已校准或未校准）、报价最优候选。
3. 下一步（`next_actions`，默认只展开首条人工待办，其余折叠并显示关键问题与其他建议数量；评审操作由顶部横幅提供。“登记提交”只在流水线完成、资料规则事实都没有更新时出现；按对中标的影响排序：先是评审中断、开始评审或评审进行中的提示，然后是可能被否决的问题、无法判断的关键条款、依据未确认的关键规则、影响得分的问题、资料更新、报价、登记提交、登记开标结果，每条带目标页面）。
4. 响应矩阵表。
5. 问题分类计数（五类，各含总数、未处理数、已处理数）。
6. 评分预测面板：估计与区间、失分点、校准状态说明。
7. 导出入口。
8. 依据说明：规则 N 条，其中 M 条未确认。

没有完成的评审时，接口返回 404 `report_not_ready`，页面显示流水线进度、“上传资料”引导，或在手动开始的项目上显示“开始评审”。

报告按项目功能开关裁剪（第 2.7 节）：关闭的检测不显示对应分类；关闭“显示预测分数”时头部卡片与预测面板只列可能的失分点；关闭报价模块时没有报价卡片和报价提示；关闭“提示登记开标结果”时登记提交后不提示登记结果；开启“规则按原文接受”时废标风险卡片与依据说明写明“按原文接受”，不出现确认规则的提示。

**导出**：页面入口分别名为“下载评审报告（Word）”与“下载批注审阅稿（PDF）”。Word 评审报告（`/report.docx`）含废标／否决与强制性要求、分类问题清单（带正文页码与引用）、评分预测与报价四部分，并响应功能开关：关闭“显示预测分数”时第三部分标题为“可能的失分点”且不含分数，关闭报价模块时没有第四部分，开启“规则按原文接受”时评审依据一段注明按原文接受；批注版 PDF（`/body.annotated.pdf`）在正文原位用 PDF 标准高亮批注标出问题，说明写在批注内容里，可用常见阅读器查看和回复；页面有旋转或证据没有坐标时只标在页面左上角，不画虚构的位置。导出的是最近一轮已完成评审，正文 PDF 大小上限 60 MB。

验收：报告的各数字与问题页、响应矩阵一致；关闭的模块不出现在报告与 Word 报告里；导出的 Word 文档包含全部分类和预测的校准状态说明；批注版 PDF 在有坐标的证据处有高亮批注，没有坐标的证据只出现在页面左上角；没有完成评审时导出返回 404。

### 4.9 依据：规则与事实（辅助）

依据页管理两样东西：

- **规则**：按性质分组，废标／否决／强制在前；每条显示确认状态（未确认时标“评审暂按原文判断”）、评分条款的分值、原文页码；可确认、驳回、暂缓，废标／否决／强制类可以一键“全部按原文确认”。确认的语义见[第 2.3 节](#23-规则确认后置且按需)。
- **事实库**：从招标文件和图纸清单中确认的工程事实（名称、数值与单位、适用对象与范围、证据），由人工录入，可撤回。事实更新不自动开新一轮，报告提示重新评审；评审时需要某个事实才能下结论的问题，若事实已在库里确认，就不要求人工确认。事实库是可选的：不录入事实也照常评审，界面不催促录入。

验收：确认已确认的规则不产生新规则包；驳回已被某一轮引用的规则会产生新规则包，旧一轮仍可复现；事实库修改后报告显示 `facts_changed`。

### 4.10 问题复核与改稿（辅助）

- **复核**：人工对问题执行确认（`confirm`）、驳回（`reject`）、暂缓（`defer`）、请求补充事实（`request_facts`）、重新打开（`reopen`）、标记已解决（`resolve`），状态在“待复核、已确认、已驳回、暂缓、修改中、待复检、已解决”之间流转；确认可以不写理由，其余决定必须写明理由；记录对象版本以拒绝过期操作。
- **改稿**：针对已确认的问题生成局部修订建议，限定可使用的事实；提供差异对比；由人采纳或驳回。采纳不等于已解决：采纳后问题转“修改中”，由人确认新正文已落实并填写理由后才标记已解决。
- **证据查看**：问题详情带正文证据，PDF 页内高亮。

验收：复核记录会话身份为操作者，请求体里的操作者字段被忽略；不合法的状态转换返回 409；驳回后的问题可以重新打开；采纳改稿后原问题转“修改中”，不会自动变为已解决。

### 4.11 结果登记与校准（辅助）

- 登记提交（`submissions`）关联所提交的正文版本与评审输入；开标结果（`outcomes`）关联到具体提交，记录阶段结果（`pending`、`technical_shortlisted`、`not_shortlisted`、`rejected`、`candidate`、`awarded`、`not_awarded`、`cancelled`、`failed_tender`）、成绩口径（技术总分、综合总分、无分数）、原分与满分、聚合方式、来源与页码。
- 来源分用户报送与官方两类，核实状态为未核实（`pending`）、已核实（`verified`）、冲突（`conflict`）；“已核实”必须有官方来源文件和核实人。结果更正追加新记录，旧记录保留，不覆盖。
- 综合总分、“/”和未披露不填技术总分、不作零；没有结果的项目不进入已知结果的分母。
- 技术总分的官方结果与预测配对后进入校准（见 FR-002）。结果登记后可记录反馈，说明预测偏差或问题原因，不修改原预测。
- 项目关闭“提示登记开标结果”（`outcome_tracking`）时，登记提交之后报告“下一步”不出现“登记开标结果”；结果登记功能本身照常可用。

验收：未核实的结果可用于度量但不冒充官方分；只有官方、有来源、有核实人的结果才能标为已核实；更正后只统计最新的一条；候选公示与最终中标分开记录。

### 4.12 项目、资料与自动评审流水线（支撑）

- **项目**：标题、招标编号、标段、轮次、地区、工程类型、截止时间，创建时只有标题必填；总览每个项目一行，显示否决风险未处理数、预计技术分（含覆盖程度）、状态、截止与下一步。
- **资料**：拖拽上传，选择用途（招标文件、补遗、技术标正文、图纸、清单、已提交稿、官方结果、其他）；分片上传，校验值去重，相同内容不重复入库；每份资料显示版本、关联状态（未确认、已确认、冲突）和解析状态（完整、部分、失败），解析缺口说明未能识别的页面、表格与图示。上传后顶部出现流水线进度条。
- **任务**：解析、规则提取、核对、预测、改稿建议都是持久任务，带租约、重试和进度事件；浏览器关闭后可再次进入查看，同一任务重试不重复写结果。Word 评审报告与批注版 PDF 的导出是同步接口，不走任务；复检任务范围外。
- 其他：全文检索（关键词检索；请求混合检索时如实降级为关键词并说明原因）。
- **开始评审**：自动开始的项目资料齐了就评审；手动开始的项目由人在报告页点“开始评审”，与“重新评审”是同一个接口（`POST /projects/{id}/analysis`），系统记下“要求开始”的标记，提取规则等异步环节完成后据此继续，直到本轮输入冻结时用掉这个标记；之后的资料更新会再次等人点“开始评审”。

验收：缺招标文件或正文时项目为“资料待补充”并说明缺什么；上传相同文件不产生新版本；解析失败的文件在横幅中点名；重复触发推进不产生重复任务；本轮输入不能冻结（例如资料的取得时间晚于截止时间）时项目进入“评审中断”，横幅的核对步骤写明原因；提取规则期间招标文件或补遗又有新版本时，那次提取不形成规则包，系统针对最新资料重新提取；核对覆盖不完整时“重新评审”会重跑核对；评审完成后资料、规则或事实有变化时项目不停留在“可登记提交”。

### 4.13 项目级功能开关（支撑）

**目的**：让不愿完整跟随流程的团队只用需要的部分，降低使用门槛；核心检测不因此缺席。开关、默认值与理由见[第 2.7 节](#27-项目级功能开关)。

**行为**：

- 项目设置的“功能开关”列出七个开关及说明，以开关控件呈现；修改后一次保存（`PATCH /projects/{id}`，`settings` 整体替换，带 `If-Match` 项目版本号）。
- 新建项目时 `settings` 取默认值；请求体可以同时给出 `settings`。缺省的键按默认值读取。
- 每次修改写审计 `project.update`，细节含修改后的全部开关取值。
- 修改不自动开新一轮评审，也不改写已完成的评审。

**验收标准**：

- 新建项目的开关为：`auto_start`、`consistency_check`、`scope_check`、`show_score`、`price`、`outcome_tracking` 为开，`accept_rules_as_written` 为关。
- 关闭 `auto_start` 后上传招标文件与正文：只产生解析任务，不产生规则提取、核对或预测任务；项目状态为 `ready_to_analyze`，流水线阶段为 `waiting_start`，资料步骤完成、其余三步等待。点“开始评审”后评审完成，项目进入问题待处理。之后上传正文新版本：流水线回到 `waiting_start`，`stale_reasons` 为 `body_updated`，报告仍为第 1 轮且“下一步”第一条为 `start_analysis`；再点“开始评审”后报告为第 2 轮。
- 同时关闭前后矛盾检测、范围残留检测、报价模块、显示预测分数并开启规则按原文接受后评审：这两类问题总数为 0；报告没有报价摘要，“下一步”只有“登记提交”；存在未确认的废标／否决／强制类规则时登记提交成功；Word 报告含“可能的失分点”与“按原文接受”，不含“技术标估计”与“四、报价”；审计记录了修改后的开关。
- 关闭 `auto_start` 的项目资料就绪、处于 `ready_to_analyze` 时重新打开开关：评审立即开始并完成，不需要再点“开始评审”。
- 关闭报价模块与“提示登记开标结果”、开启规则按原文接受时，已提交且未登记结果、尚未保存报价、仍有未确认关键规则的项目，“下一步”为空。
- 用过期版本号修改返回 412；修改不存在的项目返回 404（`project_not_found`）。

对应的验收用例为 AC-067—AC-074，见 [acceptance-cases.json](../05-技术与设计/contracts/acceptance-cases.json)。

### 4.14 非功能需求

| 编号 | 要求 | 验收 |
| --- | --- | --- |
| NFR-001 证据可追溯 | 每个问题、判定、预测失分点都能回到原文件的物理页与原文摘录；印刷页码与物理页码分别记录；问题的证据必须来自本项目且摘录真实出现在原文 | 抽查问题均能打开原页；伪造或错位的引用被拒绝 |
| NFR-002 评审结果可复现 | 一轮评审使用的资料版本、规则包、事实集冻结为输入；规则包、证据、审核、提交与结果追加保存，由数据库触发器强制；更正落在新记录上 | 规则被更正后旧一轮报告不变；任一轮可还原当时使用的资料和规则 |
| NFR-003 失败不冒充通过 | 解析失败、模型输出不可用、覆盖不完整都如实显示，不得呈现为“未发现问题”或“满足” | 模拟模型失败时规则判定为“检查失败”，项目不进入“可登记提交” |
| NFR-004 预测不夸大 | 分数是否经过验收通过的打分模型校准始终写明：已校准时给出训练组数、评估误差与适用范围，未校准或超出范围时带“未校准”标签与原因；在线对照样本不足不给误差；不把预测写成结果承诺 | 页面、Word 报告与接口在三种校准状态下的展示均有测试覆盖 |
| NFR-005 服务端认证与审计 | 所有接口要求登录会话；身份只取自服务端会话，请求体里的操作者字段不被采信；规则审核、问题复核、报价保存、开关修改、提交与结果登记都写审计记录并记录操作者；写接口支持幂等键 | 未登录被拒（401）；审计记录操作者；同一幂等键重复请求不重复写 |
| NFR-006 数值与时间精确 | 分数、金额用十进制，拒绝 NaN；时间带时区，提交时间不能晚于当前 | 报价算例与手算一致；无时区时间被拒 |
| NFR-007 可访问性与窄屏可用 | 键盘可达、焦点可见、状态不只靠颜色、对比度达标；手机宽度可阅读报告、问题和证据，长篇编辑以电脑为主 | 以[交互与视觉设计](../05-技术与设计/交互与视觉设计.md)的检查项验收 |

## 5. 页面与信息架构

页面的版式、状态与视觉规范见[交互与视觉设计](../05-技术与设计/交互与视觉设计.md)，本节只规定内容和流程。

项目内导航顺序即流程：**报告**（落地页）、**问题**、**依据**（规则与事实）、**报价**、**提交与结果**、**资料**；工具为检索、设置（项目信息与功能开关）。全局为项目总览与**度量**。关闭报价模块的项目，导航不出现“报价”。

| 页面 | 内容 |
| --- | --- |
| 项目总览 | 每个项目一行（否决风险、预计技术分及覆盖的分值、状态、下一步按钮），新建项目只需填名称 |
| 资料 | 拖拽上传多个文件，用途与版本按文件名预填、上传前可改，上传队列显示进度并可重试，版本与解析状态；上传后顶部出现流水线进度条，没有“下一步”按钮 |
| 报告 | 见[第 4.8 节](#48-评审报告与导出辅助) |
| 问题 | 分类标签页（废标／否决风险、强制性要求、前后矛盾、范围残留、改进建议）与状态筛选，键集分页列表，详情，正文证据查看，复核动作与改稿建议 |
| 依据 | 规则分组与确认动作，事实库作为同页标签 |
| 报价 | 评标价规则表单、竞争对手报价（逐行或批量粘贴）、候选报价；评标价规则按招标文件预填并注明出处页；右侧实时试算（结果表、价格分曲线、换算句、风险提示）；保存与历史版本 |
| 提交与结果 | 登记提交（闸门逐项列出未满足条件并给出处理入口，全部满足后出现登记表单）与开标结果登记，同页两个标签 |
| 设置 | 项目基本信息；功能开关（七个开关、说明与当前取值） |
| 度量 | 见[第 7 节](#7-指标与验收口径)，含图表 |

词汇统一为：评审（一轮对招标规则的核对加预测）、核对、判定、响应矩阵、废标／否决风险、强制性要求、评分条款、依据（规则与事实）、报告。

## 7. 指标与验收口径

统计单位为公司一次正式投标的标段及投标轮次。同一标段重新招标单独登记。**所有指标围绕中标，不统计过程类指标；系统不管投标人的内部成本。** 度量由 `GET /metrics` 提供，只统计调用者有权查看的项目。

| 类别 | 指标 | 定义 |
| --- | --- | --- |
| 结果 | 提交数、已出结果数 | 未被重新提交替换的提交数；已登记最新有效结果的提交数 |
| 结果 | 入围数／不入围数／被否决数／中标数／未中标数 | 按每个提交的最新有效结果（未被后续更正记录替换、核实状态不是冲突）的阶段结果计数 |
| 结果 | 入围率 | 进入后续评审的数量（技术入围、中标候选、中标、未中标）／已有明确阶段结果的数量（上述四类加不入围、被否决）；项目取消、流标、结果未出不进分母；分母为零时不给值 |
| 结果 | 中标率 | 中标数／（中标＋未中标＋不入围＋被否决）；候选公示不计中标；分母为零时不给值 |
| 废标／否决风险闭环 | 评审发现数 | 每个项目最近一轮评审里废标／否决风险与强制性要求类问题的总数 |
| 废标／否决风险闭环 | 提交前已解决或驳回数 | 其中状态为已解决或已驳回的数量 |
| 废标／否决风险闭环 | 提交时仍未处理数 | 已提交的评审输入上，这两类问题处于未处理状态的数量 |
| 废标／否决风险闭环 | 招标方实际否决数 | 阶段结果为被否决的提交数 |
| 预测校准 | 配对数、`mae`、`bias` | 见 FR-002；配对不足 20 组不给误差 |
| 整改动作与得分变化 | 逐轮变化 | 每个项目逐轮的预测得分估计、未处理问题数、已解决问题数、未处理的废标／强制类问题数，以及实际技术分（如已登记）；最多展示 20 个项目 |

能力验证指标用于衡量检测本身是否可靠，需要人工参考标准，定义如下：

| 指标 | 定义 |
| --- | --- |
| 关键条款召回 | 正确提取的参考废标／否决／强制条款数／人工参考条款总数 |
| 判定准确率 | 与人工参考一致的判定数／受检判定数；“无法判断”单列，不计入准确 |
| 废标风险问题准确率 | 人工确认成立的废标／响应类问题数／受检问题数；漏报与误报分别记录 |
| 证据定位 | 正确定位支撑或冲突原文的问题数／受检有定位问题数 |
| 预测误差 | 预测减官方技术分，按满分折算为百分制，报告 MAE、偏差、样本数及按规则分组的误差 |
| 相对基线增益 | 与预先固定的简单基线（如训练集均值）在相同独立测试组上比较，训练内提升不算 |
| 失分点命中 | 预测列出的失分点与人工评分复盘一致的比例 |

分母为零或资料不足时记不可评价。验收阈值在取得基线后、试点前固定，调整留理由。系统自评分、历史相关性、离线质量改善和少量试点都不能直接证明系统导致中标率提升；试点结果按样本量和归因限制如实表述。

问题主要在解析时，先改善扫描、表格与版本识别；检测不可靠时补规则与事实；已入围但持续未中标时，分析报价与后续评审环节，不默认继续扩充技术标功能。

## 8. 验证计划

### 8.1 样本与参考标准

可用样本的现状唯一见[案例库](https://github.com/zys743551828-art/tender-datasets/blob/main/README.md#数据可用性)。验证前固定样本成员、排除原因、资料版本、参考答案和配置。规则参考答案来自原文提取与人工核对，废标／强制条款的参考清单由市政工程师标注并记录复核人；固定规则参考集见 [RULE-001](https://github.com/zys743551828-art/tender-datasets/blob/main/评测集/RULE-001.json)，由开发者依据归档原文建立，没有独立工程复核或盲测。

| 验证任务 | 参考资料与检查点 | 所需条件 |
| --- | --- | --- |
| 废标／否决与强制条款识别（FR-001） | 道路评标表中的否决依据（主要管理技术人员配置、项目经理及其业绩等），见[市场研究第 3.6 节](../01-背景与市场研究/市场研究.md#36-公开评审结果对照与数据限制)；企业业绩与人员业绩分开；补疑中的认可例外 | 已取得相应招标与补疑原件；工程师形成参考清单 |
| 规则版本与例外（FR-008） | 补疑对分档区间的修改；保函前后期限均认可；原文日期冲突不自动更正 | 已取得对应补疑 |
| 评分条款与预测（FR-002） | 评分条款分值提取；失分点与人工复盘比较；与官方技术分配对 | 完整提交正文、生效规则、官方技术分与满分配对；数量见第 8.3 节 |
| 前后矛盾与范围残留（FR-004、FR-005） | 在公开或自有稿件上植入与自然存在的矛盾、残留对象，统计召回与误报 | 多个完整正文与对应招标文件 |
| 报价模拟（FR-006） | 手算算例与程序逐一核对；各类评标价规则表述的覆盖范围 | 招标文件的评标价条款；公开价格规则只作为公告能证明的部分 |
| 公司结果（FR-009、FR-011） | 全部正式投标与结果，含入围、否决与未中标 | 公司台账；不能用公开项目的投标人分布代替 |

### 8.2 废标／否决检测的验证方法

1. 工程师对每份招标文件标注全部废标／否决／强制条款（含原文页码），再对对应正文逐条标注“满足、违反、无法判断”，作为参考。
2. 运行评审，按第 7 节计算关键条款召回、判定准确率、废标风险问题准确率、证据定位，漏报与误报分别列出，重大漏报单列。
3. 分开统计规则已确认与未确认两种依据下的表现，检验“依据未确认”标注是否有意义。
4. 隐藏工具来源与历史成绩，争议项由第二名工程人员复核。

放行条件：参考集内的废标、否决与强制条款不接受无提示的遗漏或虚构；无法确认的条款必须以“无法判断”或“检查失败”呈现。其余目标阈值取得基线后固定。

### 8.3 评分预测的对照试验

1. 确认目标：最终技术总分，保留满分、官方来源、聚合方式、规则版本和实际提交稿。只有综合总分而无法拆分的结果不作技术标签。
2. 盘点样本：按独立项目数、工程与规则类别、时间、分数分布登记，连续收集普通、未入围、被否决与高分稿件，不只选高分或已披露成绩的项目。
3. 锁定划分：同项目、近重复和同源模板同组，开发、校准、测试不交叉；评分文件、评标公示和事后结果不得作为事前预测输入。
4. 建立基线：训练集均值或中位数、按规则分组的基线，与预测在相同独立测试组上比较。
5. 评估：报告绝对误差、偏差、相对基线增益，按规则与工程类别分层；样本不足标不可评价，不用跨项目相关性代替区分能力。
6. 稳健性：同输入重复运行的波动；只增字数或改文风；缺附件；未知规则。
7. 失分点：与工程师对正文的评分复盘比较命中率。
8. 结论：报告项目数、分数范围、误差、波动与相对基线的增益。目标误差在最终测试前结合实际分差固定；区间的覆盖率另行检验，不用模型自述信心代替。未通过时保持“未校准”，如实记录失败。

执行方式（工具见 tender-research README 第 5 节与[案例与数据规范](../03-数据与案例/数据管理规范.md)）：

| 步骤 | 命令 | 产出 |
| --- | --- | --- |
| 入库 | `python -m tender_research.intake --sheet 样本登记表.csv --inbox 收件 --upload` | 评分配对集（格式 A）与入库报告：查重、无文字层、综合分、分数超满分、同源模板分组 |
| 系统预测 | `python -m tools.batch.predict_dataset 评分配对集.json --out 系统预测 --cache-dir 缓存`（tender-app/backend；先 `--estimate-only` 估费用、`--limit 10` 试点） | 每份样本一个格式 B 文件：逐项判断、特征 `pf-1`、锚定比较 |
| 评测与导出 | `python -m tender_research.score_eval --pairs … --predictions … --protocol 评测协议.json --name …`（先 `--mode cv` 比较方法，协议冻结后 `--mode holdout` 只跑一次） | 报告（误差、增益区间、分层、区间覆盖、项目内排名、入围概率、学习曲线）与打分模型 |
| 登记 | `bidwb-admin register-scoring-model calibration_bundle.json --report report.json --reviewer … --environment shadow`，对照无误后再登记到 `business` | 产品按模型校准，界面显示“已校准” |

标签来源在协议里明确（`label_sources`，例如官方原件与公司台账）；报告同时给出全部准入标签与“已核验官方原件”子集两套结果，结论以前者为准、写明来源构成。第一批约 300 份样本按此流程建立第一版模型；数据持续增加时重跑同一流程，学习曲线显示增加数据是否仍能降低误差。

系统内置的在线对照（配对 20 组起给出 MAE 与偏差）是上线后的持续监控，不替代上述对照试验。

### 8.4 其他验证

- **前后矛盾与范围残留**：算法为确定性规则，验证目标是召回与误报；范围残留的词表覆盖范围用自有稿件检验，词表之外的对象不会被发现，这一点在报告中如实说明。
- **报价模拟**：函数为确定性计算，用手算算例、边界值（偏差为零、扣到零分、基准价缺失）和风险提示条件逐一验证；平均值法的结果取决于竞争对手报价的估计，不评价估计的准确性。
- **结果闭环**：真实结果出现前已有带时间的预测；之后关联真实技术分与阶段结果；分别核验检测质量、预测误差和中标表现，不互相替代。
- **真实试点**：保存建议、采纳情况、最终稿与实际结果；预先确定比较口径，按地区、工程类型、评标规则和竞争条件分组；离线质量改进不等同于真实中标效果。

**数据是瓶颈。** 两个 P0 的可靠性取决于数据：废标检测需要带人工标注的招标文件与正文，评分预测需要“完整提交正文＋官方技术分＋满分”的配对；逐项得分、同场全部投标人的技术分与入围线能显著提高训练和评测的价值（见数据规范 2.3 节）。公开评标公示只披露部分成绩且不含正文（例如一份公开结果里 208 家投标只有 5 家披露技术分），不能作为训练集；需要补充历史标书与官方成绩。没有验收通过的打分模型之前，系统按如实标注的方式运行：预测带“未校准”、样本不足不给误差、规则依据未确认就写明未确认。
