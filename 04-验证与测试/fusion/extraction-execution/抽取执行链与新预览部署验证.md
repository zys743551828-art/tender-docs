## 实际执行机制

专用全新 PostgreSQL 库从统一 SQL 计划初始化，API／Worker 分别使用非 owner LOGIN。显式合成夹具提供解析行和已完成解析阶段；原件字节存入内存对象存储适配器，文件摘要、大小及上传声明一致。真实 `verify_bytes` 校验实际字节，不跳过摘要核对；这些字节不是实际 PDF，未执行 OCR 或解析 Worker。

认证 ASGI 请求 `/bids/{id}/reviews`，再执行真实 `prepare_intent`，由其选择精确匹配权威包并持久化冻结 descriptor／operation／outbox。任务消息交给真实 `engine.handle`（或租约反例的 acquire/run_compute/finish）执行 `compute_prepare` 与 `publish`，创建实际规则集、效果回执和抽取绑定。只有模型生成与对象存储使用显式测试适配；不模拟准备、租约、规则发布或回执 SQL。

| 场景 | 实际观察 |
| --- | --- |
| 正常完成及重复投递 | 实际准备、计算、发布成功；重放同一消息不再调用模型适配器；恰有一份抽取绑定，新清单为 exact_frozen_input_result，完整性仍 false |
| 旧租约被替换 | 原租约超时，新租约 fence 增长；旧 lease 完成返回 false，新 lease 完成一次；之后重复投递不重复执行或写回执 |
| 模型漏报一个输入证据 | EXTRACTION_RANGE_INCOMPLETE 持久失败；没有抽取绑定；同消息重放不再调用适配器 |
| 计算期间规则集更新 | PREPARATION_RULE_SET_CHANGED 持久失败；迟到结果不覆盖新规则，不生成错误的精确绑定 |

四项场景均验证模型适配器只调用一次。这里只证明调用边界与持久化机制；未测实际供应商响应、计费恢复或模型质量。
