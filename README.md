## 2. 目标、分工与原则

建设约束：全新系统，无旧系统迁移或兼容需求；消息基础设施确定为Kafka；RAG为首批能力，pgvector承担向量数据库职责。历史标书作为新资料入库，备份恢复保留。

本项目是公司内部长期使用的市政工程投标辅助系统，**目标是中标**，不是产出一份看起来合规的文档。项目不设对外 SaaS 盈利、软件销售、付费客户增长或市场份额目标，也不为这些目标建设功能。

一份施工组织设计能否中标，取决于三件事，按重要性排序：不被淘汰（废标／否决项、强制性要求）、技术分尽量高（按评分条款评估）、价格分与技术分合理换算（评标价规则）。据此，一期有两个并列的 P0：**废标／否决项检测**与**评分预测**；其余功能——响应矩阵、前后矛盾检测、范围残留检测、报价模拟、评审报告与导出、规则与事实、结果登记与校准——都是围绕这两件事的辅助。需求与优先级见[业务需求说明书](02-业务与产品/业务需求说明书.md#5-业务需求与优先级)。

目标产品以上传即评审、风险优先和清楚的下一步承接日常工作，需要时展开GovDash式章节编制、来源与版本工作区；AI既可直接对话，也可随页辅助，历史项目和企业知识可独立进入。保留上传即评审、完整报告、规则确认后置和标准提交闸门。项目、会话和知识的生命周期及评分闭环见[AI 投标工作台 PRD](02-业务与产品/AI投标工作台PRD.md)。现有报告页面与接口行为见[一期方案第 2 节](02-业务与产品/一期方案与验证计划.md#2-产品流程)，不因目标规格写成而视为已完成改造。

用户不一定愿意完整跟随这套流程，所以核心之外的模块都可以按项目关闭或跳过：自动开始评审、前后矛盾检测、范围残留检测、显示预测分数、报价模块、提示登记开标结果默认开启，可以关闭；“规则按原文接受”默认关闭，开启后未确认的废标／否决／强制类规则不阻止登记提交。废标／否决检测、响应矩阵、证据溯源和提交闸门是核心，没有开关。开关的行为与理由见[一期方案第 2.7 节](02-业务与产品/一期方案与验证计划.md#27-项目级功能开关)与[决策与依赖](00-项目管理/决策与依赖.md)（DEC-019—DEC-021）。

效果只用中标导向的度量评价：入围率与中标率、废标／否决风险的闭环、预测校准、整改动作与得分变化；口径唯一见[一期方案第 7 节](02-业务与产品/一期方案与验证计划.md#7-指标与验收口径)。系统不管投标人的内部成本，也不统计任何过程类指标。

一期聚焦市政工程，以道路、管网及综合市政验证。历史案例具备完整提交正文，得分有技术总分和综合总分两种口径，暂缺评分项明细，实际入库可用性见[案例库](https://github.com/zys743551828-art/tender-datasets/blob/main/README.md#数据可用性)。**数据是瓶颈**：先核验10—20份“实际提交正文＋生效招标补遗＋技术分及满分＋成绩出处”的样本，再向约300份训练与评测资料扩展。逐项得分、评委与同场资料有则保留；缺少不补造。未经独立验收的预测保留未校准身份，不声称误差或区间已经达标。

| 维护人员 | 承接运行、规则更新、数据维护与交接 |

系统只有一道登录门槛：登录的成员可以查看全部项目并执行全部操作，关键操作按会话身份留审计记录；一期不做岗位分权。

共同原则：

- 结论有来源，事实、假设、建议及未决信息区分清楚；每个问题和判定都能回到原文页。
- 失败不冒充通过：解析失败、模型输出不可用、覆盖不完整如实显示；“无法判断”不等于“满足”。
- 预测不夸大：大模型只做判断，分数的量尺来自官方成绩训练、评测通过的打分模型；始终写明是否已校准，未校准时带标签与原因，不当作对结果的承诺。
- 官方成绩、人工标注和模型判定分别保存；评分明细缺失时不编造分项或扣分归因。
- 没跑过的验证不写成已验证；模板、目录和计划不代表实现或效果已验证。
- 新系统按[成熟方案调研](01-背景与市场研究/成熟AI系统与技术组件调研.md)独立选型，目标技术主规格见[全新系统技术方案](05-技术与设计/AI投标工作台全新系统技术方案.md)；旧架构文档只维护现有实现事实，不作为复用前提。
- 需求、证据、设计、技术决定、测试与真实效果可追溯；评审使用的输入冻结，规则与结果的更正追加新记录，旧报告可还原。

## 3. 实施阶段

新系统的交付依赖和退出条件统一见PRD第19节、全新技术方案第16节。当前建设重点是评分预测：基础契约具备后，首批案例核验和评分实验与最小项目工作区并行，不等待完整知识平台。

| 阶段 | 工作与交付 | 完成条件 |
| --- | --- | --- |
| 立项依据 | 背景与评标规则研究、业务需求说明书、范围外与数据依赖 | 明确中标障碍、两个 P0、一期范围、度量口径和数据依赖 |
| 方案与设计 | 工作台PRD、全新系统技术方案、四层评分方案及相应审查 | 业务、技术、评分和验收一致；规格与实际证据分别标明 |
| 可用系统 | 新系统代码、契约、受控评分实验、最小工作区与部署检查 | 按正式阶段完成真实链路与验收；旧系统代码和测试不替代新系统交付 |
| 真实环境验证 | 服务器与数据到位后的端到端跑通；真实数据上的废标检测评价与评分预测对照试验 | 依赖服务器与数据，尚未验证；有可核实的参考标注与官方成绩配对后按验证计划执行 |
| 真实试点 | 实际使用，登记提交与开标结果，复盘入围、否决与中标 | 有可核实结果；按一致口径计算入围率、中标率与废标闭环；结果尚未确定时不声称效果已验证 |
| 稳定运营 | 正式部署、账号管理、监控故障、备份恢复与回退验证、培训交接 | 公司可日常使用，责任明确，关键恢复操作有验证记录 |

规则研究、数据补充和系统实现可并行。系统设计完成不等于评分预测或废标检测的精度得到验证。

已执行的验证（详见[验证报告](04-验证与测试/验证报告.md)）：后端 ruff、ruff format、mypy（严格模式）、bandit（中高危 0）与 pytest 153 项全部通过，测试运行在真实 PostgreSQL 16 上，worker 用受限的 `app_worker` 角色；前端 prettier、eslint、tsc、vitest 292 项与 vite 构建全部通过；研究仓库 pytest 155 项与代码检查通过；评分预测从入库、批量预测、评测到登记与产品内校准的整条流程在合成数据上跑通；浏览器端到端冒烟在 Chromium 中用真实 API、真实 PostgreSQL、进程内 worker（脚本化模型）和构建后的前端，用 `demo` 账号走通“登录 → 项目总览 → 评审报告 → 导出 Word → 处理否决风险 → 全部按原文确认 → 报价试算与保存 → 功能开关 → 度量 → 窄屏无横向滚动”。

## 6. 文档维护规则

每类信息有一个主记录，其他文档用链接引用。只维护实际有内容的文件；业务需求、技术设计、测试或运维成果形成独立内容时再拆出，并更新入口。

正式文档保留文档编号，正文说明目标、范围、证据、方法、结论及执行要求。分析和测试注明实际覆盖范围。文档只呈现终稿，写法要求见[贡献指南](CONTRIBUTING.md)。

来源带机构、发布日期、核实日期、地区与项目类型；具体规则以生效招标文件及补遗为据。供应商自述与实际试用分开。案例规则、成绩和版本见案例记录。

重要业务选择写入[决策与依赖](00-项目管理/决策与依赖.md)；有独立技术权衡时记录 ADR。沿用 FR／NFR／OBS／DEC／ADR／CASE 等编号，记录关联、理由、影响及复审条件，不补造证据。业务或技术选择变化时直接更新对应主记录。

原件只读；临时处理文件在完成后清理，正式目录保存业务资料与成果。

## 7. 交付提纲

下表作为写作提纲，按真实范围调整。

| 交付 | 必备内容 |
| --- | --- |
| 研究／市场报告 | 问题、方法、来源及适用范围、对比／实测、结论可信程度、建议及未决信息 |
| 业务访谈 | 对象岗位、日期目的、实际流程、问题实例、现有工具、诉求和未核实的陈述 |
| 业务需求 | 中标障碍证据、投标流程、结果基线与指标、价值假设、范围优先级、范围外、依赖与业务验收 |
| PRD | 关联业务目标、FR／NFR 编号、用户流程、字段口径、功能输入输出、登录与审计、异常状态、验收与追溯 |
| 技术／ADR | 架构数据流、文件处理、接口、规则知识模型、认证与任务、异常重试、部署运维；选择理由、备选及复审条件 |
| 交互／视觉设计 | 任务流程、信息层级、视觉稿、原文证据交互、组件文案、全部状态、可访问性、响应布局及使用验证 |
| 测试／评测／缺陷 | 关联需求、环境和数据版本、用例方法、结果分母及证据、失败与限制、复现、原因、处理和回归 |
| 发布／运维／培训 | 发布范围验证、配置迁移、回退；监控故障、备份恢复验证、规则升级、账号交接及使用指南 |
| 试点／复盘 | 目标范围、基线和版本、真实成绩与业务结果、入围与否决原因、归因限制、改进及下一轮 |
