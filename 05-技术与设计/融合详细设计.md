# 标书工作台融合详细设计

## 0. 整包落地约束与契约资格

本文为融合系统事务、模块、执行和部署的详细设计主记录；架构以[融合技术方案](融合技术方案.md)、业务以[PRD](../02-业务与产品/AI投标工作台PRD.md)为准。Codex配套SQL／OpenAPI／规约的固定链接用于理解已审目标及原反例，不表示其中所有SQL可直接执行。实际契约只维护在融合应用`workbench/packages/contracts/`，不在文档仓另复制第二份机器契约。

| 写入责任 | 整包扩展与必须保持的事务边界 |
| --- | --- |
| workspace／identity | 工程、标段、轮次、主体与bid_profile分别定位；当前指针不能覆写冻结身份 |
| documents | 权威依据包／本方投标包、不可变修订、文件成员、逻辑部分、页段、解析及核验；字节相同的解析订正仍有新身份 |
| requirements | 材料清单和要求绑定主体／标段／册／时点；补遗的取代、并存、冲突与未知不按上传顺序猜测 |
| review | 冻结包、规则、事实、方法、适用范围；逐项覆盖、跨册矛盾和整包聚合；partial／unknown不能汇总为passed |
| scoring | 从冻结包构造干净技术子范围；保留三次有效独立判断、覆盖、拒绝和失败，不混入事后标签 |
| authoring | 稳定章节、保存CAS／ACK、模板、构建快照、双格式产物；生成结果被选入新包后才有评审身份 |
| closure | 标准提交闸门核当前包和确认决定；实际提交冻结包及回执；offline_fact不制造当时检查通过事实 |
| operations | Kafka／Outbox／独立Worker；lease、fence、领取、续租、崩溃回收、取消和晚到结果按同一领域身份收敛 |

F01-01—08实现并通过前，现有`current_body_id`／`body_version_id`等只支持旧单正文语义。文中`body`、正文版本及其状态图是相应子范围设计输入，不授权以隐式选最后一稿代替包成员；F01须同步DDL、schema、OpenAPI、实现及反例测试。包修订至少冻结成员文件版本、用途、主体、顺序、逻辑页段、解析身份及摘要，评审／比较／提交均引用包修订。文件和解析身份不能互相替代。

### 整包执行输入与发布协议

执行控制面、原件核验、Worker计算与结果发布分别负责以下边界。内部原件核验和发布守卫已实现，真实PG锁验证状态见[冻结原件专项](../04-验证与测试/fusion/frozen-originals/冻结原件与发布守卫验证.md)；正式任务表、启动接口、Worker和报告适配仍属待实现设计，不由当前false资格反推可用。

| 边界 | 输入与责任 | 拒绝条件 |
| --- | --- | --- |
| 明确任务输入 | 指定四项scope、冻结input_id及frozen_digest、当前候选语义context_digest、用途和显式重跑意图；原根保留原context，当前观察另存 | 缺身份、scope串用、摘要不符、隐式latest、用body_id代替整包 |
| 锁外原件核验 | RR只读快照消费同一不可变根，按原成员顺序取得精确parse及存储定位；关闭全部连接后逐件有界流式校验大小与SHA；第二次RR快照比较完整证据、当前观察、上下文与阻断 | 原件不可用／损坏、精确解析损坏、来源／事实／人工依据／方法／政策或头变化；核验失败不产生内部回执 |
| 发布前守卫 | 调用方持有READ COMMITTED事务，先锁项目，再取来源图锁，再从同一根重读当前状态；与内部核验回执逐项比较，仅排除观察时间与快照摘要 | 自动提交、旧RR快照、任何语义／证据／阻断差异、任一执行资格不满足；原件已核过不能替代资格 |
| 正式启动事务 | 先查幂等ACK；新请求经锁外核验后，在持锁事务中重查幂等、运行发布守卫，再一起写执行输入、任务／阶段、Outbox、审计和ACK | 同键异体、发布守卫拒绝、提交约束失败；事务全部回滚，不留下可见任务或伪ACK |
| Worker | 仅消费冻结执行输入与明确方法／用途；使用独立非owner角色，按lease／fence领取、续租和提交，不读当前body替换输入 | 不完整输入、篡改根、方法不匹配、丢租约、取消或晚到；普通Worker不能补写冻结输入或持API凭据 |
| 结果发布 | 外部模型／对象IO在事务外；结果不可变且回指同一冻结输入、执行身份和阶段收据；发布事务复核当前资格和lease／fence | IO期间来源撤回或输入变化、资格失效、被新fence取代；不把过期结果当当前有效报告 |

任务输入的内容身份覆盖冻结input_id／根摘要、四项scope、完整上下文语义摘要、方法／政策／用途；自愿重跑原因和nonce进入执行身份，不改变原输入身份。ACK和执行回执独立于只读观察；当前只读复核不写Command。公开任务状态至少区分准备、等待执行、运行、成功、失败、取消及未知外部结算，不用一个成功状态混同模型完成和报告发布。正式schema／SQL／OpenAPI应随对应实现一起落在应用契约目录，未注册操作不提前出现在实际API清单。

当前内部 `VerifiedFrozenOriginals` 只在进程内传递，原始快照文本不进入repr，公开观察只含成员／parse引用和大小／摘要；不含正文和对象定位。防御性副本防止调用方修改回执。发布守卫不调用对象存储、不自行提交事务、不写任务，当前全部资格仍false。正式运行前还需确定对象存储的不可变版本／条件写保障；流式SHA证明核验时的字节，不承诺存储之后不会被外部替换。

解析标题深度与人工编辑树限额分开：Codex人工树最大6层／500活动节点不限制任意解析标题或评分完整相关子节。Word保存、生成、渲染、版式核验、评审、实交各有独立状态；页数预算不是实际页数，TOC不是仅有目录字段就验证通过。原同SHA第二批次503、图片遮挡数字误complete和表格几何反例必须保留。

预算SQL中NULL／unknown结算、预留2048与最大输出8192不一致，以及helper04的NOLOGIN祖先继承越权属于实施阻塞；分别由F08-01／02、F02-02修复并验证后使用。归档denominator C与retrospective WIP只可先审，不串跑旧SQL补丁。固定证据不转移模型正式资格；组合的API、Worker、浏览器、实际文件和独立恢复分别验收。

## 1. 落地基线与决策门槛

### 1.1 推荐组合

| 层次 | 推荐基线 | 采用边界 |
| --- | --- | --- |
| 页面 | React 19、TypeScript、Vite；React Router、TanStack Query；局部视图用React状态 | 内部SPA；路由与查询缓存独立；组件使用可替换的Radix基础与统一视觉令牌，锁定前做React 19兼容检查 |
| 章节编辑 | Tiptap开源编辑核心／ProseMirror JSON文档 | 首批固定基础段落、标题、列表、表格和图片；不依赖付费协作、云转换或AI扩展 |
| API | Python 3.12、FastAPI、Pydantic、SQLAlchemy 2、Alembic、psycopg 3 | 模块化单体；HTTP和worker共用领域用例，不通过内部HTTP串写事实 |
| 事实与向量数据库 | PostgreSQL 17＋pgvector；业务与向量分schema、用途视图和连接预算 | pgvector是向量存储与检索层，RAG从首批实现；规模实测决定是否独立部署向量服务 |
| 事件与固定任务 | Apache Kafka＋confluent-kafka Python客户端＋独立Worker | Kafka由用户指定；消费位点、重试与业务幂等按第6节实现，生产配置须故障验收 |
| 原件与产物 | 私有对象存储；OSS／S3分别适配 | 供应商随部署地域确定；上传校验、条件写、版本保护独立验收 |
| 文档处理 | PDF解析端口＋OCR端口；DOCX生成与受控转换容器 | 首批Docling结构化、PDFium渲染与PaddleOCR扫描页适配；LibreOffice受控转换，全部须真实文档验收 |
| 模型与研究 | 类型化模型端口；scikit-learn Pipeline；不可变实验清单 | 不把LLM直接给分当监督模型；基础实验记录先行，MLflow按需要接入 |

项目间隔很长不等于单个任务需要持续等待数月。上传、评审、生成和人工确认分成独立操作：任务结束后保存事实，成员以后确认时启动新命令。首批不为等待人工操作长期占用worker。复杂AI路径确有分支和恢复需求时，在单个步骤内部增加有界LangGraph；它不承担第二套业务提交或后台调度。

Kafka是确定的消息基础设施，普通Python Worker执行固定阶段函数；Celery、RabbitMQ和Temporal不作为当前运行依赖。Kafka负责传输和保留事件，不承担领域事务、人工授权或任务最终状态。跨步骤恢复以明确阶段收据、Outbox和幂等协议实现，不能宣称Kafka事务覆盖数据库、对象存储或模型外部调用。

本系统全新建设，没有旧系统数据迁移、旧接口兼容、旧库状态映射或双系统切换要求。历史招标、实交稿和官方成绩按新资料导入；独立备份、恢复与未来结构升级属于正常运行能力。

版本锁定在实现仓库的锁文件与镜像digest完成；Kafka版本、Python客户端和pgvector组合在实际环境验证后冻结。消费位点与向量检索依据见[公开技术依据](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/README.md#公开技术依据)。

### 1.2 模块与写入责任

| 模块 | 独占写入的事实 | 对外用例 |
| --- | --- | --- |
| identity | 成员、会话、登录审计 | 登录、退出、会话续期；成员均可操作全部项目 |
| workspace | 工程、轮次、投标单元、设置、当前输入指针 | 新建项目、变更资料归属、设置、归档 |
| documents | 上传会话、原件、解析、页面与证据块 | 授权上传、校验完成、解析、证据查询 |
| requirements | 生效规则、工程事实、确认决定 | 提取、补遗冲突定位、规则和事实核对 |
| authoring | 目录、章节修订、计划、AI补丁、构建快照 | 保存、预览、应用、撤销、生成 |
| review | 冻结评审、响应矩阵、问题与复核决定 | 开始评审、比较、问题复核、主要下一步 |
| scoring | 干净评分输入、三次判断、特征与预测 | 逐项判断、资格检查、预测；不登记官方成绩 |
| closure | 实交稿、官方结果、核验、更正 | 提交闸门、线下事实补录、结果配对 |
| knowledge | 知识版本、用途、来源闭包、停用影响 | 查询、候选、发布与停用 |
| operations | 命令幂等、后台操作、分阶段收据、事件 | 启动、重试、取消、SSE与通知 |
| research | 样本准入、划分、实验、验收、模型路由 | dry-run、实验、人工发布、回退 |

模块直接调用显式应用服务；只有所属模块写它的表。一个涉及多个模块的命令由应用层在同一数据库事务协调，不把它拆成最终一致的多个HTTP调用。文件转换、模型调用、网络请求一律在事务外执行。

## 3. 领域身份、修订与不可变记录

### 3.1 身份与可变头

工程、标段轮次与投标主体分开标识；`bid_id`是界面中的项目工作单元，项目名不作唯一键。时间存UTC的TIMESTAMPTZ，界面和计划默认Asia/Shanghai。金额、分值与满分用十进制，JSON交换为十进制字符串；拒绝NaN、Infinity与超范围分数。

| 身份 | 可变内容 | 不可变内容与引用 |
| --- | --- | --- |
| bid | 当前资料修订、当前草稿、当前评审、设置revision | 工程／轮次／主体关联；历史快照独立保留 |
| document | 名称与归属头 | 原字节blob、每份document_version、角色分配修订 |
| parse_run | 执行状态 | 完成后的页、块、坐标、配置与原件摘要 |
| draft／section | 当前revision指针 | 每次章节JSON、目录顺序和草稿整体快照 |
| document_build | 执行摘要 | 已冻结草稿、模板、字体、转换参数；各格式输出分别有身份 |
| review_run | 执行与展示资格 | 输入manifest、原始判断、覆盖、产物、方法 |
| submission／outcome | 当前有效记录指针 | 原登记、更正记录、出处、实交字节及当时预测 |
| knowledge／model_route | 当前head、停用或路由revision | 旧版本、训练清单、验收与发布决定 |

内容寻址只对字节去重；同一blob在不同项目、角色、取得时间和用途下仍是不同资料版本。文件名、抽取文本、编辑器HTML均不作为Word／PDF一致证明。

### 3.2 输入修订与摘要

`material_revision`记录资料集合与角色分配变化；`draft_revision`记录目录和章节整体快照；`settings_revision`记录项目开关；`presentation_revision`只记录当前展示政策。它们不混成一个容易误失效的全局计数器。

冻结输入manifest至少包含：bid、正文document_version、全部生效招标补遗版本及顺序、角色分配revision、规则包与事实包、parse_run及配置digest、方法／提示／模型／用途策略digest、引用来源head、内容检查开关、稳定评估时点as_of及审计冻结时刻frozen_at。完整冻结证据摘要、内容身份、执行去重身份分别保存，算法及固定输入输出以[评审身份参考](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/identity_reference.py)和[固定向量](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/review-identity-vectors.json)为准。

#### 3.2.1 三种摘要的精确投影

所有输入先通过ReviewManifest Schema，再规范化：UTC时刻固定六位小数及Z；parse_run_ids按UUID字典序排序且不得重复；source_refs按id排序且不得重复，known_at保留业务值；有业务顺序的资料角色/补遗顺序保存在引用的物料与证据清单，不能排序掉。使用RFC 8785规范JSON的UTF-8 SHA-256；该协议输入仅含整数、布尔、null、字符串及容器，十进制必须字符串，无float/非BMP键，参考程序限定这一子集。

| 摘要 | 唯一计算对象 | 用途 |
| --- | --- | --- |
| review_inputs.manifest_digest | 规范化后的完整ReviewManifest，包含frozen_at | 审计与完整证据身份；不同冻结时刻可不同 |
| review_inputs.input_digest | `{"identity_version":"review-content/1","input":P}` | 内容归并与合格缓存身份 |
| operations.input_digest | `{"identity_version":"review-execution/1","input_digest":input_digest,"rerun_nonce":null或显式UUID}` | 执行去重；普通入口nonce=null，重测显式nonce |

P只包含下列精确字段，不是任意删时间：bid_id、body_version_id、material_snapshot_id、material_revision、rule_set_id、fact_set_id、parse_run_ids、method_digest、policy_digest、purpose、source_refs、content_checks、as_of、evaluation_context_digest、evidence_manifest_digest。frozen_at只在完整摘要；as_of、来源known_at和证据中的有业务效力时间均参与内容身份。新增业务输入字段必须升级identity_version、固定向量及所有生产者/缓存消费者，禁止各团队自选投影。

evidence_manifest_blob_id指向服务端写入并核验SHA的不可变证据清单，ReviewManifest.evidence_manifest_digest必须等于该blob.digest。清单固定正文/资料/规则/事实/解析/方法/提示/模型/策略的版本ID和实际内容/配置摘要、资料角色顺序、来源head revision、完整祖先闭包及known_at/effective_from/effective_until和适用范围；对应被引用blob字节通过同一摘要闭包校验，不能只记录可移动head。manifest_digest是这一冻结记录及证据根的完整证明；content_digest不能代替档案完整性校验。签名URL、请求ID、显示名称及聊天不进入语义摘要。

#### 3.2.2 稳定as_of、来源效力与并发归并

RequestReview的自动、按钮、构建和聊天入口必须调用同一服务端FreezeReviewInput用例。事务先锁bid，再锁review_slots及所需来源head，以数据库时间t读取当前输入、来源/祖先head、生效关系与时间窗。context_fingerprint是规范化的基础输入身份（正文/物料/规则/事实/解析/方法/策略/检测开关）及当前允许来源和全祖先head版本/有效状态/窗口的摘要，排除请求t、trigger、frozen_at与nonce。服务端计算context_valid_until为所有会改变来源资格或规则效力的下一未来known_at/effective_from/effective_until/评估截止边界中最早者，无边界为null；不能只看当前允许集合而漏掉将来生效来源。

在head仍相同、fingerprint相同且t<context_valid_until（或null）时复用review_slots.context_as_of。否则重算允许集合，固定新context_as_of=t，保存新fingerprint和下一边界；首次同样如此。由此同一有效窗口中的后续请求共享稳定as_of，而跨生效边界形成新时间上下文；时点是服务端已有快照的评估点，不是每次请求的墙钟。evaluation_context_digest固定该fingerprint、as_of和valid_until的规范记录。有效时点不能由普通客户端任意指定；研究历史as_of另受冻结实验协议与当时已知来源限定。

组装新manifest时frozen_at=t。计算三种摘要后，优先查询当前内容的在途execution_digest；已有则返回原review/operation和原manifest，不再插新冻结记录或重复调用。无在途且有可复用成功结果时，先重验当前来源、效力和用途，满足缓存协议才复用。活动槽有其他输入时写latest pending意图，不把晚请求抢成当前。active_same_input唯一索引、bid行锁与命令幂等共同处理竞争，不能仅靠前端节流。

显示预测和结果提醒只改展示，不重算模型；auto_review决定触发，不进入内容差异。内容检测开关、真实来源/效力、规则事实、方法变化建立新内容；自愿重测显式rerun_nonce及原因，执行摘要不同但input_digest保持同一内容，不把它算作新独立官方样本。正式评分受限上下文同样必须通过score_context_chunks使用review_inputs.as_of过滤，frozen_at不能代替该业务时点。引用应用与结果发布前仍复核当前head和有效性；来源停用不能因旧as_of或旧缓存而继续新增应用。

### 3.3 目标关系约束

[核心约束DDL](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/core.sql)给出独立`design` schema的可执行关系模型：跨项目复合外键、不可变快照、幂等键、单份有效提交、操作和副作用收据、评审输入、保存修订及事件序号。它保存事务内核；[domain.sql](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/domain.sql)补充领域表，[retrieval.sql](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/retrieval.sql)提供向量与来源模型，[roles.sql](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/roles.sql)限定能力账号。字段与约束以这些可执行SQL为准，JSON语义和领域gate仍由用例验证。

| 对象族 | 必需字段与索引 | 额外约束 |
| --- | --- | --- |
| pages／evidence_blocks | version、parse、physical_page、ordinal、kind、text、bbox、rotation、quality | 页号≥1；块定位必须同parse和同原件；`(parse,page,ordinal)`唯一 |
| rule_sets／rule_items | material_revision、source_version_ids、conditions、exceptions、max_points、evidence_ids | 每条规则携带来源；rule_kind、确认决定与问题判定分离 |
| fact_sets／fact_items | subject、scope、value、unit、evidence、confirmation | 空缺不默认为0；不同工程前提不可直接合并 |

| templates／build_outputs | template_version、schema、fontset_digest、source_snapshot、format、digest、render_gaps | 一个构建可有多个格式；每种输出分别成功或失败 |

常用复合索引以`bid_id`开头：评审列表`(bid_id,created_at DESC,id)`、证据`(bid_id,parse_id,page,ordinal)`、问题`(bid_id,review_id,severity,id)`。列表采用稳定游标`(created_at,id)`，不依靠大offset；公开游标签名并绑定过滤条件。

## 4. 命令、并发与错误协议

所有正式写请求要求会话、CSRF、`Idempotency-Key`；依赖已见状态的请求还要求强ETag的`If-Match`。幂等scope为成员＋命令类型＋目标ID；相同键不同规范请求摘要返回409。一次动作提案由所有成员全局最多消费一次，不能因成员不同创建第二次效果。

| 场景 | 状态码／领域错误 | 客户端处理 |
| --- | --- | --- |
| 未登录／CSRF无效 | 401／403 | 保留输入，重新登录后重新读取状态 |
| 缺少条件头 | 428 `PRECONDITION_REQUIRED` | 获取最新对象与ETag |
| 已见修订过期 | 412 `REVISION_MISMATCH` | 显示本地／服务器差异，由人决定重试 |
| 幂等键内容冲突／动作已被消费 | 409 `IDEMPOTENCY_CONFLICT`／`ACTION_CONSUMED` | 显示既有结果，禁止静默换键重试 |
| 输入未就绪／提交被阻断 | 409 `INPUT_NOT_READY`／`SUBMISSION_BLOCKED` | 显示结构化阻断项及可执行入口 |
| 格式错误／不支持的格式 | 422 `VALIDATION_ERROR`／415 | 定位字段或提供转换入口 |
| 异步受理 | 202 | 返回对象引用和operation；不显示已完成 |
| 来源停用／受影响 | 409 `SOURCE_UNAVAILABLE` | 保留候选，要求重新选择或重新生成 |
| 限流／模型暂时不可用 | 429／503 | 尊重Retry-After；不自动重复正式决定 |

统一错误含`code,message,request_id,retryable,details`；details不泄露文件原文和密钥。所有写入稳定锁序为bid头→领域head按ID→operation→action→stream头；事务内不访问网络。读快照之外的最终提交条件必须锁头重查。序列化失败或死锁由服务端对同一命令有限重试，不能重做外部调用。

命令事务顺序：登记／读取幂等命令→锁目标与校验revision→核验用途、来源和业务条件→写事实与副作用收据→写outbox／SSE／审计→提交→返回。返回成功前必须完成提交。业务拒绝的审计在独立短事务可靠保存，再返回错误，避免HTTP异常使拒绝记录一并回滚。

## 5. 上传、批次与自动评审

### 5.1 接收协议

1. 创建上传批次，明确bid、资料角色、文件大小、声明摘要及是否结束本批。每个文件取得服务端生成的暂存键和短期签名；客户端永不取得存储凭据。
2. 浏览器直传；重传只针对缺失分片。完成接口幂等，服务端从实际对象核验大小、格式及SHA-256；声明摘要只作预检。
3. 文件进入隔离扫描与解析。扩展名和MIME不一致、加密PDF、宏／嵌入对象、解压炸弹等返回清晰状态，不送模型。
4. 批次结束且全部必需文件核验完成后，在一个事务更新角色分配、`material_revision`，产生一次`materials.committed`；失败文件仍可见。部分成功必须由人明确以当前有效集合结束批次，不悄悄漏掉补遗。
5. 自动评审开启且有正文和必要招标资料时安排评审；规则确认不构成启动前提。只有DOCX时先走受控转换，旧DOC提示转换。快速PDF路径不依赖编辑器、目录或模板。

暂存对象初始保留24小时、签名15分钟是起始配置；解析任务耗时不能依赖签名有效期，worker用服务账号按对象ID读取。上传会话过期后重新授权，不创建另一个原件。上传后仍须受项目归属和完整性检查约束。

### 5.2 同输入归并与最新待评

按钮、聊天、自动事件和生成后评审都调用同一`RequestReview`。锁定bid的review槽，比较规范input_hash：同输入在途返回原review与operation；不同输入且槽忙，保存最新`pending_input`意图并替换较旧待评意图，在运行结束后重新验证资料与开关再冻结。运行中的旧manifest永不被新资料改写。

待评意图保存来源：明确人工请求保留，自动意图在开关关闭时撤销；用户取消某轮同时可以取消该输入的待评，不能立即由同一自动事件再次启动。定期对账仅补已受理未投递记录；不凭当前有文件而无界创建新评审。补遗冲突未解决时允许展示旧结果与新输入缺口，但不能把旧结果指为最新有效。

## 6. 后台执行与恢复

### 6.1 队列与阶段粒度

| 路由 | 工作 | 起始并发限制 |
| --- | --- | --- |
| document | 校验、逐页解析／OCR、受控转换 | 每池2个进程；转换进程一次一个独立工作目录 |
| review | 规则结构、章节包、逐项判断、汇总 | 最多2轮评审；每轮模型最多4个在途请求 |
| export | DOCX、PDF、报告展示副本 | 1个进程，避免字体／渲染相互影响 |
| research | 数据导出、训练、离线评价 | 1个任务，独立资源额度 |

并发数只用于起始试验，按模型供应商RPM／TPM和实测调整。每类任务独立topic和consumer group：`tender.task.document.v1`、`tender.task.review.v1`、`tender.task.export.v1`、`tender.task.research.v1`；同组worker竞争分区，不同职责组不能共同消费同一任务以免重复执行。领域变化进入`tender.domain.events.v1`，索引、影响分析和站内通知使用各自group，各取一份事件。

消息采用版本化JSON信封，只含`event_id,operation_id,step_key,input_digest,generation,handler_version,payload_ref`等身份，不携带整份PDF、聊天或模型密钥。任务key为`operation_id:step_key`以分散独立子项；领域事件key为bid，业务正确性依靠revision与PG事务，不依靠跨分区顺序。topic起始6分区是压测配置，实际并发不超过分区数；增加分区后仍依靠业务身份防重。

Producer使用`enable.idempotence=true`、`acks=all`，Outbox仅在delivery callback确认后标记已发送；进程重启后的重复发布仍以event_id与领域收据防重。生产建议3个broker、任务topic副本数3与`min.insync.replicas=2`，KRaft控制器仲裁按实际拓扑验收；单节点仅开发验证，不宣称容灾。Kafka地址、TLS／SASL与ACL仅在服务端，worker只能读所属topic／group。

Consumer使用`enable.auto.commit=false`及`enable.auto.offset.store=false`。起步实现每个分区最多一个在途任务，消费poll循环与执行进程分离，处理期间pause该分区并继续poll其他分区和心跳。只有领域结果提交成功，或重试／隔离已在PG可靠接管后，才提交该分区`offset+1`；禁止先提交位点再计算。并发扩展若允许同分区多条在途，须另实现连续完成水位，不能提交最大已完成offset跳过未完成记录。

再均衡时停止给撤销分区派新工作，只提交确认处理完成的连续位点；未完成记录保留重放。新消费者接管执行前核对并提升PG fence；旧执行者仅在仍持有当前有效fence时有权提交。客户端失去分区所有权后不再提交offset，业务已提交但offset提交失败由重放读取既有收据恢复。

### 6.2 阶段与收据

评审固定阶段：校验输入→准备规则和事实→建立正文树／证据→核心核对→逐项评分三次判断→证据验证与汇总→发布当前可用结果。规则与解析已存在且输入配置相同时复用不可变产物。核心核对与评分可以并行，但两者各自报告完成度；评分失败不抹掉有效风险结果，不满足核心覆盖不能登记提交。

每个阶段以`(operation_id,step_key,input_hash)`唯一，取得单调fence后才开始计算，结果提交必须匹配fence。重复投递若发现已完成收据直接返回；正在有效执行则不启动第二份。活跃状态心跳30秒、失联120秒仅为起始阈值，单次外部调用必须有小于其任务预算的超时。对账判失联时先提升fence使旧执行者失效，再按同一阶段和输入重新投递；旧执行者可能继续消耗模型费用，但无权提交结果。该机制只是领域副作用防重和有限固定任务对账，不扩展为通用工作流DSL。

阶段完成事务同时写收据、领域产物和下一阶段outbox，避免“数据库已完成但没发下一任务”永久停住。并行子项不依赖消息中间件的结果后端；预先登记固定子项集合，子项完成事务写收据，汇总消息重复触发时检查全部必需收据，利用汇总唯一键最多提交一次。

### 6.3 失败、重试和取消

| 故障 | 处理 |
| --- | --- |
| outbox提交后API断线 | 同幂等键返回已受理operation |
| Kafka发布确认丢失 | 重发同身份消息；worker从已提交收据去重 |
| worker在领域提交后崩溃 | 重投读取收据，不重建第二份结果 |
| 原件读取／模型429、5xx | 在阶段总时限和费用预算内指数退避加抖动，最多3次外部尝试 |
| 输出结构不合约 | 最多2次定向修复，计入同一外部尝试预算；仍失败保留无法判断 |
| 扫描导致OOM／转换崩溃 | 逐页和隔离资源处理；持久预算到限转人工，不无限重投 |
| 非法输入／来源撤回 | 不自动重试，保存可定位的失败原因 |
| 操作取消后外部响应到达 | 保存受限诊断记录；不写有效结果与当前指针 |

operation状态：`queued → running → succeeded | failed`；取消使用`queued/running → cancel_requested → cancelled`，取消提交后禁止发布正常完成。完成和取消争用同一operation锁；完成先提交则取消返回既有结果，取消先提交则后续回调无法发布。Kafka没有按任务可靠撤回已消费消息的业务语义，领域取消状态是执行依据；取消不撤销已经人工确认的决定。离开页面、关闭助手、暂停任务模板均不代表取消。

重试不是Kafka原生延时队列：阶段失败时先在PG记录原因、尝试数和`outbox.available_at`，持久接管成功才提交原消息offset。投递器只发布到期记录，提升generation与fence；重试次数和费用预算都在PG，不能靠Kafka redelivery次数猜测。不可恢复或预算耗尽时保存failed与可定位原因，通过Outbox发布到`tender.task.dead-letter.v1`，原位点随后提交。死信重放必须显式创建新操作并关联原记录，不重放已完成正式决定。

计划与提醒由独立短周期唤醒器检查PG到期计划，锁定计划行，写唯一`(schedule_id,scheduled_at)`触发收据、下一时刻与Outbox后一次提交。唤醒器可用成熟定时库，但计划事实唯一位于PG；崩溃重启从持久到期时刻续查，错过多次默认合并一次，保存时区并防重复。Kafka不保存长期ETA，不让worker睡眠等数月。

## 7. 解析、证据与补遗

每个parse_run固定原件digest、解析器及配置digest、页数和页质量。原页以1起始物理页定位；印刷页码只是显示标签。页面输出尺寸、旋转、裁剪和坐标变换，bbox统一为旋转归一化后的左上原点页面坐标，并记录单位。前端根据渲染矩阵转换；矩阵校验失败退回整页，不画猜测高亮。

优先使用可靠文字层；低文本密度、乱码或图像页交给OCR。表格保存结构与原图，图页保留可核验的视觉观察；文字提取成功不等于图表理解成功。范围覆盖记录总页、已读页、关键未读页与失败原因，不以非空文本替代完整性。

补遗以明确适用对象、效力顺序、取得时刻和替代关系建包；冲突由用户确认，不按最新上传时间猜生效。依赖边连接资料→规则／事实→章节／问题→构建／评审／提交。影响定位输出确定受影响、确定不受影响、未知范围三类；未知不能被局部重跑自动清零。来源撤回或新补遗使历史报告增加影响提示，但不改写旧报告原字节和旧输入。

解析器选型样本必须覆盖扫描、旋转、跨页合并表格、公式、图纸、页眉页脚、目录、暗标和双栏；以页级标注比较条款召回、表格保真、证据定位与资源，再选默认路线。依赖真实资料，尚未验证。

## 8. 章节编辑、AI补丁与构建

### 8.1 编辑保存

章节正文存ProseMirror JSON，`schema_digest`固定允许节点、属性和迁移函数；服务端验证节点白名单、大小、图片引用与链接协议，不能只信任编辑器输出。图片先转为受控资源ID，不保存任意可执行HTML。首批单人编辑加乐观并发，不引入CRDT、在线多人光标或无损Word往返承诺。

前端本地即时编辑，初始800毫秒防抖保存。同一草稿保存请求串行，携带已确认`draft_revision`和各章节`base_section_revision`；新改动排到下一次，不用已过期ETag并发提交。服务器事务追加章节修订、草稿快照并移动指针，响应返回新revision与ETag。冲突显示两份内容，可复制或人工合并；不自动最后写入覆盖。

保存失败时保持脏状态并在离页提示。可用IndexedDB按成员和bid短期保存待恢复内容，退出／切换账号清理，恢复须由用户选择；浏览器缓存不是正式版本。路由切换和后台通知不能卸载未保存编辑器。

### 8.2 AI建议与应用

AI提案包含目标section、base_revision、结构化patch、before_digest、规则／事实manifest和所用来源版本，不允许模型直接运行SQL或修改当前稿。预览展示新增／删除和来源；应用事务按当前revision、来源head、用途与有效时刻重新核验，失败返回412或409。patch使用稳定节点ID与前置摘要，拒绝范围漂移。应用与撤销都追加新修订；问题是否解决由对应新稿复检决定。

知识停用事务与应用事务按同一head锁序竞争：停用先提交则应用失败；应用先提交则保留当时成立的引用，随后记来源影响，要求复核。不能把索引里的旧`published`字段当作最后授权。

### 8.3 构建快照与文件对应

“生成”先等待全部保存ACK，再携带明确`draft_revision`请求。保存失败直接阻止本次构建；用户另选“使用已保存版本”必须显示版本和时间。构建冻结目录顺序、章节修订、引用、模板、字体、资源及转换配置，后续编辑不影响该构建。

构建阶段：快照校验→DOCX组装→受控渲染PDF→结构与页面检查→登记各格式产物。DOCX生成成功而PDF失败时如实显示；不能把DOCX成功显示成“Word与PDF均已就绪”。目录、编号、分页、字体替代、图表、签章与暗标分别检查。正文不自动夹带UI徽标、AI指令、风险批注和审查报告；未完成占位符与匿名限制残留显式阻断或提示，不偷偷删除。

转换链记录`source_docx_digest,renderer_digest,fontset_digest,options_digest,pdf_digest,gaps`。外部DOCX与同名PDF默认不构成受控关系；补传可用UploadRequest.declared_source_document_version_id声明同稿来源，DocumentView.source_relation返回user_declared_same_draft＋unverified，不写controlled_render。声明和实际PDF各有独立版本，同名不升级核验。只有服务端受控转换及完整链证据才能写controlled_render＋verified；人工核验关系保留独立证据，未核验时Word交付资格另查。文件经过外部Word编辑后重新上传并建立新转换与评审身份，旧PDF结果不继承。转换失败卡固定显示“Word原件已保存，本次未完成对应检查”，主动作“上传此修改稿的PDF”携带项目/角色和已保存DOCX身份，显示逻辑文件选择；同时给转换缺口，仅可重试错误提供重试。备用PDF作为独立格式逻辑文件/版本评审，报告写实际受检PDF，用户声明关联不赋予Word检查资格。

自动评审开启时默认“生成并评审”，关闭时默认“生成版本”；显式`follow_up=review`始终可用，不修改项目设置。生成回调只为冻结输出发出评审意图，不能把旧构建覆盖到当前新草稿／当前评审指针。

## 9. 响应矩阵、风险与提交闸门

核对输入为全部生效核心规则及相关完整正文范围；输出为满足、未满足、无法判断和证据，严重性独立于置信度。未检索到证据只意味着当前搜索范围内未找到，必须记录搜索范围，必要时扩大全文检查后才能作缺失型判断。

风险、人工复核和解决状态分别记录。接受建议、复制文字、关闭卡片不改变已解决状态；新稿复检后产生跨轮问题关联。当前输入冲突与必需解析失败优先于旧轮次问题。`NextActionPolicy`按PRD第3.7节执行，API返回动作ID、理由和跳转目标，页面与助手读取同一投影。

`EvaluateSubmissionGate`只读预检供界面展示；`RegisterSubmission`在同一事务锁头重算，预检token不是授权。检查项包括：当前有效资料与目标正文一致、核心解析与规则覆盖完整、关键风险与废标／强制响应问题已处理、必要事实有效、规则确认或明确按原文接受、正文artifact_kind正确。模型尚未验收、隐藏预测或只有普通建议不构成阻断。按原文接受仅豁免对应规则确认，不豁免其他条件。

登记保存实交对象、字节摘要、提交时刻、材料／规则／方法身份、当时最新合格盲预测ID、执行成员及闸门快照。外部平台提交由用户完成，系统登记不冒充已经向交易平台上传。

线下事实补录使用独立命令：允许如实登记未经过闸门、甚至错传评审报告的实际文件，保存出处并标`offline_fact`，不能冒充标准放行。更正追加记录、移动有效指针，旧决定不删除。归档检查项目阶段和活跃操作，归档本身不注销证据与实交关系。

## 10. 评分输入、执行与发布

### 10.1 输入隔离

ScoreInputBuilder只接受服务端解析的冻结身份。允许目标招标补遗、目标正文、事前有效事实与明确受控方法数据；聊天记录、会话摘要、正式结果、评委意见、事后知识和任意工具文本不得作为拼接输入。[评分输入Schema](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/protocol.schema.json)固定字段，拒绝额外字段。JSON结构校验之后仍需在服务端检查来源类型、祖先闭包、取得时刻、分组与实验边界，不能把Schema合格当作已隔离。

在线评分worker只使用评分专用读取接口／数据库视图和受限账号，不能任意查询outcomes和聊天；训练worker在受控导出后才取得标签。提示词中的身份说明不足以防泄漏。图像、OCR、附件、摘要、缓存和检索邻居都按同样来源策略处理。文档里的提示性文字作为资料，不作为工具权限或系统指令。

### 10.2 四层运行协议

| 阶段 | 输入 | 必须保存的输出 | 缺口处理 |
| --- | --- | --- | --- |
| RubricPreparation | 全部生效细则／补遗与正文结构 | 分项、档位、要点、满分校验、章节映射 | 满分／适用冲突单列，不能进入完整总分 |
| ChapterPackageBuilder | 每项关联完整章节、表格、图页 | 实际源范围、分块顺序、已读／未读、digest | 超长层级拆分，不静默截断；摘要不当完整覆盖 |
| ItemJudgment | 相同冻结材料、独立replicate 1／2／3 | 档位、要点、针对性、具体性、引文、分歧 | 重试不算新的replicate；缺少有效判断如实记失败 |
| FeatureBuilder／Predict | 三次有效判断与版本化方法 | 特征向量、模型digest、适用性、点分资格 | 不符合模型适用范围则拒绝正式估分 |
| ControlledAnchor | 训练内／固定独立锚点清单 | 邻居、标签来源、fold和缓存digest | 首批关闭，独立消融通过后启用 |

三次调用互不接收彼此输出，不以多数一致冒充独立真值；固定模型、参数和方法，记录供应商实际返回的模型标识和usage。API不保证随机种子可复现时如实记为非确定。单个子项三次与其重试分别计费，重复worker调用不随意新建一次评分测量。

输出分为原始判断／未校准逐项合计、合格正式预测、官方成绩三种类型；区间与技术入围概率另有独立验收，不能用LLM波动直接作置信区间。覆盖不足时只显示可评范围，不补齐总分。

### 10.3 样本、实验与业务路由

样本单位为唯一有效实交稿＋生效招标补遗＋官方技术分及满分＋出处和核验。技术分、综合分、未知与真实0分分别校验。项目／模板／近重复关系生成连通组；按分组与时间留出；所有标准化、填补、特征选择、锚点与校准仅用正确训练来源。实验协议、划分manifest和验收目标在最终测试前冻结。

模型发布为人工命令，检查独立验收、适用范围、可部署产物、影子观察与回退对象；原子切换route revision。业务预测固定模型route和artifact，不因路由变化改写旧结果。未通过的模型保留研究身份；正式成绩回流后的重跑为回测，不改当时预测或挑选最接近成绩的一次。数值验收阈值与实验细节引用评分主记录，不在本文再定义另一套。

## 11. RAG、向量数据库、来源与缓存

### 11.1 必需链路与职责

RAG是首批必需能力，用于资料问答、条款与正文证据定位、章节写作参考、企业知识和历史案例查找。链路为：原件解析→保留页与章节的分块→Embedding→写pgvector→词法与向量并行召回→RRF融合→可配置重排→组装带来源上下文→模型生成→引文核验。仅写入向量不算完成RAG；尚未索引或索引失败必须有明确状态。

PostgreSQL保存业务事实；pgvector扩展承担向量数据库职责。两者可以运行于同一PG实例，但业务schema、检索schema、用途视图、账号与连接／查询预算分开。当前不另部署Milvus或Qdrant；若实测向量规模、更新速度、备份窗口或查询负载超出预算，通过RetrievalPort替换向量适配器，原件与版本身份保持不变。

### 11.2 索引数据与构建

`retrieval_chunks`记录chunk_id、source_version、parse_run、页／章节／表格范围、原文digest、source_node、适用条件与known_at；块正文和原页关联不可丢。文字按标题与语义边界分块，表格保留表头／单位和原图引用，图页保留可核验视觉观察，不能凭固定字符截断破坏工程含义。

`embedding_profiles`固定供应商／权重digest、维度、距离、归一化、分词和预处理；`chunk_embeddings`以`(chunk_id,profile_id)`唯一。首批选BAAI/bge-m3的1024维dense profile，固定余弦与L2归一化；每个profile固定权重与预处理摘要，其他维度建立独立定长表或分区，禁止跨profile直接比较距离。原件／解析更新创建新chunk身份，失效旧索引；新profile完成覆盖和召回验收后切路由，不原地改写实验身份。

解析完成事件经Outbox和Kafka触发索引任务，重复事件按解析与profile digest归并。每份资料显示未建、构建中、可用、部分和失败；原件可读不代表已可语义检索。停用事件加速清理派生索引，最终可用性仍由查询和引用时的权威来源复核决定。

### 11.3 召回、隔离与引用

普通问答、正文核对、正式评分、历史查证和实验锚点是不同purpose。端口为`Retrieve(query,purpose,allowed_manifest,as_of,excluded_groups,profile)`，allowlist由服务端任务构造。先按权威关系过滤，再召回，再重查；不允许模型扩大权限。公开检索API只接受界面上下文，不能直接授予正式评分或任意全库allowlist。

词法通道保留条款号、单位、工程名和专业词；语义按固定embedding_profile检索。起始可各取50个候选，RRF融合后重排前20、上下文最多8项，是待调优配置而非质量结论。小允许集先精确向量排序，HNSW须验证过滤召回不足；扩大扫描只能在允许集内进行。重排端口从首批具备，是否启用及参数由真实标注的收益、延迟和预算共同确定。

每次检索保留query digest、purpose、候选来源、profile、融合／重排版本、入选及排除原因。上下文携带原件版本、物理页、章节、块及引用ID；模型引文须能回到实际入选证据，不把“生成了citation字符串”当作支持结论。回答资料不足时明确缺口，不从相似项目借用本项目事实。

正式评分可以利用RAG定位相关章节，但ChapterPackageBuilder必须扩展为完整相关章节、附表与图页；top-k片段不能代表完整评分覆盖。聊天成绩、事后结果及同组派生知识从正式评分索引允许集和缓存同时排除。

### 11.4 缓存与验收

缓存分三类：字节／解析产物按原件和配置；AI／检索结果按输入、用途、策略、模型、profile与实验身份；展示副本按review、presentation_revision、source_impact_revision。停用立即改变权威head并产生影响事件；缓存删除只是加速，不能作为撤回成立条件。

建立中文市政检索标注集，覆盖条款号、跨页表格、近义施工措辞、相似项目、失效知识与禁止组；记录Recall@k、排序质量、证据正确率、拒答和延迟，单独检查过滤后少召回与泄漏反例。RAG检索验收和最终评分误差验收分别进行，不能以向量召回成功推定预测准确。

## 12. 助手、确认动作与页面

### 12.1 助手协议

消息由文本、资料引用、业务卡片引用、工具观察等part组成。模型只能输出白名单工具提案；服务端从领域对象生成卡片，Markdown不渲染任意执行按钮。读取工具按purpose限制；正式写入通过proposed_action确认，包含目标、base_revision、参数摘要、来源、失效时刻和可读预览。前端按钮与聊天确认调用同一确认接口，不从自然语言“好的”直接推定任何未指明的业务决定。

小对话入口默认继承当前bid和当前显式页面对象，历史深链接始终优先；一般解释可以读取当前历史对象，正式评分必须重新构建干净输入。项目记忆按当前有效事实、待决问题、草稿和已确认决定重新组装，记录来源revision；摘要不能升级为工程事实。助手摘要只是定位信息。关闭侧栏不取消操作；会话中的旧卡会显示其绑定版本，并在确认时重新验证。

### 12.2 前端状态归属

| 状态 | 位置 | 更新规则 |
| --- | --- | --- |
| 项目、评审、操作与来源状态 | 查询缓存，以对象ID＋revision标识 | SSE失效后重取；关键决定后用服务端结果覆盖投影 |
| 路由、当前章节、证据位置 | URL＋局部视图状态 | 显式对象链接优先，后台结果不抢导航 |
| 尚未保存正文 | 编辑器＋待恢复缓存 | 保存ACK前始终为脏；不伪造服务器revision |
| 上传字节进度 | 上传会话状态 | 完成必须由服务端核验，不按100%传输显示已评审 |
| 主要下一步／提交资格 | 服务端投影 | 前端不维护另一套判断公式 |

核心页面固定入口为当前项目、历史项目、企业知识；项目内按概览、资料、响应矩阵、章节、评审、版本与导出、提交结果展开。加载与失败按资料、风险、评分分别显示，不能整页白屏或用“0项风险”替代尚未完成。证据抽屉与编辑器保留位置；窄屏可返回详情。具体尺寸与颜色统一引用视觉主记录。

### 12.3 页面路由与加载边界

目标路由为`/projects`、`/history`、`/knowledge`，项目详情为`/bids/:bidId/{overview,materials,matrix,sections,review,versions,submission}`；历史评审显式用`reviewId`，章节用`sectionId`，证据位置用`evidenceId`。列表进入当前主要下一步，带明确对象的深链接直接打开该对象，不被最近浏览位置覆盖。

项目壳保存随页助手与上传会话，章节编辑器在证据抽屉或助手切换时保持挂载；切到另一项目前处理脏状态。Query Key包含bid、对象ID、过滤条件和展示政策revision，防止隐藏预测后命中旧可见缓存。每个模块单独加载、错误边界与重试；取消操作在确认卡上表达，不能复用页面关闭事件。

## 13. API与事件契约

[目标OpenAPI](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/openapi.json)覆盖关键写入与查询；[协议Schema](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/05-技术与设计/detailed-design/protocol.schema.json)定义冻结输入、构建、保存、操作、评分、错误和提交等边界。范围为全新系统的业务闭环，不以旧系统接口覆盖作为要求。Accepted响应的resource_kind区分已冻结评审与最新待评意图；pending_latest只表示意图排队，不表示已创建完整评审。所有操作采用明确的请求与响应对象，集合使用带稳定游标的类型化Page，下载返回短期授权；不以通用ID外壳代替业务视图。正式目标前缀为`/api/v1`；应用代码尚未实现，不代表现有应用已提供这些路由。

SSE按stream保存单调seq：先锁stream_heads，再同事务递增并写事件，提交顺序与序号一致。`Last-Event-ID`为绑定stream的签名游标；事件持久保存关键对象变化，token.delta为临时内容，断线从消息快照恢复。事件过期返回`reset_required`和快照位置。客户端去重、补拉后再恢复实时；连接时和长连接期间复查会话，不把旧链接当登录授权。

Outbox与SSE都不存完整模型提示或文件原文，只存对象引用、revision、事件类型和安全摘要。列表筛选与导出使用同一领域投影。GET不能以副作用触发训练、模型发布或资料更改。

## 14. 导出、展示政策与实交安全

`artifact_kind`至少区分`bid_body`、`review_report`、`annotated_review_copy`、`source_original`、`research_artifact`。格式字段另存；PDF不是正文的充分条件。标准提交拒绝报告和批注稿，线下事实补录仍可忠实记录已发生错传。

评审原始产物不可覆盖。新下载展示副本按当前预测显示设置和来源影响revision生成，隐藏预测数值、区间及派生分差，保留风险、覆盖、满分和官方成绩登记；页面、助手、复制、图表与新导出共用ProjectionPolicy。生成任务完成时复核policy revision，已变化则不能把旧展示文件作为当前下载返回。服务端响应不把隐藏值藏在未展示JSON字段；聊天历史中已存在的预测part也应通过当前投影处理。

已下载离线文件无法撤回。下载授权短期且绑定成员、artifact和用途，记录审计；对象私有，不以可猜测路径访问。原始模型预测可在受限服务端用于合格回流，不等于向浏览器暴露。

### 14.1 报价、比较与业务指标

报价计算为Decimal纯函数，先把招标公式转为有出处的受支持策略与参数，保存公式digest、取整规则、假设投标人集合和价格方案。API输出每步计算；未知竞争报价用情景范围，不从技术分推导实际中标概率。用户保存方案走确认命令，开关关闭时收起模块，不改变历史方案。未支持的公式返回无法计算，不由LLM临时执行代码；不包含内部成本利润。

跨轮比较固定两份正文、规则、满分和方法。完全相同规则与方法才把分差标为可比；方法不同可发起同冻结方法对两稿的对照重跑，历史原数值不改写。采用建议后未复检不显示“已提升”。业务指标仅以有效实交和经核验结果计算，未知不算未中标，候选人不算最终中标，零分母返回无数据；点分误差只纳入合格事前配对。工程运维时长不混入中标效果报表。

历史项目查询同时检索标题、工程身份、阶段和允许全文，返回原版本与出处；案例比较按用途标记，不把历史技术分泄入一般内容建议。批量导入先dry-run，按外部记录ID＋原件摘要防重，逐条保留缺失来源、成绩口径冲突和正文身份异常；部分失败留在异常队列，成功条目不回滚，重新运行只处理明确选中的异常记录。

## 15. 安全、运行与恢复

### 15.1 基础安全

一个登录门槛，成员无岗位权限划分；服务身份仍按职责区分API、解析、评分和训练，以防任意组件取得全库与外部出口。会话cookie设HttpOnly、Secure、SameSite，写请求检查CSRF与Origin；密码安全哈希，登录限流，退出撤销服务端会话。

文件转换无外网、非root、只读根文件系统、临时磁盘限额和CPU／内存／超时限制；DOCX拒绝外部关系自动取网，PDF脚本不执行，模型工具不跟随资料中的任意URL。模型出口按部署地域、供应商和允许资料类型配置，日志去除正文和凭据，敏感调试产物单独授权保存。

SQL注入、Markdown／HTML脚本、SSRF、ZIP炸弹、路径穿越与跨项目引用纳入实现验收。内部全员可看所有项目不代表无需核对对象的bid归属：同一评审不得误引用另一个项目正文。

### 15.2 部署预算与探针

| 部署单元 | 试点起始预算 | 扩容依据 |
| --- | --- | --- |
| API | 2 vCPU／2–4GB；2进程，连接池每进程最多5 | 请求延迟、PG等待；SSE连接按反向代理实测 |
| 文档／导出worker | 独立4 vCPU／8GB；OCR大页另限额 | 峰值内存、页耗时、失败率 |
| 模型worker | 2 vCPU／4GB，受供应商并发预算限制 | RPM／TPM、超时、实际费用 |
| PG与Kafka | PG 4 vCPU／8GB起；Kafka单开发节点2 vCPU／4GB起 | 活跃连接、磁盘、积压与备份窗口 |
| 研究 | 按实验临时分配CPU／内存 | 不与在线OCR抢资源 |

Kafka生产三节点按各节点和控制器分别预算，不能把单开发节点预算当整个集群。预算是各单元估计，**不能全部塞入同规格单机并宣称足够**。试点可单主机合并但要汇总资源；正式拓扑与单机故障窗口按采购确定。首轮容量用5名成员、2轮并发、100／220／400页作为假设测试，文件大小与页数限制根据实测冻结，不无依据承诺“大文件无限制”。模型费用以实际usage和采购价计，三次判断、修复、失败、图像输入与缓存分别核算。

API `/live`只查进程，`/ready`查关键配置、PG和schema兼容；broker故障时已提交命令可以在outbox等候，页面明确排队。worker探针报告队列消费与最近心跳；不以进程存在当可完成任务。记录request／command／operation／step／model_call ID关联，关注积压时长、超时、重复效果、证据缺口、SSE重置、token和费用；这些是运维指标，不作为产品中标效果指标。

### 15.3 备份、恢复与升级

试点恢复目标起始为RPO≤15分钟、RTO≤4小时，须以实际恢复演练确认。PG使用基线备份＋连续WAL归档，至少每日检查备份与恢复链；对象原件开启适合供应商的防覆盖／版本保护并跨故障域备份，保存checksum清单。PG备份成功不证明对象已备份，二者以manifest和可恢复时点核对。

恢复顺序：暂停写入与worker→恢复数据库到目标点→核验被引用对象及摘要→恢复Kafka集群及consumer group位置／重建缺失投递→提升旧attempt fence→对账未完成操作→验证提交、报告、来源与模型路由→恢复流量。后于恢复点的对象不直接删除；旧worker和旧消息先隔离。至少抽查一次实交稿、评审原件、来源链和模型产物。未恢复的对象显式缺失，不能用空内容替代。

未来数据库结构升级采用expand／migrate／contract；新worker兼容在途任务的`handler_version`与输入schema，旧任务完成或安全取消前保留旧处理器。部署回退先检查数据库兼容性，不回滚追加的真实业务决定。对象垃圾回收先按引用标记，再经过保留期及备份核验，不能由用户删除知识直接物理删除历史来源。

### 15.4 全新建库与资料入库

部署从空业务库、空对象存储和空检索索引开始，执行初始化DDL、受限角色、默认设置和方法配置；不连接旧库，不复用旧ID或状态，不设计旧系统兼容层与切换流程。人工试点资料与历史样本按新系统登记表和版本规则导入，先校验原件、成绩出处与关联，不承接任何旧系统模型资格。

私有档案导出包包含原件、manifest、实际提交和结果、更正链、人工决定、知识来源及方法／模型摘要，按引用闭包核验字节和摘要。它用于日常备份与自主留存，不是旧系统迁入项目；密钥和当前登录cookie不进入导出。

## 17. 设计审查与待验证门槛

### 17.1 三轮审查范围

| 轮次 | 核对内容 | 重点反例 |
| --- | --- | --- |
| 领域与契约 | 跨项目关系、修订、正文／报告身份、接口条件头、评分白名单 | 同名Word／PDF、旧评审被当当前、缺失值被记0分 |
| 并发与恢复 | 幂等、outbox、worker重复、fence、取消、来源撤回 | 提交后ACK丢失、取消后回调、同时保存、来源停用时应用 |

历史三轮按各自输入快照保存；用户后续Kafka、RAG与全新建设约束单独记录和检查，不冒充此前三轮已覆盖新修改。具体检查产物与执行范围见[详细设计检查记录](https://github.com/zys743551828-art/tender-docs/blob/f1e5c36c1a818668c3f61a111a0443494515bae9/04-验证与测试/detailed-design-checks/README.md)。设计文件检查、独立SQL机制验证和完整产品端到端验收分别记录，不相互替代；产品方案三轮审查的既有快照保持不变。

### 17.2 冻结前必须解决的事项

| 门槛 | 验证方法 | 失败时的行为 |
| --- | --- | --- |
| Kafka／Python Worker执行基线 | 同一假模型负载注入API断线、worker kill、broker重启、重复消息、取消与版本升级；验证consumer rebalance、位点提交与业务提交的崩溃窗口 | Kafka基础设施选择保留；未通过的消费、重试与幂等协议修正后再验收 |
| RAG与向量检索 | 真资料检索标注、profile切换、过滤少召回、来源撤回与标签隔离 | 不把索引存在视为检索质量通过；不足时提示或拒答 |
| 解析与证据 | 市政真实资料页级标注、图表／扫描／补遗回放 | 保留无法判断与缺口；不放行依赖缺口的提交 |
| DOCX与PDF转换 | 固定字体环境，对目录、表格、图片、编号、暗标及外部Word再编辑逐项验收 | 限制Word能力；PDF独立评审仍可交付 |
| 模型供应商 | 真实资料的证据正确性、JSON稳定性、时延、usage、地域和出口条件 | 保持未配置／未通过，不用合成响应冒充真实评审 |
| 评分模型 | 合格成绩配对、分组时间留出、冻结协议、独立测试及影子对照 | 原始判断可用，正式预测和区间不获发布资格 |
| 部署与恢复 | 实际账号、存储、WAL、对象校验、失效凭据、升级回退演练 | 不承诺SLA；受限试点明确恢复窗口 |
