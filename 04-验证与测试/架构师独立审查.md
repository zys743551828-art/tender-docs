# 架构师独立审查

**结论：带条件可开工。** 全新系统、Kafka＋Python Worker、PostgreSQL＋pgvector、用途隔离及完整章节三次判断的总体方向成立，不需要重做架构。工程骨架、登录、契约生成和页面框架可先行；Worker事务实现前须修正A01，自动评审去重实现前须澄清A02，上传模块契约冻结前须闭合A03。当前不宜将“详细设计可以不加解释地直接分派给多人并行实现”作为准入结论。

本轮只做独立审查及最小反例，未修改产品主记录、技术主记录、应用代码或历史检查结果。没有发现必须停止全部基础开发的P0问题；下列问题分别阻塞对应实施边界。

## 1. 按严重程度排序的发现

### A01 · P1：合法Worker事务路径与数据库能力角色不闭合

**阻塞边界：T0的Worker领取／提交联调；研究批次执行。不是仅研究模块的问题。**

依据：[接口与任务实现规约](../05-技术与设计/detailed-design/接口与任务实现规约.md)第88、100—103行要求领取和完成事务先锁bid，再操作operation与阶段收据；[roles.sql](../05-技术与设计/detailed-design/roles.sql)第15—21、30—37行给普通Worker的bids权限仅为SELECT，给研究Worker的权限还缺少step_receipts、effect_receipts、model_calls。[保留功能实现规约](../05-技术与设计/detailed-design/保留功能实现规约.md)第99行要求研究费用预留与model_calls reserved在同一事务。

触发场景：新Worker按规约使用WORKER_DATABASE_DSN，执行`SELECT ... FROM design.bids ... FOR UPDATE`。PostgreSQL行锁需要UPDATE权限，仅SELECT不够；实际返回`42501 permission denied for table bids`，任务在领取阶段即失败。研究Worker同样无法加该锁，也不能读阶段收据、写付费调用账本；反过来由普通Worker调用reserve_research_fee又没有EXECUTE权限。当前两类角色均不能独立完成规定的研究事务。

**已验证：** 在隔离的真实PostgreSQL 17.11＋pgvector空库运行现有五份SQL，以SET LOCAL ROLE执行上述合法路径，共复现5个42501反例。见[角色反例结果](architect-review-checks/role-counterexamples.json)。这不是模型或对象存储配置缺失造成的。

建议修正：明确每个领取、完成、预算及账单事务由哪个进程、哪个能力角色执行；补齐最小权限，或提供限制用途、固定search_path且撤销PUBLIC执行权的数据库入口。保留bid锁序，不能简单删除锁规避错误；也不能让Worker使用初始化owner或授予官方成绩、人工决定、业务模型路由写权限。研究调度与研究执行若刻意分离，须明确两者的事务边界和入口，确保预算与调用账本仍在一个PG事务。

验收条件：以真实非owner、非superuser的LOGIN账号完成一次领取→付费调用预留→完成的合法事务；调用账本插入失败时预留整体回滚；重复调用不重复占预算；取消、迟到fence拒绝发布；原有禁止读取标签和禁止发布业务模型的负向权限检查继续通过。

现有检查的遗漏：[probe_retained_sql.py](development-readiness-checks/probe_retained_sql.py)第88—96行的预算正向检查以owner执行，第98—101行才切换角色检查越权拒绝。它证明预算原子性和部分禁止路径，尚未证明Worker合法事务可执行。原有检查结果在其声明范围内有效。

### A02 · P1：语义摘要缺少冻结时间的字段投影规则，同内容归并存在两种不相容实现

**阻塞边界：RequestReview、自动触发归并及评审缓存身份实现。**

依据：[详细技术设计](../05-技术与设计/AI投标工作台详细技术设计.md)第122行要求冻结manifest包含冻结时刻，并用RFC 8785规范JSON计算摘要；第124行已经区分评审内容input_digest与另含rerun_nonce的operation.input_digest；第178行要求按钮、聊天、自动事件按相同input_hash共用在途运行。[ReviewManifest](../05-技术与设计/detailed-design/protocol.schema.json)第119—139行把frozen_at设为必填，但没有另一个明确定义的“参与内容去重的字段投影”。

触发场景：相同正文、资料、规则、事实、方法和来源，自动请求于01:00:00冻结，按钮请求于01:00:01再次组装manifest。若实现者按第122行直接散列整个manifest，两个摘要不同，会创建新的待评意图或执行身份；同内容归并失效，可能产生重复模型调用。若另一团队自行排除时间，则又可能与记录和缓存团队的摘要不一致。

**已验证：** 两份仅frozen_at相差一秒的合成ReviewManifest均通过现有Schema，按规范JSON适用子集序列化后的SHA-256不同。见[契约反例结果](architect-review-checks/contract-counterexamples.json)。该结果证明字段规则缺口及按全文散列时的后果，不是已运行应用发生重复调用的证据。

建议修正：在现有“评审内容身份／执行nonce身份”区分之上，明确完整冻结记录摘要与内容归并键各自的规范字段、引用版本和计算时机，并给固定输入输出向量。frozen_at作为审计时刻如何处理必须唯一；检索as_of有业务效力，不能把所有时间字段一概删掉。应由服务端确定稳定的评估时点和生效来源集合，重用既有冻结运行前复核当前来源／效力；生效截止改变导致允许来源不同，应形成明确的新输入。

验收条件：同内容在不同请求时刻、不同入口得到同一在途operation；显式rerun_nonce得到独立执行但保留相同内容身份；真正改变评估时点／来源有效集合、规则事实或方法时得到新身份；输入全量证据摘要可还原。以上均有固定散列向量及并发测试。

现有检查的遗漏：Schema检查只证明frozen_at格式合法，源文件摘要检查只证明检查针对哪份文件；二者都不证明业务上等价的两次请求具有相同去重键。

### A03 · P2：文件版本CAS冲突后保留了字节，但缺少用户重新选择目标的命令

**阻塞边界：A1上传版本冲突恢复的交付；不阻塞登录或首次无冲突上传。**

依据：[保留功能实现规约](../05-技术与设计/detailed-design/保留功能实现规约.md)第25—29行把expected_file_revision固定在UploadTarget，并要求批次412时保留核验结果，用户可选择基于最新版本继续或另建文件。[domain.sql](../05-技术与设计/detailed-design/domain.sql)第123—127行把file_id和expected_file_revision保存在upload_transfers。[BatchCommit](../05-技术与设计/detailed-design/protocol.schema.json)第791—811行只接受upload ID集合及部分接收标记。现有上传路径只有创建、查询、complete、authorizations、abort及commit，未定义重新绑定目标的命令。

触发场景：两人都基于文件head revision=2上传不同修改稿。第一人提交后head=3，第二人的已核验上传在commit得到412。刷新bid ETag再提交并不能改变其upload_transfers.expected_file_revision=2，仍会失败。authorizations只接受片号，complete只接受片收据和摘要；CreateUpload也没有复用已核验upload的字段。界面无法按现有契约完成规约承诺的“保留结果、重新选择”。

**已验证：** 给BatchCommit附加目标和新expected revision会被additionalProperties=false拒绝；已枚举当前上传路径，未找到接收该目标变更或引用旧核验结果的新命令。见[契约反例结果](architect-review-checks/contract-counterexamples.json)。这是接口恢复路径缺口，不表示版本CAS本身错误；CAS拒绝过期head应保留。

建议修正：定义一次显式、有审计且可幂等的重新绑定／重新确认命令，或创建新提交意图并引用原verified upload；携带最新文件head和目标、校验同bid及角色，保留原传输目标和冲突历史。不要由后台静默把旧expected revision改成最新值。将核验字节保留期限、重新确认权限及过期反馈写入契约。

验收条件：两个并发修改稿只允许一个先推进head；另一人收到412后不重传字节即可选择基于最新head继续或另建文件；选择后再次竞争仍执行CAS；重复确认不产生重复版本；跨bid、角色不符及已过期核验对象均拒绝。

## 2. 核查后应保持的设计

| 核查范围 | 判断与边界 |
| --- | --- |
| 建设范围和基础设施 | 新建设、不做旧库兼容；Kafka传输、PG事实和Outbox分工清楚。没有因沿用GitHub功能而承接旧模型资格。 |
| 原件、文件与实交身份 | 内容去重与来源身份分开；文件head有复合外键和CAS，标准提交要求评审正文一致，报告／批注稿不是正文。A03补恢复入口即可，不应放宽约束。 |
| 规则沿用和事实撤回 | 条件、例外、生效来源及原决定共同决定沿用；fact head新集更正并保留旧集，全部撤回仍有非零修订。应用用例还须核验JSON和数组语义，设计已明确这点。 |
| Kafka执行 | generation与fence分开、手动offset、PG持久重试、取消与完成竞争、Outbox续租均有具体协议。A01修正后可据此实施；尚不能把机制探针等同实际Worker的acquire／finish验收。 |
| 评分与研究隔离 | 正式输入受限账号、完整相关章节、三次有效独立判断、分组时间留出、标签受控导出、模型独立验收和人工发布方向一致。普通聊天RAG不得代替完整评分范围，应继续保持。 |
| 来源撤回 | 权威head与祖先闭包决定新引用／应用资格，缓存清理和Kafka传播只加速失效。已存在历史引用保留身份与失效提示，符合不可重写历史的要求。 |
| 首个开发范围 | T0后可先交付上传PDF→风险与原页→修改复检→实际提交；完整编辑器、企业知识维护及正式预测精度不应成为最小PDF链路的前置。真实适配未配置时明确不可用。 |
| 备份恢复 | PG恢复点、被引用对象摘要、Kafka位点／收据对账、旧fence隔离和模型资产有恢复顺序。该设计可作为实施起点，真实WAL／对象一致性及RPO／RTO仍是上线前运行验收，未演练本身不算本轮设计缺陷。 |

## 3. 实际执行的验证与未验证范围

- 已通读产品关键路径、技术主记录、五份实施规约及数据库／权限／执行策略；针对上传、评审身份、研究预算和评分隔离交叉核对Schema、OpenAPI、SQL及现有probe。没有逐一调用91个API，也未把静态形状通过解释为业务通过。
- 在全新隔离PG容器按现有初始化顺序执行五份SQL，复现5个合法Worker路径的权限错误；容器无网络、无真实资料，完成后删除。
- 执行合成契约反例：两个合法manifest仅冻结时刻不同产生不同散列；冲突后重设目标的BatchCommit扩展字段被拒绝，并盘点上传命令路径。
- 未执行：业务API、浏览器、实际Kafka Worker、真实模型调用与计费、真实OCR／Embedding／检索效果、官方成绩精度、生产备份恢复和多节点故障。原检查中的来源过滤、权限拒绝、租约与预算并发机制证据保留有效，本轮不重写其结论。

```bash
python architect-review-checks/probe_architect.py
python architect-review-checks/probe_contract_paths.py
```

第二个脚本需要jsonschema。输入身份和本轮证据清单见[审查记录](architect-review-checks/review-record.json)。脚本成功表示反例已按预期复现，不能解释为相应缺陷已修复。
