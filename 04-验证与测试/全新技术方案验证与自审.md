## 1. 审查对象与结论范围

对象为[全新系统技术方案](../05-技术与设计/AI投标工作台全新系统技术方案.md)，选型依据为[成熟方案调研](../01-背景与市场研究/成熟AI系统与技术组件调研.md)。实验程序从零编写，不导入旧应用实现；每组结果说明具体覆盖范围。

推荐路线具备可重复的关键机制证据，同时保留生产运行和真实数据门槛。五组实验均为本地隔离运行；部分负对照故意产生错误以验证修正必要性，它们被正确复现才算该项实验符合预期。实验不构成完整产品、真实评分或生产部署验收。

源资料清单保存28个官方仓库77份成功取得文件的固定提交与摘要；404和域名受限亦保留记录。当前源码、发行包和生产部署的成熟度不能混用：读取main用于机制调研，实际实验使用另外锁定的发行版本。

## 3. 五组机制实验

### 3.1 Temporal：持久等待、重试与版本检查

程序：[probe_temporal.py](architecture-checks/probe_temporal.py)；结果：[temporal-result.json](architecture-checks/temporal-result.json)。

| 场景 | 操作 | 实际结果 | 支持的结论 |
| --- | --- | --- | --- |
| 提交后故障，未幂等 | Activity先提交PG计数，再故意失败 | 第二次尝试后业务计数为2 | 工作流重试不等于外部副作用恰好一次 |
| 同样故障，增加唯一操作键 | 首次提交后失败，第二次读已有结果 | 两次尝试，业务计数为1 | 幂等领域事务可控制本实验的重复写入 |
| 人工等待，Worker退出 | 工作流等待，停Worker，期间发确认信号，再启动新Worker | 信号保留并恢复完成 | 执行历史可以承接Worker中断与人工等待 |
| 旧对象版本 | 输入预期revision1，数据库改为2 | 返回stale_rejected，无副作用 | 恢复时可以重新校验对象，不盲用历史批准 |
| 等待中取消 | 取消尚未执行活动的工作流 | 确认为取消，未产生业务写入 | 请求与终态应分别处理 |

未验证：Temporal服务端崩溃与恢复、正式PG持久后端、网络分区、生产认证、跨版本Workflow回放、长Activity取消和云模型重试计费。不得把Worker重启写成完整灾备演练。

### 3.2 LangGraph：interrupt恢复的重复执行

程序：[probe_langgraph.py](architecture-checks/probe_langgraph.py)；结果：[langgraph-result.json](architecture-checks/langgraph-result.json)。

创建图与SQLite checkpoint，中断后关闭连接，重开存储并重新编译，再resume。两组节点均从头执行两次；故意放在中断前的未保护计数产生2次，使用操作唯一约束后计数为1。

这段中断前写入是负对照，不是推荐的人工确认实现。正式系统不能在批准前写业务决定；幂等只控制重复，不能替代授权。结果支持将业务提交和图状态分离，不支持“LangGraph不可用”或“比Temporal性能更差”的结论。

### 3.3 PostgreSQL：并发、游标、来源与冲突

程序：[probe_postgres.py](architecture-checks/probe_postgres.py)；结果：[postgres-result.json](architecture-checks/postgres-result.json)。

| 场景 | 结果 |
| --- | --- |
| 32次并发相同命令 | commands、effects、outbox各1条；对象revision仅增加1；响应一致 |
| 同键不同内容 | 明确冲突，未产生新副作用 |
| 旧revision和提交前故障 | 前提不满足被拒绝；故障事务整体回滚，业务、Outbox和revision保持一致 |
| 全局自增事件游标负对照 | seq1未提交，seq2先提交，客户端游标推进2；之后seq1被漏过 |
| 同stream锁行并递增序号 | 第二事务等待第一提交，事件序号按1、2可续传 |
| 撤回后的旧缓存 | 缓存版本1，权威状态已为停用版本2，不能新增引用 |
| 派生来源负对照 | 只检查直接group错误允许知识5；递归祖先过滤后只返回允许的1、6 |
| 冲突成绩 | 简单排除conflict会错误回退旧52.1；未解决冲突整体阻断时无有效标签 |

这不是完整领域DDL。认证、不同成员用不同键消费同一提案、真实撤回并发、完整归档和迁入还需实现验收；不得把简化实验当成已完成业务模块。

### 3.4 pgvector：强过滤与候选不足

程序：[probe_pgvector.py](architecture-checks/probe_pgvector.py)；结果：[pgvector-result.json](architecture-checks/pgvector-result.json)。

5000条合成三维向量，只有1%符合过滤条件。为暴露机制而固定HNSW执行计划，ef_search20、关闭迭代时返回0条；精确检索返回10条，开启strict_order迭代后也返回10条，本次ID与精确基线相同。

证明的是全局ANN候选后过滤可能不足，以及这一配置下的修正。没有使用真实中文embedding，不代表真实召回、生产吞吐或所有查询都达到精确排序。正式查询必须记录计划、允许集合、扫描上限及召回对照。

### 3.5 sklearn：相关样本泄漏与有限校准

程序：[probe_scoring.py](architecture-checks/probe_scoring.py)；结果：[scoring-result.json](architecture-checks/scoring-result.json)。

构造24个相关组、192条合成样本，同组目标近似相同。sklearn Pipeline将预处理放在训练折内。随机切分MAE约0.0795，整组GroupKFold留出约13.9687；所有严格折的组交集为空。

这些数字说明组泄漏可以制造虚假高精度，不能解读为本产品真实评分误差。另检验90%有限样本残差分位数：只有5个校准残差时所需次序超出样本数，拒绝声称有限半宽；21个残差时按有限样本次序取值。没有检验真实投标分布的交换性或实际区间覆盖。

## 5. 重现与检查方法

隔离程序和依赖见[执行说明](architecture-checks/README.md)。每个程序有非零失败退出；只有真实运行产生的结果才用于本次结论。官方资料下载结果含失败项，不因部分地址404就用推测补足来源。

[check_design_assets.py](architecture-checks/check_design_assets.py)检查来源快照／摘要、需求追踪、产物身份和本地链接；带资料缓存参数时重新核对实际下载的77份文件。它不自动证明自然语言架构全部正确，也不替代五组程序重跑。

检查记录见[design-assets-result.json](architecture-checks/design-assets-result.json)，输入与结果摘要见[运行清单](architecture-checks/run-manifest.json)。源资料不能再次下载时仍可检查清单结构，但应明确跳过了原文摘要复核，不能写成全部来源已重新访问。

旧应用曾额外运行任务、配对与模型登记相关22项测试，全部通过，有1条测试客户端弃用警告。结果仅用于理解旧基线；没有把它作为全新架构已实现或已经兼容旧数据的证据。

## 7. 后续验证门槛

| 门槛 | 必需输入 | 通过证据 |
| --- | --- | --- |
| 领域契约 | DDL、OpenAPI、状态保护条件与执行器 | 并发、重放、认证、旧卡、错误恢复和跨模块引用测试 |
| 文档质量 | 真实招标／补遗／正文、表格与扫描样本及原页标注 | 同基准解析器比较、覆盖缺口和定位准确性 |
| 检索有效 | 经标注的查询与允许／不允许参考来源 | 相关性、召回、来源准确、时效和泄漏反例；对比精确与ANN |
| 正式评分 | 实际提交稿与官方技术分、满分和来源，冻结协议 | 独立项目／时间测试、基线增益、覆盖与区间、稳定性和分层结果 |
| 生产运行 | 真实供应商、生产Temporal与数据库、完整负载 | 直传、超时取消、升级历史回放、容量、备份恢复与回退演练 |
| 使用体验 | 投标人员和真实任务 | 上传至复评、选参考、提交、成绩核验等任务观察及修正 |

其中正式精度门槛仍待真实案例与业务认可，不把建议数字变成效果承诺。用户可以据此开始全新系统的契约和骨架实施；本次交付止于技术设计、调研和机制证据。
