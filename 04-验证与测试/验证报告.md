## 1. 结论与可用范围

本报告只陈述已经做过的验证。系统（tender-app）的自动评审流水线、项目级功能开关、规则与依据、响应矩阵、确定性检测、评分预测与校准、报价、提交闸门、报告导出、度量和任务协议，已用自动化测试在真实 PostgreSQL 16 上验证了逻辑；前端页面行为由组件测试验证；一条浏览器端到端冒烟在 Chromium 中走通了从登录到度量的主要路径。所有这些都使用脚本化的模型和测试替身，没有调用真实模型，也没有使用真实标书。因此：

- 系统在真实招标文件、真实技术标正文和真实模型上的表现，包括废标／否决项的召回与误报、一致性与范围残留检测的误报率、评分预测与官方技术分的差距，依赖服务器与数据，尚未验证，本报告不给出这些指标。
- 评分预测的四层（逐项判断、特征、打分模型、比较式锚定）与入库、批量预测、评测、登记、产品内校准的整条流程已在合成数据上跑通（第 2.5 节）；官方成绩与预测的配对数为 0（见第 4 节），还没有用真实成绩训练的打分模型，界面显示“未校准”，预测精度不可评价。
- Windows Docker Desktop 上的核心服务启动、迁移、Kafka 主题初始化与 OSS 独立上传探针已验证（第 2.9 节）；真实模型对合成资料的整轮评审和导出已通过（第 2.10 节）。Milvus、MLflow、浏览器整轮交互、真实标书质量、备份恢复与性能压测尚未验证。

### 2.4 浏览器端到端冒烟

`backend/tools/smoke/smoke_server.py` 起真实 API、真实 PostgreSQL 与进程内 worker（脚本化模型、内存对象存储），自动评审在进程内跑完；前端用构建产物运行；`backend/tools/smoke/e2e.py` 用 Playwright 驱动 Chromium，用 `demo` 账号依次完成：

1. 登录；
2. 项目总览：项目行显示否决风险“1 个未处理”和“处理否决风险”按钮；
3. 评审报告：结论、下一步与技术分预测（显示“只覆盖 8 / 60 分”）；
4. 导出 Word 评审报告，下载得到 `.docx`；
5. 从“处理否决风险”进入问题页，招标文件要求与施组正文写法并排，填写理由并确认问题；
6. 在依据页点“全部按原文确认”，一次确认全部待核对的规则；
7. 报价页显示“已按招标文件填好评标价规则，请核对”，填写竞争对手报价估计与候选报价，实时试算后保存；
8. 在设置页关闭报价模块并保存，导航中不出现“报价”；
9. 打开度量页；
10. 以 390px 宽的窄屏打开评审报告，页面没有横向滚动。

脚本同时收集页面脚本错误与状态码 400 以上的响应（登录前探测会话的 `/me` 除外），任何一条都会使冒烟失败；这次运行没有收集到任何一条。冒烟不覆盖：资料上传（对象存储预签名直传）、Kafka、真实模型、批注版 PDF、手动开始评审与其他开关在浏览器中的操作。

### 2.5 评分预测流程的合成数据联调

用合成数据把评分预测的整条流程逐段接起来，验证各段的交接格式与产品内的校准路径（合成数据只证明程序行为，不代表真实精度）：

1. **入库 → 批量预测 → 评测**：入库工具对 12 行合成登记表归档出 10 份案例（缺文件、文件名歧义各 1 行被拒），生成评分配对集；批量预测工具直接读取它、从本地缓存定位原件、经真实上传接口入库并跑完流水线，每份样本写出格式 B；评测程序读取两者并给出“不可评价”（准入 5 份，低于下限），排除原因与标签来源构成如实列出。联调同时核对了两处交接细节：同场成绩缺失、公示里单个分数未公布时都写为空值，评测程序按缺失处理。
2. **训练 → 登记 → 产品显示**：研究侧合成生成器产出约 300 份格式 A／B（123 个项目），交叉验证选定“岭回归＋锚定”，评估通过并导出打分模型；用 `bidwb-admin` 的登记逻辑把这份模型登记到业务环境后，地区填“合肥”、工程类型为市政道路的项目，预测显示“已校准”，分数 36.9／60、约 80% 区间 33.3–40.5，并带出训练组数与误差。项目地区（如“合肥”）与模型适用范围（训练数据出现过的完整地区，如“安徽省合肥市”）按地名包含关系匹配。
3. **公式一致**：研究侧导出模型时生成参考向量（`protocols/scoring-model-1.golden.json`），后端测试读取同一文件，产品侧计算结果与之逐位一致；两侧特征名单逐项一致。

### 2.6 独立代码审查

后端评审流水线、核对与预测、报告与导出、报价、提交闸门由一次独立代码审查逐模块检查，找出 11 项缺陷，均已修复并补了回归测试（见 2.2 节 `test_auto_pipeline.py`、`test_parsing.py`）：

| 缺陷 | 修复 |
| --- | --- |
| 提取规则期间上传补遗，较早的提取结果晚完成时成为最新规则包，流水线停在“评审中”且重新评审无效 | 规则提取入库前核对资料仍是最新，过时的结果不入库；流水线对“已完成却没有对应规则包”的情况重新提取 |
| 上传图纸、清单或回执后，提交闸门要求它们进入本轮输入，而评审输入不含这些资料，导致永远不能登记提交 | 闸门只核对招标文件、补遗和技术标正文 |
| 手动开始模式下更新正文后，项目状态停在“评审中” | 等待开始时回到旧报告对应的状态 |
| 冻结输入被拒绝（如资料晚于截止时间）时项目一直“评审中”，回收器整批回滚，上传也随之失败 | 冻结在保存点内执行，被拒时项目为“评审中断”并在流水线状态给出原因；回收器按项目隔离；上传后的推进失败不回滚上传 |
| PDF 文本层的 U+FFFE（行末连字符标记）导致导出 Word 失败 | 解析时按连字处理并去掉 XML 不允许的字符，导出时再过滤一次 |
| 同一提交登记多条结果时校准重复计数 | 每个有效提交只取最新一条带技术分的结果 |
| 规则或事实更正后项目仍显示“可登记提交” | `settle` 在输入变化时把项目降为“问题待处理”；“下一步”只在报告是最新时提示登记提交 |
| “重新评审”不重跑覆盖不完整的核对 | 覆盖度不是完整的核对可以重跑 |
| 手动开始的判定比较了数据库与应用主机两个时钟 | 改用“要求开始”的标记，冻结时清除 |
| 打开“自动开始评审”后不推进 | 开关变化后立即推进一次 |
| 极大的报价数字使计算溢出 | 十进制字符串至多 24 个字符，计算使用足够的精度 |

### 2.7 这些测试没有证明什么

- 模型是脚本化的（按提示词内容返回预设 JSON），检验的是程序对模型输出的处理：落地校验、降级规则、覆盖度、写入与状态推进，不是模型本身的质量。
- 合成的 PDF 只有几页，规模、版面和措辞远小于真实标书；检测器的误报率没有在真实正文上度量。
- Kafka 用进程内的消息总线替代，对象存储用内存实现或 moto；它们的真实行为（再均衡与位点、分片直传与跨域、预签名地址）没有测过。
- 导出的 PDF 批注只检查了批注数量，没有在真实阅读器里目视核对高亮位置。
- 浏览器冒烟只走一条路径、一个合成项目，不代表各页面在所有状态下与真实后端的联调都已验证。
- 评分预测的合成数据按设定的规律生成（官方分与系统估计之间有已知关系），评测“通过”只说明训练、选型、区间与导出的程序正确；真实标书上的误差、哪种方法胜出、锚定是否有用，都要用真实成绩评测后才知道。
- 数据集原件的对象存储工具只对内存假桶做过测试，并核对了真实 SDK 生成的请求格式；没有连过真实的 OSS 桶。

## 3. 研究侧试验（与系统流水线相互独立）

[tender-research](https://github.com/zys743551828-art/tender-research) 的程序在真实资料上做过一组试验，输出保存在 [results](https://github.com/zys743551828-art/tender-research/tree/main/results)。它们回答的是“读取公开规则和读整份技术标时，通用模型会出什么问题”，用的是研究侧的程序，不是 tender-app 的流水线，结果不能代替系统在真实数据上的评测。

真实输入为 [RULESET-001](https://github.com/zys743551828-art/tender-datasets/blob/main/公开规则资料/README.md) 的 12 份官方文件（531 页）和 CASE-001 的两份文件（269 页），合计 14 份原件、800 页，原件 SHA-256 与资料清单一致。运行环境为 Python 3.13，OCR 另用独立依赖环境。

### 3.1 解析与检索

在 32 题的 [RULE-001 评测集](https://github.com/zys743551828-art/tender-datasets/blob/main/评测集/RULE-001.json)（政策 6 题、道路 13 题、园林边界 13 题，另有 2 项可见页负向探针）上比较 9 种解析加窗口的组合（pypdf、pdfplumber 裁剪、裁剪加稀疏页渲染保护；窗口 900 字／重叠 180、1500 字／重叠 300、整页），统一使用 BM25 与中文二字片段。参考由开发者从原文建立并参与开发，是已知参考回归，不是盲测。

- 裁剪加稀疏页渲染保护的三种窗口都通过 2 项可见页探针（单纯 pypdf 为 0／2，仅裁剪为 1／2）；所需摘录在前 3 条内齐全的题数为 32／32（整页窗口为 32／32，首条齐全为 28／32）。所有候选的返回摘录字符校验和范围错误均为 0。
- 已知题在前 3 条齐全不证明未知问题或整份技术标评分的完整性；RULE-017 需要原条款和补疑两个文件，不能只凭第一条完成。

系统现行的解析器是 pypdfium2 文字层提取，与上述研究侧的比较对象不是同一实现；系统的解析在合成 PDF 上有测试（第 2 节），在真实资料上的页码、顺序和坐标准确性尚未验证。

### 3.2 扫描页识别

对 3 页做了本地 OCR 探针（RapidOCR、ONNX CPU）：扫描收费表上找回标题与 15.12 万元、10.8 万元、2.16 万元 4 个锚点（普通抽取只有页脚），复杂跨行评审表找到 3 个锚点，空白尾页返回 0 行。系统当前不含 OCR：没有文字层的页只记缺口，不产生证据。扫描页识别的整页准确率、表格结构、旋转与低清图纸没有评测。

### 3.3 成绩与阶段导入

某公开评标表的 13 列版式导入 208 行，序号完整无重复；5 个技术总分为 91.12—91.33，其余 203 个“/”保留为未披露，没有转换为 0；两个候选公示识别为候选阶段，不计入最终中标。5 项已知检查通过，仅覆盖一个版式。

### 3.4 模型读取公开规则

用 DeepSeek 的 Flash 与 Pro 两个型号，在同样的 32 题上做规则问答（非思考模式、温度 0、JSON 输出；模型选证据 ID，程序回填原文），共 64 次调用，字段与证据绑定的自动校验均通过（32／32），不能解释为语义准确率。开发者逐题复核发现的问题包括：把商务权重加进技术权重、把不同指标说成冲突、少列一条不足人数的例外、擅自给出年份更正值、没有选择原招标文件作来源。这类错误是系统设计“模型引用必须通过程序落地校验、规则可由人确认”的依据。

### 3.5 CASE-001 整份技术标直出分数

对 CASE-001（污水管网改造及新建）的整份招标文件与技术标正文做 13 次全文请求（12 次完成、1 次未完成生成）和 1 次图像探针；用户报送的成绩 4.26 与入围门槛不进入提示，研究者已知晓成绩，属单例探索，不是盲测。

- 全文直出的候选分数随方法在 3.80 到 4.50 之间变化，另有两次拒绝估分；前四份无页绑定的输出共 132 条引用，其中 111 条文字匹配、21 条不匹配（错页、表格重排、引文改写）；页 ID 绑定后仍出现真实问题配错证据页等语义失败。
- 共 61 条模型发现经开发者逐项复核，没有独立工程准确率或召回率。
- 结论：模型可以提出有来源、需人复核的候选问题；整份直出总分未经校准，不足以用于入围判断。这是系统采用“逐条评分条款评估、区间保守、标注未校准、用官方成绩校准”的依据；系统自身的预测在真实数据上没有评测。

### 3.6 研究侧的闭环夹具

研究侧另有用 SQLite 与内容寻址文件实现的版本闭环夹具（冻结、更正、租约、整包版本与回退、备份恢复）和 NumPy 闭式回归的回测框架，用合成数据验证程序行为，不代表预测精度，也不是 tender-app 的实现。

## 4. 评分预测与校准的数据条件

官方成绩与系统预测的配对数为 0：目前只有 1 例完整正文与用户报送结果关联（CASE-001，具体分值与来源状态见其[说明](https://github.com/zys743551828-art/tender-datasets/blob/main/CASE-001_广德_污水管网改造及新建/README.md)），官方成绩原件尚未核验，没有任何一份系统预测与官方成绩配对。还没有用真实成绩训练、验收通过的打分模型，所以界面显示“未校准”的逐项合计，预测只用于排出可能的失分点，不是对结果的承诺；在线对照要 20 组以上才给出误差。第一批约 300 份历史样本到位后按一期方案 8.3 节评测，评测通过的模型先登记到影子环境对照，再登记到业务环境。需要补充的数据见[数据管理规范](../03-数据与案例/数据管理规范.md)第 2.3 节。

## 6. 复现

```bash
# 后端（需要可建库的 PostgreSQL 16，设置 BIDWB_TEST_ADMIN_DSN）
cd tender-app/backend
pytest -q
ruff check . && ruff format --check . && mypy src && bandit -r src
python tools/export_contracts.py --check      # 契约与代码一致

# 前端
cd tender-app/frontend
npm run format:check && npm run lint && npm run typecheck && npm test && npm run build

# 浏览器端到端冒烟（需要 Playwright 与 Chromium）
cd tender-app/backend
python tools/smoke/smoke_server.py             # 打印 READY project <id>
# 另开终端：构建前端后用 vite preview 代理到 API，再运行
python tools/smoke/e2e.py <project_id>

# 部署编排静态检查
cd tender-app/deploy && python check_compose.py

# 研究侧
cd tender-research && python -m pytest -q && ruff check .

# 评分预测流程（真实数据到位后；命令说明见一期方案 8.3 节）
python -m tender_research.intake --sheet 样本登记表.csv --inbox 收件 --datasets ../tender-datasets --upload
python -m tools.batch.predict_dataset ../tender-datasets/评分配对集.json --out 系统预测 --cache-dir 缓存   # 在 tender-app/backend 下
python -m tender_research.score_eval --pairs ../tender-datasets/评分配对集.json --predictions 系统预测 --protocol 评测协议.json --name <实验名>

python tender-docs/05-技术与设计/contracts/calculate_costs.py
```
