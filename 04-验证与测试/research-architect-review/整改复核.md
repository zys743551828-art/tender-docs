## 原反例闭合

RS01：价格 token 参数必须类型为 int 且精确匹配 descriptor 的4096／1000000；当前 profile_digest 也必须匹配。原同 digest、token上界1／2配置在预留前被 RESEARCH_PRICE_INVALID 拒绝，外部请求零次。预览、冻结价格身份、实际请求与保守费用预留共享同一规范上界，实际 usage 仍标估算而非供应商发票。

RS02：API 预检／stage 对象与最终发布分离，最终在 bid → graph 事务内重新构造完整权威映射并比对摘要。映射由 API-only append-only 表保存，研究角色没有其任意扫描／写入能力。研究调用每次预留时及最终发布时，受限函数从实际 operation／attempt／run／sample／当前提交与成绩头／review／chapter／preview 映射派生资格，绑定完整证据全集、精确 parse／页／原件 hash、原业务 as_of 和全部祖先 head；不接受 Worker 自报来源白名单。非 read committed 明确拒绝。

原“冻结后撤回正文根仍发三次请求”探针现得到 failed、零新请求、零 model_calls，未发布研究结果。计算完成后的 result stage 期间撤回也阻止最终发布，已发生的三次已知调用账本仍保留。该行为同时保护来源效力和真实费用，不用抹除调用来制造成功。

## 事务与权限判断

新 SQL 在架构师另建的全新隔离数据库初始化，业务实际使用受限 API／Worker／研究 LOGIN；owner 只用于新库结构与账号。合法来源资格路径可执行，错误章节、旧 parse 子来源搭新证据、RR、撤回及无权读取映射路径拒绝。固定 search_path、PUBLIC revoke 和最小 EXECUTE 授权与已审源码一致，未对历史库热补。

manifest、完整章节、原始响应和研究结果均先读取元数据后退出数据库，再做对象 I/O；发布只登记已准备的 blob 元数据。实际模型调用也在连接外。独立执行的 pg_stat_activity 机制检查覆盖 API 与研究角色在 GET／PUT／模型调用时无闲置业务事务；源码调用链同时核对没有在持 bid／run／receipt／图锁时调用对象网络。审查不以单个监测查询代替调用链判断。

## RS03：新资料准入改变冻结组后批次仍继续执行（P2，阻塞受影响研究运行）

位置：冻结 `packages/research/outcomes.py:428`，尤其449–452；`packages/research/worker.py:63`（73–78仅核提交与成绩身份）；`deploy/sql/research-source-qualification.sql` 的执行资格关联未绑定原冻结source_group身份。手工 record_grouping 的暂停路径没有覆盖 admit 的自动归组。

触发：已有冻结并运行的研究批次。另一个同工程、不同轮次的资料完成成绩核验并执行 sample-admission，尚未进行后续人工归组；自动连通组重算移动原样本 source_group_id。旧 run 未暂停，调用前与发布时亦未对比原冻结组身份。

独立实证：新空 PostgreSQL、受限 API／研究角色、实际 ASGI 成绩核验与 sample-admission 后，确认旧组 ID 已改变、run 仍 running；随后原 process 继续发送三次 Mock 请求，条目 succeeded。见 `candidate02-admission-group-counterexample.json`、`candidate02-group-delta-junit.xml` 和 `probe_admission_group_delta.py`。该单例“通过”代表成功复现缺陷，不代表组隔离通过。探针首轮撞到工程／标段／轮次唯一键属于夹具问题，改为同工程第二轮后成立；首次失败 JUnit 保留。

修正：自动准入与人工归组共用受影响运行失效逻辑；调用预留和成功发布还应核对服务器冻结的组／样本身份，不能只依赖 run 未暂停。新增组协调需维持91143 → 有序bid → operation／receipt／run → 图锁的统一顺序，不在已持bid后反向等91143。历史成功产物及真实 usage 保留，不能由恢复偷偷改掉原划分。

验收：新增同工程成员及连接既有组的资料准入先提交时，旧批次暂停且后续零新调用；推理期间发生变更时，拒旧结果发布但保留已发生的调用账本；重新冻结必须重新核验全组时间与独立集合，不能沿用旧组标识。组不变的合法执行、unknown／取消和最小权限不得回退。
